Beyond All Reason command inventory vs Budget Annihilation
Date: 2026-08-11

Scope
=====

budget_design_philosophy.html is the authority. "BAR Inspiration, Project
Identity" makes BAR the ergonomics reference and the gameplay fallback, and
"Commands require real systems" makes an authoritative system the precondition
for any button, hotkey, cursor, or preview. So this audit answers two
questions per command, not one:

  1. Does BAR expose it, and on which unitDefs?
  2. Does OUR equivalent exist end to end -- hotkey, input path, server
     authorization, sim execution, presentation -- for every host that owns
     the capability?

A command we expose without a system behind it is dead UI and must go. A
system we own without a command is unreachable functionality and must gain
one. Both are defects; this document lists what was found of each.

Sources: ../Beyond-All-Reason luaui/Widgets/gui_ordermenu.lua (commandInfo +
hiddenCommands), language/en/interface.json ui.orderMenu.*, the CMD./CMD_
constants actually referenced by BAR's Lua, and the units/ unitDef flags
(onoffable, removestop, removewait, cancapture, cancloak, canmanualfire,
canattackground, hightrajectory, transportcapacity, builddistance,
workertime).


1. The BAR player-facing order inventory, by class
=================================================

This is the parity inventory: player-facing order descriptions, not every
internal engine command ID. BAR's own gui_ordermenu.lua hides LOAD_ONTO,
SELFD, GATHERWAIT, SQUADWAIT, DEATHWAIT, TIMEWAIT, AUTOREPAIRLEVEL, raw move
(39812), and set-unit-target-no-ground (34922) from the order menu, so those
are hotkey-or-internal in BAR too.

4. Defects found and fixed
==========================

D1. Fourteen contract tests were never invoked.
    src/game/sim-wasm/init.ts registered 81 boot contract tests; 14 more
    existed on disk and ran nowhere, including the three that guard this
    exact surface: SelectionPanelCommandSurface, ServerCommandAuthorizer,
    and InputSelectedCommands. All 14 are wired in now, and a script check
    confirms no exported run*ContractTest is left unregistered.

D2. The WORLD group's TERRAIN and LIQUID toggles did nothing.
    Gameplay-setting commands carry no per-entity ownership, so
    authorizeGameServerGameplayCommand deliberately falls through to
    `default: return null` for them, which makes GameServer.receiveCommand's
    host-only server-control switch their only route on the authoritative
    architecture. setTerrainSurfaceMode and setLiquidSurfaceMode were the
    only two members of LOCKSTEP_GAMEPLAY_SETTING_COMMAND_TYPES missing from
    that switch, so both were dropped for every non-host-admin authority --
    which includes ordinary local play. Fixed, plus a contract assertion
    that the switch covers the whole set so the two registries cannot drift.

D3. Three buildings owned a live mechanic with no command.
    ON/OFF was gated on BAR's onoffable unitDef flag. That flag is a strict
    subset of our active-state mechanic: armwin has no onoffable and
    armrad/armsonar set it false, yet buildingWind, buildingRadar, and
    buildingSonar all carry the authoritative production + 0.1x-damage
    fortify tradeoff here. Under the default bar-grid preset the player
    could not reach it. Now capability-gated per the philosophy's building
    panel vocabulary ("ON/OFF toggle (buildings with an active-state
    capability)"), and the BAR-narrowed path is deleted.
    This is a deliberate divergence from BAR's unitDefs, chosen because the
    local system is real and the philosophy names wind turbines explicitly.

D4. The command-execution gate was dead from its Attack case onward.
    runCommandExecutionContractTest threw at the Attack live-center
    assertion, so roughly its last third -- capture, resurrect, transport,
    formation, scheduled settings -- had not run. Three fixture faults, all
    of which no-op silently rather than failing loudly:
      - updateUnits skips body-less entities, so any case driving unit
        actions through Simulation.update needs real physics bodies;
      - a bare Simulation resolves the commander win condition on tick one
        and zeroes every entity belonging to a commander-less side, so the
        capture target was dead before capture could accrue;
      - a bare WorldState has no generated heightmap, so the terrain module
        answers WATER_LEVEL everywhere and a land-only waypoint filter
        refuses every point.
    The whole file passes now, including the Attack live-center refresh.

D5. Two stale assertions were masking working behavior.
    The factory quota-bypass check still regexed `event.altKey` after the
    handler moved to factoryProductionClickModeFromEvent; it now asserts
    Alt-bypasses/Meta-does-not at the helper itself. The entity-slab build
    progress check still expected the averaged fill fraction after
    getBuildFraction became coupled (min across resource lanes, commit
    592ea19e), and the EntityCacheManager unit stub predated
    locomotion.motionControl and crashed the whole test.


5. Every exposed command is certified to execute
================================================

Exposure is not function: a button can be exposed and still do nothing
because the sanitizer drops the payload, the authorizer refuses it, or the
executor no-ops on that host kind. commandCoverageContractTest.ts closes that
gap. For every one of the 39 unit and building blueprints it builds a live
scenario (physics bodies attached, a living commander per side so the win
condition does not wipe the enemy on tick one) and drives every command the
host exposes through the real path --

  sanitizeCommand -> authorizeGameServerGameplayCommand -> executeCommand

-- then requires an observable change in the same authoritative field the
renderer and the snapshot read. It runs the inverse direction too: a host
that lacks a capability must NOT have the command take effect, so a gate that
silently stops gating fails here rather than appearing as a new button.

1030 host/command pairs are exercised. Three things it caught while being
written, none of which the exposure matrix could have shown:

  - Manual Launch is gated differently per preset, and IS working on every
    armed host (see D-c). The earlier claim that it was dead was wrong.
  - Trajectory is likewise a union: BAR presets gate on the armart analogue,
    prototype presets on any ballistic arc weapon, and the sim accepts the
    broader set.
  - Air-only and ground-only weapon categories are enforced at the
    authorizer, so a fighter ordered onto a ground target is correctly
    refused -- the probe has to pick a target its host may legally engage.

A dozen more command/host pairs pass only because the scenario is built
correctly; the helper comments record each trap.


6. Deliberate differences from BAR, with reasons
================================================

D-a. No Restore. Terrain is immutable here -- there is no terrain
     deformation system anywhere in src -- so per "Commands require real
     systems" the BAR grid's M binding stays unbound rather than promising
     it. Verified: `combat.restore` resolves to an empty binding list in all
     three presets and has no panel button, so the dormant
     toggleRestoreAreaMode handler is unreachable rather than dead UI. This
     is the philosophy's own worked example of the rule.

D-b. No Stockpile. Verified from data, not assumed: no mapped BAR analogue
     sets stockpile=true, and the only "stockpile" in this repo is the
     economy resource store (NetworkServerSnapshotEconomy.stockpile), not a
     per-weapon charge count. There is no weapon-stockpile system to command.

D-c. Manual Launch is reachable, but only under prototype presets. BAR
     presets gate the button on canmanualfire, and no mapped analogue sets
     it (armcom's is surfaced as D-Gun), so BAR presets hide it. Prototype
     presets gate it on Set Target instead, which is also the executor's own
     gate (hasManualLaunchWeapon === entityHasBarSetTargetCommand), so every
     armed host can force a volley at a clicked point and the coverage
     certification exercises it on all of them. An earlier draft of this
     document called it dead everywhere; that was wrong, and the certification
     in section 4 is what caught it.

D-d. No sell, unit sharing, or blueprint place/create. These are BAR gadget
     commands with no local economy or system behind them.

D-e. Factory Stop is named "Clear Queue". BAR's armap sets neither
     removestop nor removewait, so BAR shows CMD.STOP and its custom
     stopproduction separately. We expose stopproduction (queue + quotas)
     and Wait, which covers the same authoritative behaviour; a second
     button doing the same thing would be the panel creep the philosophy
     retires. Difference is in the label, not in what the player can do.

D-f. ON/OFF is broader than BAR (see D3), and the converter keeps it even
     though armmakr has no onoffable.

D-g. Commander Resurrect exists in the sim (entityCanIssueResurrectCommand
     accepts any commander) and is offered under prototype presets, but BAR
     presets hide it because armcom has no canresurrect. The wreck
     resurrection system behind it is real -- the coverage certification
     drives the command on the Commander and observes the queued action -- so
     this is an abstraction above BAR rather than dead UI.

D-h. Under prototype presets only, a separate Attack Ground button is shown
     for every armed host; air-only weapons (unitEagle, towerAntiAir) then
     have the command filtered at input, authorization, and execution. BAR
     presets hide the button entirely and use BAR's unit-or-map Attack, so
     the BAR-faithful path has no dead affordance. The certification asserts
     the filtering: entityCanBarAttackGround gates the probe, and an air-only
     host that received the order would fail the absence direction.


7. How to run the gate
======================

  npm run contract:tests                       whole suite, boot order
  node scripts/contractTestHarness.mjs --only=Command    substring filter

`?contractTests=1` is not a usable gate on its own: init.ts awaits each test
in sequence, so the first one that hangs or rejects silently suppresses every
later one and the page still looks clean. That is how fourteen registered
tests came to run nowhere. The harness boots the app normally and then invokes
each test individually with its own timeout, so nothing can mask anything else.

Several sim contract tests share module-level singletons (the entity slot
registry, the spatial grid, the terrain module) and are therefore
order-dependent -- runEntitySlotRegistryContractTest passes in boot order and
fails in a filtered subset. Run the whole suite before believing a result.


8. Suite status
===============

96/96, stable across three consecutive full runs.

Getting there closed six real defects outside the command surface, all found
by running the tests that had never been run:

  - THREE.Material.copy() does not carry onBeforeCompile, so the per-object
    fade path cloned the base, composed with the prototype no-op, and dropped
    every earlier shader patch. Any entity on that path rendered untextured
    for its whole nanoframe build-in and death fade.
  - cachedShieldUnits was built inside a loop gated on isAttackEmitterConfig,
    which correctly rejects persistent sphere barriers -- and so dropped every
    sphere host out of the shield render list. Their fields never drew.
  - Hot-motion typed rows write only a server target; only the lockstep branch
    of applyPrediction materialized them, so on the authoritative-snapshot path
    a moving unit sat at its last full-row pose with a stale render row.
  - Travelling shots had the same hole: motion updates wrote a target nothing
    consumed, so a shot stayed frozen at its spawn point while the render index
    culled it against a stale position.
  - runCanonicalCheckpointContractTest tore down the shared terrain mesh and
    never put it back, which poisoned every later terrain-dependent test.
  - The tightest demo preset fit all 26 production lines for eight of nine
    seats and came up one short on the ninth; the factory placement search ring
    went 48 -> 64 cells.

The rest were fixtures that had drifted from deliberate content changes -- the
Commander LOD kit shedding parts per rung, the Sea Turtle's authored seabed
standoff lift, the submarine depth trim, coupled build progress, the widened
surface-probe lattice, unitRex missing from the locomotion policy table, roof
probes spaced wider than the building they stood on -- plus one environmental
case: runDeterministicLockstepBackendContractTest needs a free sim slot, so it
runs against contractTestHost.html rather than sharing a page with the lobby's
background battle.

Two traps worth remembering, both of which cost real time here:

  - A "solid" support-surface sample is NOT dry ground. Sampled groundZ clamps
    to the liquid surface where the bed sits under it, so a bed at -400 still
    reports solid while the sampler answers -120.
  - An installed authoritative tile map OUTRANKS the terrain generation config.
    Setting a known config while a battle mesh is installed changes nothing.
