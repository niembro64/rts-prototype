PERFORMANCE CADENCE AUDIT 02
============================

Date: 2026-08-23
Scope: production simulation, Rust/WASM kernels, snapshot publication, client
presentation, renderer preparation, effects, HUD/UI polling, and recurring
preview loops. Tests and one-shot boot/content-generation work were inspected
only where they explained a production path.

This is a static audit, not a measured flame-chart ranking. "Impact" is the
expected scaling risk from call frequency, algorithmic shape, data crossings,
and the project's 5,000-unit target. Confirm priorities with the existing
sim-only, sim+snapshot, and full-stack performance harnesses before and after
each change.


RUBRIC TAKEN FROM budget_design_philosophy.html
-----------------------------------------------

The relevant rules are unusually clear:

* The authoritative simulation is fixed-step, 20 Hz by default, while every
  display frame merely interpolates two adjacent post-tick Rust/WASM poses
  (budget_design_philosophy.html:179-181, 873-880).
* Root pose and turret pose must be captured after every fixed tick. Rich
  snapshots are independent of simulation/display cadence and carry lifecycle,
  visibility, fog, economy, minimap, sparse events, beam topology, and recovery
  state (lines 456-477, 856-866). src/architecture.json:2-16 sets 20 Hz fixed
  simulation and 5 Hz nominal presentation snapshots.
* Visibility must be aggregate, indexed, and cached at a deliberate cadence;
  expensive acquisition is only for turrets needing work (lines 830-853).
* Expensive intercept prediction is deliberately 10 Hz for missiles and 5 Hz
  for light rockets, staggered by projectile ID; only cached-point steering,
  integration, collision, arming, and lifetime remain fixed-tick (lines
  1017-1024).
* Pathfinding is already a retained, resumable, deterministic budget: one ally
  team per fixed tick and at most 4,096 closed A* nodes (lines 1380-1400).
* Full-world scans are acceptable for boot/debug/full recovery snapshots, not
  normal gameplay ticks. Hot paths should use packed numeric data, dirty sets,
  spatial indices, area-of-interest bounds, and WASM batches. Design assumes
  5,000 units (lines 1577-1600, 5131-5136).

Recommended cadence vocabulary used below:

* EVENT/DIRTY: execute only after a lifecycle, command, configuration, source
  movement, ownership, visibility, or camera-bucket version changes.
* 20 Hz ACTIVE: keep exact fixed-tick work, but only for the compact set whose
  state can change this tick.
* 10 Hz / 5 Hz STAGGERED: deterministic lower-rate service, distributed by a
  stable entity ID so all work does not land on one tick.
* 1 Hz SCRUB: defensive invariant checking, not the primary state transition
  mechanism.
* DISPLAY: only interpolation, camera motion, shader clocks/uniforms, and the
  smallest position/anchor updates that genuinely need display continuity.


EXECUTIVE PRIORITY ORDER
------------------------

P0 -- Remove first / highest confidence

1. Delete the zombie travelling-projectile motion-delta producer.
2. Stop rebuilding sight/radar boundaries and WorldShade coverage every
   display frame.
3. Stop full 20 Hz restamps of unit spatial rows and combat targeting state;
   update moved/dirty/active rows.
4. Stop reconstructing the complete builder/work graph multiple times per
   fixed tick.
5. Split render-scope/LOD/membership discovery from display-rate pose
   interpolation.
6. Remove the duplicate pre-combat projectile broadphase restamp.
7. Stop rebuilding the locomotion support index every display frame.

P1 -- Large scaling wins after the P0s

8. Put stable shields, host attachments, building active states, factories,
   transport state, and articulation into active/transition sets.
9. Replace action-queue sweeps, gather-group rebuilds, patrol searches, and
   game-over polling with mutation/event indexes plus slow safety scrubs.
10. Aggregate economy producer membership per player instead of repacking
    every producer every tick.
11. Cache static/render topology and throttle environment LOD, shield packets,
    contact membership, minimap entity data, HUD membership, and CPU effects.
12. Limit finite-pose, terrain-normal, and hazard scans to moved/eligible rows.


DETAILED FINDINGS
=================


P0-01. Zombie travelling-projectile motion events cause work every fixed tick
----------------------------------------------------------------------------

Current:

* SimulationCombatController.ts:282-310 walks every travelling projectile
  after combat, copies pose/velocity/rotation fields into event objects, and
  inserts every one into projectileMotionUpdates on every 20 Hz tick.
* SimulationEventQueues.ts:51-75 later materializes IDs, conditionally sorts,
  copies Map entries to an array, and clears it. Lines 78-83 classify the mere
  presence of these motion rows as pending presentation work.
* GameServer.ts:364-374 schedules a sparse projectile snapshot between rich
  5 Hz snapshots whenever that predicate is true.
* ServerSnapshotPublisher.ts:1152-1155 explicitly says adjacent Rust poses own
  ordinary motion, then drains the legacy motion rows WITHOUT serializing them.
  With no real lifecycle/audio/beam data it returns at lines 1157-1163.

Why this is too frequent:

The complete per-projectile producer, Map traffic, task/timer scheduling, drain,
and possible sort are dead work at 20 Hz. This is exactly the "removed system
still touches pooled fields" zombie-write class warned about in the philosophy.

Change:

Delete steady-state projectileMotionUpdates generation and remove it from
hasPendingProjectilePresentationEvents(). Keep spawn, despawn, one-shot audio,
and genuinely dirty beam topology as sparse events. Rich snapshots remain the
recovery path; adjacent Rust/WASM pose rows remain the travelling-shot motion
path. This should be deletion, not a lower rate.

Also verify:

When a live line projectile exists, the false motion predicate currently makes
emitProjectileDelta continue into per-recipient visibility and beam work. After
removal, beam topology needs its own dirty/version trigger (see P0-02).


P0-02. Every sparse projectile delta fully reserializes all live beam topology
-----------------------------------------------------------------------------

Current:

ServerSnapshotPublisher.ts:1137-1218 emits a projectile delta if presentation
events OR any line projectile exists. stateSerializerProjectiles.ts:1498-1528
then walks every line projectile, applies visibility, allocates/fills a pooled
beam update, and copies every path point. The P0-01 false trigger can pull this
work up to 20 Hz between rich snapshots.

Why this is too frequent:

Variable-length topology is sparse state, not a root-motion stream. A beam's
unchanged reflector chain should not be rebuilt for every recipient just
because its endpoints move or because some unrelated travelling shot exists.

Change:

Give line topology a monotonic version/dirty set. Publish only beams whose
point chain, obstruction state, reflector identity, visibility admission, or
lifecycle changed. Derive moving source/target endpoints from interpolated host
and projectile pose where possible. Coalesce remaining topology publication to
5-10 Hz; rich 5 Hz snapshots provide recovery.


P0-03. Projectile spatial/hot-state rows are restamped twice per fixed tick
---------------------------------------------------------------------------

Current:

* Simulation.ts:667-713 calls spatialGrid.updateProjectiles() before combat.
* SimulationCombatController.ts:228-248 integrates projectiles and calls the
  same full-list method again before collision.
* SpatialGrid.ts:220-285 walks all travelling projectiles, fills many TS typed
  arrays, binds slots, crosses into the spatial API, and separately writes the
  entity-state hot batch (position, velocity, HP, flags, owner, type, radii).

Why this is too frequent:

The post-combat stamp from tick N is already the correct pre-combat state at
tick N+1. Spawn/despawn paths individually register/unregister rows. The first
full stamp repeats unchanged work; only the post-integration position is needed
for this tick's collision broadphase.

Change:

Remove the pre-combat projectile full restamp. Keep one post-integration batch,
or better, update only moved/new rows and remove dead rows individually. Verify
submunition and reflection ordering with collision contract tests.


P0-04. Unit update performs full-world spatial sync and orchestration at 20 Hz
----------------------------------------------------------------------------

Current:

Simulation.ts:1925-1934 gets all units and spatialGrid.updateUnitSpatial()s
every one before planning. It then walks all units again at lines 1935 onward,
sets default drive inputs, clears combat priority state, scans action queues,
and conditionally queues active planning. Idle, sleeping, dead, transported,
and incomplete units still pay portions of these passes. A separate full-world
gather scan occurs just before them (P1-08).

Why this is too frequent:

At the 5,000-unit target, even an army that is mostly idle still incurs two TS
object walks and a cross-layer spatial/state write for every unit every 50 ms.
Physics already knows which body slots were awake/stepped, and commands/lifecycle
already know whose actions changed.

Change:

Maintain deterministic compact sets for:

* moved/awake/physics-dirty spatial rows;
* units with non-empty actions;
* cruise-without-command units;
* carried/constructing/dead units whose state just transitioned;
* units needing a one-tick zero-drive or combat-mode clear.

Run exact movement and steering at 20 Hz for those active sets. Update unit
spatial rows from the physics stepped-slot list plus explicit teleports/spawns,
not all units. Use a 1 Hz staggered invariant scrub to catch membership bugs in
development builds.


P0-05. The combat targeting bridge rebuilds every target and turret row at 20 Hz
-------------------------------------------------------------------------------

Current:

SimulationCombatController.ts:101-115 calls stampCombatTargetingPool() every
fixed tick even though the downstream targeting FSM has a scheduled acquisition
model. targetingInputStamping.ts:1287-1339:

* beginStamp() invalidates all alive/turret counts;
* walks every combat-target entity, including unarmed buildings and shots;
* restamps entity dynamic data plus turret configuration/mount fields;
* rebuilds observation masks for every sensor source;
* re-adds all scan circles.

The individual turret stamp above those lines also recomputes many blueprint-
static fields (ranges, include masks, type codes, launch constants, mount data).

Why this is too frequent:

Scheduled acquisition saves probe work but not its upstream full-world object
walk, TS-to-WASM writes, static config restamp, or visibility-mask rebuild.
This conflicts directly with "aggregate/indexed visibility" and "expensive
acquisition only for turrets that need work."

Change:

Split the slab into:

* immutable/lifecycle data: write once on spawn/config/mount change;
* dynamic pose/HP/medium data: share or copy only moved/dirty entity slots;
* turret FSM/servo state: only active or changed turret rows;
* observation masks: rebuild on sensor-source movement cell, power/toggle,
  cloak/detector, scan, ownership/team, terrain-occlusion, or lifecycle version.

Keep the acquisition scheduler and fixed-tick firing semantics. Mobile source
coverage can be 5-10 Hz staggered if its cache is conservative between samples;
static coverage should be event-driven.


P0-06. Sight and radar boundaries rebuild O(S^2) unions every display frame
----------------------------------------------------------------------------

Current:

RtsScene3DRenderPhase.ts:497-508 calls both boundary renderers on every display
frame. SightBoundaryRenderer3D.ts:168-192 rebuilds both target-medium unions.
Lines 200-265 repeatedly scan allied unit/building turret sensors (the radar
renderer also collects sight sources). For every surviving source, lines
282-390 compare it with every other circle and insertion-sort covered angular
intervals. Lines 392-427 resample terrain along every visible arc and repush all
line segments.

Why this is too frequent:

This is O(S^2), plus sorting, trigonometry, terrain queries, and GPU-buffer
rewrites at 60-144 Hz while the authoritative sensor facts normally change at
20 Hz or less. Camera smoothing alone makes the exact scope change every frame,
so simple equality gates will not help.

Change:

Cache union geometry by (vision-team mask, sensor-source version, scan version,
terrain version, mode, target medium). Recompute on source/lifecycle/toggle
changes or at 2-5 Hz for moving sources. Apply camera clipping in the shader or
update a generously padded camera bucket at at most 10 Hz. Retain the previous
vertex buffer between updates. Share collected sensor rows between the sight
and radar products.


P0-07. WorldShade rebuilds sensor/shadow coverage and renders a texture at display rate
--------------------------------------------------------------------------------------

Current:

RtsScene3DRenderPhase.ts:609-619 calls terrainTileRenderer.update() every frame.
TerrainTileRenderer3D.ts:2928-2935 calls WorldShade.update(); under the normal
graphics tier effectFrameStride is 1 (RtsScene3DRenderBudget.ts:36-43).
WorldShade3D.ts:438-470 then:

* resizes/checks a supersampled drawing-buffer-sized render target;
* rebuilds visible bounds;
* scans allied units/buildings and every mounted sensor source
  (WorldShade3D.ts:660-761);
* appends entity-shadow regions;
* uploads all regions;
* renders the off-screen coverage pass.

Why this is too frequent:

Fog/sensor truth comes from snapshots and fixed ticks, not display frames.
Changing coverage bounds on every smoothly moving camera frame forces the full
CPU collection and GPU coverage draw even when all world inputs are unchanged.

Change:

Separate fog/contact coverage from entity shadows. Cache sensor regions by
snapshot/source version and update 5-10 Hz or on dirty input. Use padded,
quantized coverage bounds so the texture survives small camera motion, and
remap/sample within those retained bounds. Update moving-unit shadow positions
at 10-20 Hz if needed; static-building shadows only on scope/lifecycle/config
changes. Keep shade uniforms and final scene sampling at display rate.


P0-08. Render membership, scope queries, and LOD discovery are rebuilt every display frame
-----------------------------------------------------------------------------------------

Current:

RtsScene3DRenderPhase.ts:452-465 recomputes scope and projectile query lists,
then lines 529-538 call prepareRenderEntityPackets3D every display frame.
ClientViewState.ts:399-547 resets every packet and packet-flag slab, spatially
collects scoped entities, cone-culls them, recomputes LOD, walks every visible
unit/building, and separately builds HUD, shield, shadow, name, and ground-print
rows. Even buildings with static transforms are repushed at lines 486-507.
ClientViewState.ts:559-571 also re-marks prediction/dirty/lifecycle flags from
sets every frame, then clears them after render.

Why this is too frequent:

Only interpolated pose and a small number of screen anchors need display-rate
updates. Membership changes at lifecycle/fixed-tick boundaries or when the
camera crosses a meaningful culling/LOD boundary. Rebuilding all topology at
display rate multiplies CPU work and buffer traffic by 3-7x over the 20 Hz sim,
and by 12-29x over rich snapshots.

Change:

Split render preparation into retained topology and dynamic pose:

* scope membership: update at 10-20 Hz or when camera crosses a padded spatial
  cell/bucket; use hysteresis;
* LOD rung: update 5-10 Hz or on threshold crossing, not continuously;
* building/static metadata: event/dirty-driven;
* lifecycle and visibility membership: snapshot/version-driven;
* unit/projectile/turret root pose: interpolate the retained dense rows every
  display frame in WASM/GPU;
* HUD/effects membership: maintain separate lower-rate lists (P1-27).


P0-09. The renderer rebuilds the complete locomotion support index every display frame
------------------------------------------------------------------------------------

Current:

Render3DEntities.ts:546-550 calls refreshLocomotionSupportSurfaces() every
display frame. LocomotionTerrainSampler.ts:50-56 directly calls
SupportSurfaceIndex.rebuild(). supportSurfaceIndex.ts:63-85 visits every support
entity, updates proxies/buckets, then scans all retained proxies again for stale
rows.

Why this is too frequent:

Most support surfaces are static buildings. Mobile support hosts only acquire a
new authoritative pose at 20 Hz; locomotion visual feet can still interpolate
against retained support data without rebuilding static buckets at display Hz.

Change:

Build static building proxies once and mutate them on lifecycle/terrain change.
Update mobile support proxies from the adjacent-tick pose update at 20 Hz (or
only when crossing an index cell). Do not do a stale-proxy sweep every display
frame; remove by lifecycle ID. If visual support must move smoothly, interpolate
the selected support's pose after indexed lookup rather than rebuilding the
whole index.


P0-10. Builder/work relationships are rediscovered several times in one tick
----------------------------------------------------------------------------

Current:

The same builder population and action queues are independently walked by:

* energyDistribution.ts:531-875: rebuilds all consumer maps/sets, scans health-
  bar buildings for candidate nanoframes, and walks all builders at least three
  times (base construction/auto-assist, direct repair, guard repair, plus a
  fourth pass when damaged units exist). Some builders perform a nested scan of
  candidate nanoframes or damaged units.
* commanderAbilities.ts:128-203: walks all builders again to rediscover active
  reclaim/guard/build/capture/resurrect work and recompute work emitters.
* workStationSystem.ts:398-499: walks all builders again to resolve work intent
  and pack every articulated station, including idle/restored stations.
* constructionLifecycle.ts:423-449: walks all builders and every queued action
  again merely to rebuild active/queued construction attendance.

Why this is too frequent:

Commands, action-queue mutations, guard-target changes, damage/lifecycle events,
and range-cell movement already identify when relationships can change. The
current design reconstructs a graph of (builder, mode, target, source rate)
from scratch multiple times every 50 ms.

Change:

Create one persistent deterministic work graph/reverse index maintained by
queue/lifecycle/ownership/guard changes. Separate:

* assignment/discovery (idle auto-assist, nearest repair, guard service): 2-5
  Hz staggered and immediately on relevant event;
* active work advancement/resource transfer: exact 20 Hz for only active edges;
* articulation: exact 20 Hz only while working or returning to rest;
* construction attendance: direct counts/sets updated with queue mutations and
  landed-work events, not a full queue scan.

This is likely one of the largest 5,000-unit simulation wins after targeting.


P0-11. Projectile lifecycle churn updates many irrelevant sorted caches immediately
--------------------------------------------------------------------------------

Current:

Every projectile spawn/despawn calls WorldState.addEntity/removeEntity
(WorldState.ts:729-753, 772-800). EntityCacheManager incrementally inserts by
linear splice and removes with Array.indexOf()+splice. Removal
(EntityCacheManager.ts:374-410) probes roughly every category list and every
per-player list even though a shot belongs to only a few. Helpers at lines
617-630 make each affected sorted-array mutation O(N) shifts.

Why this is too frequent:

Projectile churn can occur many times inside one fixed tick. Maintaining global
sorted object arrays transaction-by-transaction pays repeated shifts and scans
before any consumer observes the intermediate cache state.

Change:

Use kind/membership bits to touch only lists the entity actually joined. Batch
spawn/despawn cache maintenance once at the end of the combat phase. Prefer
dense slot lists plus tombstones/swap removal for unordered consumers; produce
a stable-ID ordered view only for deterministic consumers, once per tick and
only when membership changed.


P1-01. Stable shield equipment is fully stepped every fixed tick
----------------------------------------------------------------

Current:

SimulationCombatController.ts:146-160 calls updateShieldState and then restamps
all shield surfaces every tick. shieldTurret.ts:78-180 walks every shield host
and turret, tests power, increments onTimeMs, advances transition, resolves
mount kinematics/trigonometry, and rebuilds active field poses even for stable
fully raised/lowered static hosts. targetingInputStamping.ts:1370-1495 then
rewrites all field rows and all panel geometry/config rows to WASM.

Change:

Keep a 20 Hz active-transition set and a moved-mobile-shield set. Static stable
fields/panels persist in the WASM pool until lifecycle, power, toggle, ownership,
mount/config, or terrain-support changes. Store immutable panel geometry once;
update only its host pose. Derive visual elapsed time from a start tick instead
of incrementing onTimeMs on every stable host if that field has no gameplay use.


P1-02. Authoritative host attachment kinematics walks all armed hosts three times per tick
----------------------------------------------------------------------------------------

Current:

SimulationCombatController.ts:93-99 and 128-135 runs tickStart and postAim over
all armed hosts. workStationSystem.ts:444-454 runs the hostAim phase over all
armed hosts between them. combatUtils.ts:1169-1245 loops every eligible host and
every attached turret, resolving transforms, normals, orientations, velocities,
and targeting-slab mount writes.

Change:

Maintain an attached-host set (not all armed hosts), then an active subset:
moving hosts, active/settling servos, changed support normals, working builders,
and firing/acquiring mounts. Cache static idle sockets. Run postAim only for
hosts whose owner/child pose changed during this tick. Preserve the required
phase ordering for those active rows.


P1-03. Turret snapshot dirtiness is sampled at 20 Hz although snapshots are 5 Hz
-------------------------------------------------------------------------------

Current:

SimulationCombatController.ts:196-203 walks every armed host after firing.
turretSnapshotDirty.ts:71-99 writes and compares 12 quantized fields for every
turret, including a Rust targeting FSM read, every fixed tick.

Change:

Either mark turret rows dirty directly when the FSM/servo/shield/host-piece state
changes and coalesce until publication, or sample signatures only when a rich
snapshot is due. If visibility/lifecycle sparse deltas need turret state sooner,
sample only active servo/transition hosts. Idle static turrets need no 20 Hz
comparison.


P1-04. Laser and shield audio scan their complete equipment subsets every tick
-----------------------------------------------------------------------------

Current:

SimulationCombatController.ts:118-121 and 162-170 calls both audio state
systems every tick. laserSoundSystem.ts:76-142 checks every beam turret and beam
index. shieldSoundSystem.ts:41-87 checks every shield field/turret. They emit
state transitions plus a two-second active refresh, but still rediscover state
at 20 Hz.

Change:

Emit start/stop directly from beam spawn/despawn/orphan/death and shield
transition/power/death events. Keep active sound IDs for the two-second refresh,
and process only that set when its next refresh tick is due. No full equipment
scan is needed between transitions.


P1-05. Stable producer-building active states are repacked through WASM every tick
--------------------------------------------------------------------------------

Current:

Simulation.ts:547-553 calls updateBuildingActiveStates every tick.
buildingActiveState.ts:273-335 packs every active-state building into typed
arrays, calls a WASM batch, and writes every timer back, even though most
producers are stably open or closed with no active damage/reopen timer.

Change:

Use a deterministic tick wheel/min-heap for damage-grace and reopen deadlines.
Maintain a small transitioning set. Apply producer-rate deltas on discrete
open/close/power/lifecycle events. Stable buildings should do no work; due
transitions remain exact to the fixed tick.


P1-06. AI and factory production poll every factory every fixed tick
-------------------------------------------------------------------

Current:

* Simulation.ts:601-609 calls AI selection and production every tick.
* aiProduction.ts:60-70 creates a new Set for the factory/global roster
  intersection; lines 99-126 do it for every AI factory even when producing.
* factoryProduction.ts:206 onward rebuilds a combined factory list and packs
  state for all active factories. Idle/paused factories still pay discovery and
  branching; only a producing shell actually needs continuous progress/hold
  updates.

Change:

Cache each factory's validated roster intersection. Run AI choice immediately
when a factory becomes idle/completes, a quota/cap/toggle changes, or at a 1-2
Hz staggered fallback. Maintain a 20 Hz active-producing set for shell funding,
hold pose, and completion; process idle/paused factories only on events.


P1-07. Transport logic and collision exemptions poll all transports every tick
-----------------------------------------------------------------------------

Current:

transports.ts:356-400 walks every transport-capable unit for action tests and
beam updates. ServerSimulationCore.ts:140-145 separately calls
collectBeamCarriedEntityIds(), which clears a Set and walks every transport and
all cargo (transports.ts:190-201) before every physics step.

Change:

Maintain active load/unload/beam transports and a persistent carried-ID set.
Update membership on load, unload, cargo release, death, and transport
lifecycle. Exact beam spring work remains 20 Hz only for carrying transports;
collision exemptions should not be rediscovered from all transports.


P1-08. Gather-wait groups are rebuilt from every unit/action queue every tick
----------------------------------------------------------------------------

Current:

Simulation.ts:1717-1763 clears maps/lists, scans every live unit, scans each
unit's whole action queue to find a gather wait, constructs owner:group string
keys, sorts groups, checks all members, and releases ready heads. It is called
at the start of every updateUnits pass (Simulation.ts:1889-1895).

Change:

Maintain group membership when a wait is inserted/removed, an action queue is
replaced/spliced, ownership changes, or an entity dies. Maintain ready/member
counts and enqueue only groups whose head status changed. A 1 Hz debug scrub can
reconstruct and compare the index.


P1-09. Invalid target actions are checked across every active unit's full queue every tick
----------------------------------------------------------------------------------------

Current:

Simulation.ts:1997-2012 calls sweepInvalidTargetActions while walking units.
SimulationActionQueueMaintenance.ts:26-46 checks every queued action and may
splice intent groups. Most target invalidation comes from discrete death,
completion, reclaim, capture, ownership, or command events.

Change:

Maintain a reverse index from target ID to queued action intents. Invalidate
subscribers when the target's relevant state changes. At 20 Hz, validate only
the active head fields that can become invalid through continuous range/state;
run a 1 Hz staggered full-queue defensive scrub.


P1-10. Reachable service-action promotion rescans builder queues every tick
-------------------------------------------------------------------------

Current:

Simulation.ts:2026 calls promoteReachableBuildAction for every active unit.
SimulationActionQueueMaintenance.ts:49-82 linearly scans queued actions and
does range/target lookup until it finds a service action.

Change:

Cache the first candidate service-intent index and invalidate it on queue
mutation. Recheck range only when the builder or target moved enough/crossed a
spatial cell, or at 5-10 Hz staggered. Trigger immediately after a command or
target lifecycle change.


P1-11. Patrolling builders search for reclaim targets every fixed tick
---------------------------------------------------------------------

Current:

Simulation.ts:2028-2054 calls findPatrolReclaimTarget on every eligible patrol
tick. Simulation.ts:1566-1631 performs an enemy spatial query, candidate range
tests, a vegetation spatial query, and vegetation candidate tests.

Change:

Run acquisition at 2-5 Hz staggered, immediately on entering patrol and when a
chosen target disappears. Cache a null/result until the builder moves a useful
distance or the entity/vegetation spatial version changes. Once selected,
ordinary approach/work stays at 20 Hz.


P1-12. Construction attendance rescans every builder's entire queue every tick
----------------------------------------------------------------------------

Current:

constructionLifecycle.ts:423-449 clears three sets, drains work movements, then
walks all builders and every queued action to reconstruct active and queued
build-site attendance before visiting incomplete shells.

Change:

Maintain active/queued build-site reference counts inside the canonical action
queue mutation helpers. Landed work is already an event list. Update attendance
on insert/splice/shift/clear/death/ownership rather than reconstructing it. Only
incomplete/decaying shells need 20 Hz lifecycle advancement.


P1-13. Game-over resolution polls commander/team state every fixed tick
-----------------------------------------------------------------------

Current:

Simulation.ts:686-687 calls checkGameOver every tick.
SimulationGameOver.ts:4-49 repeatedly scans the commander list per player, then
again to select a stable winner, with alliance lookups.

Change:

Evaluate victory on commander death/removal, resign/seat/team roster changes,
and battle start. Keep a 1 Hz defensive check if desired. This state cannot
change between those events.


P1-14. Self-destruct and scan-pulse expiration use full-list polling
--------------------------------------------------------------------

Current:

* Simulation.ts:1826-1850 iterates every armed self-destruct entry every tick
  to find due timers or dead entities.
* WorldState.ts:1329-1343 filters the complete scan-pulse array every tick.

Change:

Index both by due tick using deterministic tick buckets/min-heaps; process only
the current bucket. Cancel/remove by ID on commands or lifecycle events. These
sets are probably small today, so impact is lower, but the correct structure is
also simpler at scale.


P1-15. Invalid-pose safety validation scans every unit after every physics step
-----------------------------------------------------------------------------

Current:

ServerSimulationCore.ts:147 calls repairInvalidEntityPoses(); lines 481-496
walk every unit and validate both body kinematics and entity pose. The comment
at lines 131-135 explicitly confirms it sweeps ALL units every tick.

Change:

Validate physics stepped/moved slots and other pose-writer dirty rows, because
unchanged rows cannot become non-finite spontaneously. Keep a staggered 1 Hz
full-world audit in development/diagnostic mode. In production, fail/repair at
the writer boundary and retain telemetry counters so corruption is visible.


P1-16. Ground-normal EMA samples every occupied dynamic sphere, including sleepers
--------------------------------------------------------------------------------

Current:

Simulation.ts:559-565 invokes updateUnitGroundNormal every tick.
unitGroundNormal.ts:65-83 calls Rust over the body pool.
rts-sim-wasm/src/body_pool.rs:1086-1133 loops every occupied non-static sphere
up to next_unused_slot, samples terrain, blends/normalizes, and dirty-compares;
there is no awake/moved/converging gate.

Change:

Maintain an active normal set: moved/teleported bodies plus EMA rows not yet
within epsilon of the raw terrain normal. Remove a row when converged and
sleeping; wake it on motion, terrain-version change, or support transition.
Keep the EMA's exact 20 Hz math for active rows.


P1-17. Water damage walks the entire entity-state capacity every fixed tick
-------------------------------------------------------------------------

Current:

UnitForceSystem.ts:364-387 always calls unitWaterDamageStepPool.
rts-sim-wasm/src/unit_kinetics.rs:160-212 loops entity_state.len(), filters to
live unit bodies, computes immersion fractions, reads profile rates, and records
damage. Water-safe profiles with a zero damage rate are still visited.

Change:

At minimum maintain a compact set of unit slots whose blueprint has nonzero
water damage. Better, maintain an unsafe-and-submerged/crossing set from body
motion and the water plane. Apply exact 20 Hz damage to that compact set. If
gameplay accepts coarser damage/death timing, accumulate deterministic 5-10 Hz
damage, but that is a gameplay-semantic decision and needs explicit tests.


P1-18. Lava damage scans all units and buildings every fixed tick
---------------------------------------------------------------

Current:

Simulation.ts:541-545 calls applyLavaSurfaceDamage. When lava is enabled,
lavaSurfaceDamage.ts:13-42 walks every unit and every building and tests height.

Keep a compact below-lava hazard set updated by body-plane crossings and static
building lifecycle. Apply 20 Hz damage only to that set. A deterministic 5 Hz
accumulated-damage option is possible, but it changes death timing and must be a

P1-19. Economy producer membership is repacked every tick instead of aggregated
-------------------------------------------------------------------------------

Current:

economy.ts:300-440 walks every solar, wind, and extractor building each tick,
packs one credit row per active producer, calls WASM, and then emits per-row
movement accounting. processConverters at lines 524-625 likewise packs every

Integrate one aggregate row per player per fixed tick. For wind, cache active
turbine counts and multiply by the current scalar wind rate; no per-turbine scan
is necessary. Aggregate identical converters per player where per-entity
movement visuals do not require individual accounting; emit per-source detail
only for dirty/visible diagnostics.


P1-20. Wind production rate metadata is recomputed at full sim cadence

P1-21. Active physics-force slot membership is rebuilt and sorted every tick
-------------------------------------------------------------------------

Current:

UnitForceSystem.ts:836-896 merges moving, cruising, force-accumulator, and awake

Maintain a persistent deterministic active-slot set with membership updates on

P1-22. Articulated work stations step all articulated builders, even at rest
----------------------------------------------------------------------------

Current:

workStationSystem.ts:398-545 clears/rebuilds arrays, scans all builder units,
resolves targets/aim points, packs every articulated station into the motor

Change:

Track working stations, stations waiting for restoreDeadlineTick, and stations

P1-23. Selection replacement/clear refreshes every renderable entity
-------------------------------------------------------------------

Current:

ClientViewState.ts:1466-1469 setSelectedIds() calls

P1-24. Static environment prop culling/LOD repacks instance matrices during camera motion

matrices. Repack/upload only props whose scope, LOD, asset, or reclaimed state

P1-25. Shield render packets and instance buffers are rebuilt every display frame
-------------------------------------------------------------------------------

Current:

ClientViewState.ts:1095-1142 scans every shield host when packet preparation
runs. RtsScene3DRenderPhase.ts:768-779 processes the complete packet every
display frame. ShieldRenderer3D.ts:795-855 clears cursors/seen keys, processes
every row, flushes every pool, and prunes fields. The lattice spin is a shared
time value, but CPU instance transforms/colors are still rewritten.

Change:

Retain field instances by stable key. Update topology/material/power/visibility
on snapshot/dirty events, static hosts only on those events, and moving hosts at

display-rate shader time uniform for lattice motion. Do not rebuild all field
membership merely to advance visual spin.


P1-26. Contact input is reprocessed every display frame although samples arrive at snapshot rate
----------------------------------------------------------------------------------------------

Current:

RtsScene3DRenderPhase.ts:512-517 calls ContactBlipRenderer3D every frame.
ContactBlipRenderer3D.ts:140-199 loops the entire minimap contact input to
advance/mark tracks, then loops all tracks again to fade, scope-test, repush,

Change:

On a new contact sequence, update membership/endpoints and mark unheard tracks.
Between sequences, interpolate/fade retained tracks without rescanning the
unchanged input array. Move fade/interpolation to GPU attributes + a time/alpha
uniform if track count is large; otherwise only the retained visible track loop
needs display cadence.


P1-27. HUD/shadow/ground-print membership is mixed with display-rate anchors
--------------------------------------------------------------------------

Current:

prepareRenderEntityPackets3D rebuilds body HUD/name/shield/shadow/ground-print

Split membership/value data from position anchors:

* health/name membership and text: snapshot/HP/selection/hover/toggle dirty;
* label strings/owner names: cache until metadata changes;
* unit anchor positions: display-rate interpolation only for retained rows;
* building shadows: lifecycle/scope dirty;
* unit shadows: 10-20 Hz or GPU position feed;
* ground-print terrain/grounded sampling: 5-10 Hz staggered or on movement cell/
  ground-contact change;
* waypoint geometry: selection/action/terrain/toggle dirty, with only any
  necessary moving root anchor updated at display rate.

QUALIFIED CADENCE CHANGES (REQUIRE GAMEPLAY APPROVAL)
====================================================

The following can be made less frequent, but unlike the findings above they can
change authoritative timing unless implemented as active-set/event work:

1. Water/lava damage at 5-10 Hz with accumulated dt changes the tick on which HP
   reaches zero. Prefer compact hazard sets at 20 Hz if death ordering matters.
2. Wind production-rate sampling at 5 Hz changes the exact integral unless the
   interval integrates the wind function analytically or gameplay accepts
   sample-and-hold. Per-player aggregation at 20 Hz is safe.
3. Mobile sensor coverage at 5 Hz can delay acquisition/visibility. Use
   conservative broadphase caches, stable ID staggering, and preserve exact
   checks for shortlisted combat candidates if immediate detection matters.
4. CPU shadow/effect updates below display rate are presentation-only and safe
   for simulation, but must be visually tested during fast camera/unit motion.


WORK THAT SHOULD NOT BE THROTTLED
=================================

Do not "optimize" these by simply lowering cadence; they match the design:

* ServerSimulationCore.ts:155-159 presentation.captureTick after every fixed
  tick. The philosophy explicitly requires adjacent final poses for every live
  body. Optimize its dense row layout/copy count if profiling demands it, but
  retain the 20 Hz capture.
* Display-rate sampling/interpolation of visible root position, orientation,
  velocity, support normal, and turret pose. Membership and metadata can be
  slower; the actual retained pose sampling must stay display-continuous.
* Physics integration, projectile integration/collision/arming/lifetime,
  active turret servo/firing gates, cached-intercept steering, and active force
  application at the fixed simulation tick.
* The existing missile 10 Hz and light-rocket 5 Hz expensive intercept refresh,
  including stable-ID staggering.
* The retained pathfinding budget/continuations. Do not replace the deterministic
  node budget with frame-time bursts or a wall-clock budget.
* SimulationIdleBuilderAutoRepair's top-level 1 Hz gate
  (SimulationIdleBuilderAutoRepair.ts:34-42) is already deliberately low-rate;
  improve its internal indexes if profiling shows need, not its cadence.
* Dynamic pixel-ratio adjustment already has a 750 ms gate
  (ThreeApp.ts:539-550), and GPU timer queries already sample every fourth frame
  (GpuTimerQuery.ts:41-43, 56-89).


IMPLEMENTATION ORDER AND VERIFICATION
=====================================

Recommended sequence:

1. Delete P0-01, add beam topology dirtiness for P0-02, and remove the duplicate
   projectile restamp P0-03. These are narrow and high-confidence.
2. Add counters to prove call volume: rows stamped, cache mutations, entity/
   turret/sensor/builder rows visited, region uploads, support proxies rebuilt,
   render packet rows, and bytes uploaded per second.
3. Introduce active/dirty sets for unit spatial sync (P0-04), targeting (P0-05),
   and builder work (P0-10) one system at a time. Add 1 Hz debug reconstructions
   that assert the incremental index equals the old full scan during migration.
4. Retain renderer topology and lower coverage/boundary/membership cadences
   (P0-06 through P0-09). Use padded camera buckets and hysteresis to prevent
   edge popping.
5. Convert the remaining P1 simulation sweeps to event/active sets, then the P1
   presentation/UI work. Finish with the small P2 loops.

For every authoritative change, compare peers/checksums over recorded command
streams and vary simulation tick rate. For rendering, test 60/120/144 Hz,
continuous camera pan/zoom, 5,000 units, many sensors/shields/projectiles,
visibility changes, pause, capture mode, and dropped rich snapshots. Measure:

* sim-only tick work average/high percentile and 20 Hz headroom;
* sim+snapshot materialization, visibility, encode/apply, sparse delta rate;
* render preparation versus renderer/GPU time;
* per-frame buffer uploads and off-screen WorldShade pass cost;
* long tasks, allocations/GC, and total auxiliary WebGL contexts.

The core design goal is not simply "lower Hz." It is: continuous visual pose at
display rate, exact active gameplay at fixed-tick rate, and everything else
event-driven or deliberately staggered at the lowest cadence its semantics
actually require.
