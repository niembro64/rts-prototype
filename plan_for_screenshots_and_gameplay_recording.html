Plan: Picture Screenshots & Video Recording

A four-button capture grid beside the fullscreen toggle: record video or take a snapshot, each with the HUD or as a clean world-only view. Fidelity is uncapped: video records every rendered frame at the canvas’s native backing-store resolution — fullscreen on a 1080p/60 monitor yields 1080p60, a 4K/120 setup yields 4K120. This document is the plan and the as-built record; the design constraints come from budget_design_philosophy.html. Implemented on branch worktree-gameplay-capture (Tauri native save still pending).

What We Are Building

A 2×2 button grid rendered next to the existing fullscreen button in the top-right of the game area. Rows are the media kind, columns are the HUD treatment:

VID HUD VID RAW PIC HUD PIC RAW
capture grid · fullscreen →
⛶
  • VID HUD — record video of exactly what the player sees: world plus every overlay.
  • VID RAW — record video of the world only. All HUD is hidden for the duration of the recording.
  • PIC HUD — one PNG of exactly what the player sees.
  • PIC RAW — one PNG of the world only. HUD is hidden for the one or two frames the capture needs.

VID buttons toggle: first click starts, second click stops and saves. PIC buttons are one-shot. Output goes through the existing object-URL download idiom (budget-annihilation-<ISO>.png / .webm), with a native save dialog on Tauri as a later phase.

What Counts As HUD

The stated rule — HUD is everything other than what the game camera sees — maps onto two distinct layers in this codebase, and a RAW capture must strip both, because several HUD instruments are technically drawn by the game camera inside the WebGL canvas. The philosophy already names this taxonomy: “overlay rings, build squares, selection volumes, and HUD geometry are instruments, not terrain” (budget_design_philosophy.html §Nothing In The World Has A Clean Edge, ~line 4018). Instruments are HUD regardless of which renderer draws them.

Contact blips and the fog terrain shade are world, not HUD: they are the player’s sensor truth, and a cinematic clip that suddenly reveals unseen enemies would misrepresent the battle. RAW means “no instruments,” not “no fog.”

Current State (What The Code Already Has)

  • Fullscreen button: GameCanvas.vue:2666-2677, absolutely positioned child of .game-area at top:12px; right:48px (gameCanvas.css:123-163), shown when gameplayHudVisible. Fullscreen is document.documentElement.requestFullscreen() (GameCanvas.vue:607-623), so DOM HUD remains visible in fullscreen — good: with-HUD capture has something to capture.
  • Renderer: one WebGLRenderer in ThreeApp.ts:172-182 with preserveDrawingBuffer: false (line 179), single renderer.render() at line 451, no post-processing composer, rAF loop at 426-465 with an onFrameComplete hook already wired through createGame.ts:61-70.
  • Resolution is not stable: canvas tracks the container via a ResizeObserver (ThreeApp.ts:311-319) and a dynamic pixel-ratio governor retunes DPR by ±0.25 every 750 ms on browser-desktop (ThreeApp.ts:467-497). Left alone, a recording would change resolution mid-clip.
  • The existing screenshot is unreliable: captureScreenshot() (GameCanvas.vue:625-642, the SHOT button and F12) calls canvas.toBlob() outside the render tick against a non-preserved drawing buffer — on most browsers that reads a cleared buffer. It gets replaced, not patched (§Delete The Old Path).
  • No capture machinery exists: no MediaRecorder, captureStream, or getDisplayMedia anywhere in src/. The one working capture precedent is the entity preview thumbnails (loadingUnitPreviewScene.ts), which use a dedicated preserveDrawingBuffer: true renderer.
  • Tauri has no fs/dialog plugins (src-tauri/Cargo.toml:20-23); its CSP already allows blob: for media and workers.

What The Philosophy Demands

  • This is a sanctioned “mode-specific tool”. The PIP ban (§Minimap camera and PIP, ~1826) forbids a second always-live viewport but explicitly blesses mode-specific capture/replay surfaces. Nothing here renders a second view: both lanes capture the one existing render.
  • The capture path never touches the sim. It is pure client presentation, downstream of the renderer. It never asks the sim for more data and never becomes a second cadence owner — requestAnimationFrame samples, capture samples the sample.
  • No per-frame JS pixel loops (§What TS must never own). Video encoding stays inside the browser engine via canvas.captureStream() + MediaRecorder; TypeScript only starts, stops, and collects blobs. We do not read pixels back per frame, and we do not bundle a JS/WASM video encoder.
  • Browser APIs are wrapped at one seam (§Explicit Absence, ~4646). MediaRecorder / captureStream / getDisplayMedia live behind a CaptureSource boundary; the domain side is strict T | null.
  • Availability is reported honestly (matchmaking-backend precedent). A lane that cannot work in this runtime says so up front — its buttons disable with a reason — rather than failing at click time. No silent fallback to a different lane.
  • The lifecycle is a declared FSM (§Lifecycles are explicit finite state machines) built on src/game/state/StateMachine.ts, one writer, undeclared transitions refused.
  • Knobs are data (§Config Is Data, Not Code). Resolution, frame rate, bitrate, codec preference order, and the four mode definitions are authored in a schema-validated captureConfig.json; defaults live in the schema. The four modes are enumerated config entries (camera-model precedent), not if (noHud) branches in a component.
  • HUD hiding is one level-triggered gate, like the LOD gate: a single flag every HUD consumer reads each frame, not a pile of imperative show/hide calls that can miss teardown.

Architecture

Two capture lanes behind one seam

The two HUD treatments need different pixel sources, because the composited page (WebGL canvas + minimap 2D canvas + compass canvas + Vue DOM) exists nowhere we can read it except the browser’s own compositor:

LaneSourceServesHow
Canvas lane (RAW) The main WebGL canvas, post-render PIC RAW, VID RAW PIC: canvas.toBlob() invoked from a post-render hook inside the rAF tick (drawing buffer still valid; preserveDrawingBuffer stays false). VID: canvas.captureStream() with no rate argument — one captured frame per canvas repaint, uncapped — into MediaRecorder. Works in every runtime including Tauri. No permission prompt, pixel-exact.
Display lane (HUD) The browser compositor via getDisplayMedia PIC HUD, VID HUD getDisplayMedia({ video: { frameRate: { ideal: 240 } }, preferCurrentTab: true }) — a deliberately high ideal so the browser clamps to whatever the compositor actually produces — cropped to .game-area with Region Capture (CropTarget.fromElement) where supported. VID: pipe the stream into MediaRecorder. PIC: draw one frame to a scratch canvas, toBlob(), stop tracks. One permission prompt per session (browser-imposed; unavoidable).

Both lanes implement one CaptureSource interface: availability() (supported / unsupported-with-reason), still(), startVideo() / stopVideo(). That interface is the third-party boundary; everything behind it is strict domain code. We deliberately do not build a DOM-rasterizing compositor (SVG foreignObject tricks or an html2canvas-class library) as a HUD-lane fallback: it would be a second implementation of the same truth, it cannot reach 60 Hz, and the library route is banned outright.

The capture lifecycle is an FSM

One CaptureController owns one machine built on src/game/state/StateMachine.ts. One recording at a time; a PIC request during a VID is legal only through a declared transition (it is refused in v1 — simplest correct table).

StateMeaningLegal exits
idleNothing in flightrequestStill → arming-still; requestVideo → arming-video
arming-stillGate + fidelity hold applied (RAW), waiting for the clean frame; or display frame-grab in flight (HUD)finish → idle (saved); fail → idle (restore)
arming-videoGate + fidelity hold applied; stream and recorder being created (display lane: the user permission prompt lives here)started → recording; fail → idle (restore)
recordingMediaRecorder running; elapsed time ticking on the grid cellrequestStop → finalizing; recorder error (fail) → finalizing (salvage chunks)
finalizingRecorder flushing; blob assembled and saved; gate and hold already released on this edgefinish/fail → idle

Every path into finalizing or idle runs the same restore side effects on the transition (§side effects on the transition, not in callers): release the instrument gate, release the fidelity hold, resume the DPR governor, stop stray tracks. A mid-recording fullscreen exit, tab switch, revoked display track, or component teardown lands in a declared transition, never a leaked recorder.

One instrument gate, level-triggered

A single flag in src/game/capture/captureInstrumentGate.ts, owned by the controller, read fresh every frame by RtsScene3DRenderPhase. It suppresses the in-canvas instruments only:

  • All ground overlay lines in one move: every line/ring shares the one OverlayLineSystem material, so setSuppressed() on that material hides selection rings, range rings, drag boxes, build squares, waypoint lines, and debug boundaries at a single choke point.
  • Sprite-pool instruments: the gate forces the body-HUD/name flags off and runs one empty drawEntityHud begin/end pass so health bars and labels left by the last instrumented frame hide rather than linger; waypoint flags and lift probes get an empty-selection update the same way.
  • DOM needs no gating at all — the canvas lane never sees it. That is an improvement discovered in implementation: the chrome (including the capture grid with its red stop cell) stays visible and clickable during a RAW recording while the recorded pixels stay world-only. Contact blips and the fog shade also stay, in the world and in the clip: sensor truth is world, not instrumentation.

PIC RAW therefore costs one to two frames of in-canvas instrument blink on screen (hidden frame is rendered, captured, gate released). VID RAW holds the gate for the whole recording: the player plays without in-canvas instruments while filming, which is the stated trade — but keeps the DOM HUD (top bar, minimap, panels) on screen the whole time.

Fidelity contract: uncapped, pinned against drift

  • No resolution cap: capture reads the canvas at its native backing-store size. A 2×-DPR fullscreen canvas records 4K because that is what is rendered; bitrate scales with area (below) so it is not starved.
  • No frame-rate cap: captureStream() takes no rate argument and captures one frame per canvas repaint; a 120 Hz display records 120 fps. Browsers encode variable-frame-rate WebM — a dropped render frame becomes a held frame with a truthful timestamp, never a desync or a speed change.
  • Fidelity hold, not a size pin: while a capture is live, ThreeApp.setCaptureFidelityHold(true) suspends the dynamic pixel-ratio governor and raises DPR to the profile maximum — so a recording neither drifts in resolution mid-clip when the governor would have stepped, nor sits at a degraded rung the governor picked earlier. The governor resumes when the capture ends.
  • Coverage/fog render target: viewport-derived as before; the hold changes the physical viewport exactly like a window resize does, so no special-casing.

Encoding and output

  • Codec selection walks an authored preference list through MediaRecorder.isTypeSupported: video/webm;codecs=vp9 → video/webm;codecs=vp8 → video/webm → video/mp4 (Safari/WKWebView). The chosen container decides the file extension.
  • Bitrate scales with the capture: with resolution and frame rate uncapped, a constant would starve 4K clips, so the config authors bits-per-pixel-per-frame (0.1) × live width × height × a 60 fps reference, clamped to authored floor/ceiling (8–85 Mbps). 1080p lands ~12 Mbps, 4K ~50 Mbps.
  • Stills are PNG via toBlob('image/png').
  • Memory: recorder chunks (ondataavailable every ~1 s) accumulate in an array and become one Blob on stop. At 16 Mbps that is ~2 MB/s — minutes of recording are fine; a config maxDurationSeconds (default 600) auto-stops rather than letting the tab eat RAM unbounded.
  • Saving: browser — the existing object-URL <a download> idiom (downloadReplay() precedent), filenames budget-annihilation-<mode>-<ISO>.<ext>. Tauri — Phase F adds tauri-plugin-dialog + tauri-plugin-fs for a native save dialog, selected via the existing isTauriRuntime() check.

Config: src/captureConfig.json + schema

Following §Schema is the contract: one schema next to the data, defaults in the schema, loader validates at startup. Authored knobs: outputHeight, frameRateHz, videoBitsPerSecond, codecPreference[], stillFormat, maxDurationSeconds, filenamePrefix, and the four mode entries as data — { id, media: "video" | "still", source: "canvas" | "display", hud: boolean, label, hotkey }. The controller iterates modes; nothing in the UI or controller hardcodes the four combinations.

Performance Rules For This Feature

  • Zero cost while idle: no stream, no recorder, no extra render target, no per-frame branch beyond the two existing gate evaluations.
  • While recording, the only added main-thread work is the compositor copy captureStream performs; encoding runs in the browser’s media pipeline. No readPixels, no per-frame JS access to pixel data, no per-frame allocations (chunk array reuse; one Blob at stop).
  • The capture path never changes sim cadence, snapshot cadence, or LOD rungs. If recording drops display frames, the recording drops the same frames the player lost — capture must not trigger quality reductions or private detail paths.
  • Measured, not assumed: run npm run performance:bottleneck at --width=1920 --height=1080 with a recording active and compare against the baseline before calling VID done (§Bottlenecks are measured by layer, which already documents the 1080p harness invocation).

Implementation Phases (As Built)

Phases A–E are implemented on worktree-gameplay-capture; npx tsc --noEmit and vue-tsc pass clean. Phase F remains open.

Phase A — Plumbing and contract ✅

  • src/captureConfig.json + src/captureConfig.ts: startup-validated loader that throws on any malformed knob or mode entry; the four modes are enumerated data.
  • src/game/capture/CaptureController.ts: the FSM on StateMachine.ts (idle / arming-still / arming-video / recording / finalizing), restore side effects on every edge into finalizing/idle.
  • ThreeApp.ts: requestCapturePostRender() drained immediately after the draw and before adjustPixelRatio (a DPR resize would clear the buffer), plus setCaptureFidelityHold() — DPR raised to the profile max and the governor suspended while held.
  • The instrument gate (captureInstrumentGate.ts) wired into RtsScene3DRenderPhase; OverlayLineSystem.setSuppressed() hides every shared-material ground line in one call. DOM gating turned out to be unnecessary (canvas lane never captures DOM) and was deliberately not built.

Phase B — PIC RAW (replaces the broken screenshot) ✅

  • Arm → gate + fidelity hold → next frame renders clean → same-task post-render toBlob → restore via the FSM edge → download.
  • SHOT buttons, the control-bar model contract, and F12/Meta+8 all reroute into the controller; the old direct-toBlob body (blank-frame bug) is deleted.

Phase C — VID RAW ✅

  • canvas.captureStream() (uncapped), codec preference walk, area-scaled bitrate, chunked recording, auto-stop at maxVideoDurationSeconds, recorder errors salvage through finalizing.
  • Gate and fidelity hold span the recording and release through the FSM exit edges.
  • Open verification: run npm run performance:bottleneck with a recording active and compare against baseline (needs a browser session).

Phase D — Display lane (PIC HUD, VID HUD) ✅

  • displayCapture.ts behind the one seam: getDisplayMedia + preferCurrentTab/selfBrowserSurface + Region-Capture crop to .game-area where available; honest availability probe drives disabled-with-reason cells.
  • PIC HUD: one frame to a 2D scratch canvas, tracks stopped immediately. VID HUD: recorder on the display stream; the browser’s own “Stop sharing” control finalizes and saves like an ordinary stop.

Phase E — The grid ✅

  • CaptureControlGrid.vue beside the fullscreen toggle (top:12; right:92), red pulsing elapsed-time stop cell, disabled states; four hotkey commands (ui.captureScreenshot = PIC RAW keeps F12, the other three ship unbound); CaptureControllerContractTest.ts registered in the boot contract suite.

Phase F — Tauri native save (open)

  • tauri-plugin-dialog + tauri-plugin-fs (Cargo, npm, capability entries); save path selected by isTauriRuntime(); browser download idiom otherwise.

Accepted Trade-offs & Risks

  • Permission prompt on the display lane, once per session — browser-imposed, no way around it without leaving the platform.
  • Instrument blink (~1–2 frames) on PIC RAW; in-canvas instruments gone while filming on VID RAW (the DOM HUD stays on screen and out of the clip) — both within what the brief accepted.
  • The red recording cell appears inside VID HUD footage — it is HUD, and with-HUD capture is defined as what the player sees.
  • Variable frame rate WebM: browsers timestamp real composites, so heavy scenes produce held frames rather than a fixed-cadence stream. Correct for gameplay capture; anyone needing constant-frame-rate can transcode offline.
  • Mid-recording resize: entering/leaving fullscreen mid-recording changes the canvas size, and the recording follows it (Chromium encodes the resolution change into the WebM; some players handle mid-stream resolution shifts poorly). Uncapped fidelity means the clip tracks the canvas rather than freezing a stale size.
  • Safari/Tauri lack the HUD lane — reported honestly, revisitable via a native capture source behind the same seam.
