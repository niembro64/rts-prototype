Design Philosophy: Shared Simulation, Explicit Authority, Full Physics

This prototype is a browser RTS inspired by the command scale and battlefield clarity of Beyond All Reason, but its technical identity is stricter: every meaningful physical interaction should reduce to mass, force, acceleration, velocity, position, collision, and correction.

Authority is explicit Budget Annihilation uses deterministic-lockstep as its single backend architecture, configured through architecture.json. The command-frame stream is authoritative while every browser runs the same server simulation locally.
Clients stay continuous The local fixed-step simulation (20 Hz by default, match-configurable) retains two adjacent authoritative poses in Rust/WASM, and the renderer samples between them on every display frame with one shared interpolation clock.
Physics is the language Movement, recoil, collision, hover, beams, blast pressure, and terrain contact are force and mass problems before they are gameplay effects.

Design Inheritance

Budget Annihilation, the rts-prototype repo, is our browser-native extension of Beyond All Reason. This document describes the places where the prototype deliberately differs: deterministic-lockstep networking, adjacent-tick presentation, force-and-mass physical systems, browser constraints, owned simulation code, and the atomic gameplay pieces this project adds or reshapes.

When this document does not describe a gameplay or player-facing behavior, the default is Beyond All Reason as implemented in the Beyond-All-Reason repo. That fallback covers command ergonomics, battlefield expectations, economy feel, construction and production behavior, unit control language, selection behavior, minimap/radar/sight expectations, and any other ordinary RTS behavior this document leaves unstated.

  • Rules written in this document override the BAR fallback.
  • Intentional departures from BAR should be written into this document.
  • BAR is the behavioral fallback, not a requirement to copy BAR code, Lua structure, assets, Recoil/Spring engine internals, or network assumptions.
  • When BAR behavior depends on Recoil/Spring details, translate the player-facing behavior into Budget Annihilation's browser, physics-first deterministic-lockstep architecture. architecture.json owns the lockstep cadence and support policy.

North Star

Budget Annihilation's implemented backend architecture is deterministic-lockstep, configured through architecture.json. Every browser runs the same server simulation locally and peers exchange ordered command frames; snapshots are local presentation data instead of multiplayer truth. We are still not building a thin renderer that waits for a host to stream every position at display rate.

The local server simulation owns the real world in every browser: commands, ownership, economy, construction, targeting, damage, projectile hits, physics bodies, collision response, fog of war, victory, and persistent state. The client presentation layer owns local command feedback, smoothing, camera-visible presentation, audio scheduling, and render-time interpolation. The ordered command-frame stream owns multiplayer truth.

That split is architectural, not permission for accidental duplicate game loops. A browser runtime may own only one active gameplay-truth simulation at a time. Booting a second sim in the same browser is a hard error, whether it comes from a duplicate worker, a second game session, or a stale teardown path. Throw immediately rather than letting two tick loops share input, networking, render state, or authority.

The preferred implementation is shared code inside one deterministic architecture. Physical kernels and battlefield contracts should be described once and reused by the local server simulation and the client presentation/prediction layer where that reuse buys correctness: body integration, forces, projectile motion, terrain sampling, turret pose, hover, and collision math. That does not create duplicate gameplay implementations. Economy, construction truth, target ownership, fog filtering, damage resolution, entity creation and removal, and victory run in every browser as the local copy of the same server simulation.

The target networking feel is: commands are assigned to deterministic future frames, and every browser advances the same local server simulation from the same ordered stream. Command frames and checksums are the network truth; local snapshots are for rendering and diagnostics.

Engine Ownership: In-House Simulation, Practical Renderer

The end-state engine is something we own end-to-end. The simulation is Rust compiled to WebAssembly, living in rts-sim-wasm/. The renderer may be built on Three.js, raw WebGL2, or raw WebGPU where each makes sense, but the high-count paths must still be ours: owned typed buffers, explicit update ranges, deliberate shader code, predictable batching, and measured draw-call behavior. Networking glue, input plumbing, asset pipeline, audio mixer, math kernels, ECS, physics, collision, pathfinding, fog of war, snapshot serializer, prediction integrator — all written by us, for this game. The defining trait of this project is that we are building the engine, not assembling one.

A major goal of this project is to move as much code as possible, whenever possible, out of JavaScript/TypeScript runtime ownership. If a simulation or data-transform system can reasonably live in Rust/WebAssembly, raw GPU buffers, or shader code, that is where it belongs. JavaScript and TypeScript are coordination layers, not the place we leave game logic, physical kernels, serialization loops, or high-count data transforms once a Rust/WASM or GPU-buffer path is viable.

The libraries currently in package.json (three, vue, peerjs, @msgpack/msgpack, @tonejs/midi, @tauri-apps/*) are tools with different budgets, not all equal sins. Three.js is acceptable as the active renderer shell while it lets us ship faster without hiding the high-count data flow. Vue remains UI-only. Networking, audio, and desktop wrappers are allowed where they are boundary glue. The Rust sim crate, owned GPU/shader data paths, and a thin TypeScript orchestration shell are the destination. Every dependency still needs a reason, and every hot path still needs an owned, inspectable contract.

  • The default answer to “should we add a library for this?” is no. Write it ourselves, preferably in Rust, ideally in the sim crate.
  • The default answer to “can we keep this library?” is only if it preserves ownership of the hot path. Three.js may stay when it is a renderer shell over our buffers, shaders, culling, and batching; it should not become an excuse for per-object scene-graph work at battlefield scale.
  • Adding a new npm or cargo dependency requires a deliberate, named justification — not a reflex. Vendoring the few lines we actually need is almost always preferable to taking a whole library on.
  • Libraries that have already been removed (Phaser, Pixi, Matter.js, standalone matter-js) are gone for good. Do not reintroduce them under any architectural argument. They were tried and failed our scaling rules.
  • “In-house” means the behavior, data layout, and performance contract are in our repo, in code we are willing to debug at any layer. A Three.js draw wrapper can still be in-house when the buffers, shaders, update ranges, and culling policy are ours.
  • Whenever a Rust/WASM implementation can replace JavaScript or TypeScript functionality, the Rust/WASM version is the active target and the JS/TS version becomes removal work, not a fallback architecture.
  • The Rust sim crate is the preferred home for new logic. New TypeScript modules are acceptable for orchestration, but new simulation, physics, math, or per-unit-loop code should land in rts-sim-wasm/ from the start, not get written in TS and ported later.

This is the active commitment behind Languages and Frameworks, TypeScript Coordinates, WASM Computes, and Delete The Old Path. Those sections describe what the end-state engine looks like and how migrations land; this section states why we are doing it: nobody else’s engine is going to give us thousands of physically-simulated units in a browser by accident. A library is acceptable only when it helps us reach that target while leaving the hot data flow legible and under our control.

Home, Game Room, Two Side Rooms — One Declared Map

The app’s high-level navigation is itself a lifecycle, so it follows the same rule as every other lifecycle here: it is a declared finite state machine, not a scatter of refs that happen to agree. The map follows the shape Beyond All Reason players already know — a home screen with the sandbox behind the menus, a battle room you enter to play with people, and the battle itself with an explicit loading phase. The machine that owns which surface is current lives in src/appSurfaceMachine.ts. App.vue renders the state and holds no navigation logic of its own; the components that own the gestures send the events, and an event the table does not declare is refused.

init is boot — modules loading, the sim WASM compiling — and its only edge is into home; nothing ever returns to it. HOME is one surface: the demo battle, the lobby directory, and host/join. Whether the menu sidebar is slid open or away is CHROME, not navigation — either way you are home, watching and tuning the demo. The GAME ROOM is a networked session with declared sub-states: lobby (the seating screen — teams, presets, the host deciding who plays) and battle, which itself passes through loading (handoff received; booting, and for a late joiner replaying the archive) before playing. A solo-hosted real battle enters the battle directly from home — same surface, same lockstep, one seat, no seats to negotiate. ENTITY LAB is the inspection lab and GAME CONTROLS the controls reference; neither has a network or a battle. The StateMachine primitive is flat, so the hierarchy is encoded in the state ids and read through the isGameRoomSurface/isBattleSurface predicates — the declaration is still one table.

The shape of the map is a hub. Home is the only surface connected to everything, because it is the only place every flow can regroup: the side rooms’ doors, hosting and joining into the game room’s seating screen, the solo battle’s direct road. The asymmetries are the point of writing the table down:

  • Neither side room can start a battle or enter a game room. A match needs a host or a room code, and only home has either — the road always runs through home. Their navs deliberately have no such button, and the machine declares no such edge behind one.
  • Nothing leaves the game room except its declared exits home. Leaving has network consequences — a seat resigns, a host ejects everyone — so it is an explicit act on the match’s own exits: the game-over banner, the OPTIONS menu’s LEAVE, host eviction, the seating screen’s cancel. The ~ lab hotkey is refused by the table anywhere in the game room — the seating screen included, where it used to silently disconnect the seat.
  • Loading is a declared battle sub-state, not a boolean beside the machine. The handoff enters it; finishing the boot (or the catch-up replay) is the one edge into playing.
  • Every exit from the game room says the same thing — “Return to Lobby” — and lands home with the menu surfaced, whatever the sidebar preference last was. The destination the player just chose beats a stored default.

Bottom-bar defaults are committed selections

DEFAULTS on an interactive bottom bar means “select every currently authored default,” not “temporarily display the fallback.” Each default follows the same ownership and persistence scope as clicking that option directly. In particular, if an ordinary click writes a browser localStorage key, DEFAULTS must overwrite that same key with the selected default value. It must not remove the key, depend on a missing-key fallback, or reset only the live refs: after a refresh, the stored default must be indistinguishable from a direct click on that option. A reset path may skip an expensive rebuild, restart, command, or broadcast when the live value is already correct, but it may never skip the required persistence write. Status-only readouts, one-shot actions, and settings explicitly owned by the current real-battle session remain outside browser persistence; DEFAULTS preserves those declared scopes rather than inventing new ones.

Network Model

Lifecycles are explicit finite state machines

Anything with a lifecycle — a session, a connection, a countdown, a peer’s health — is modelled as a declared finite state machine, not as a set of booleans that happen to be read together. A pile of flags like isConnecting, gameStarted, alreadyNotified encodes its real states in the combinations of those flags, including every combination nobody intended to allow. The bugs that follow all have the same shape: it fired twice, it ran after teardown, it went back to a state it had already left. Each of those is a transition no one declared and nothing refused.

The machine lives in src/game/state/StateMachine.ts. States and the events that move between them are written down as data; an event that is not legal in the current state is refused and returns false, and a refusal never changes state. That is what lets callers stop latching: “the host left” arriving three different ways, or a countdown expiring after the player already clicked through, are ordinary races that the table answers once instead of every call site answering separately.

  • If a question about a lifecycle is answered by reading two or more booleans together, it wants a state machine.
  • Declare every legal transition. Undeclared is refused — that refusal is the safety property, not an oversight to paper over.
  • Derive conditions from the state rather than storing them alongside it. Late joiners are refused because the session is not in lobby, not because a separate flag says so.
  • Put side effects on the transition, not scattered through the callers that trigger it.
  • One writer per machine. A second path that mutates the same lifecycle is the bug the machine exists to prevent.
  • Hysteresis and “fire once” belong in the table as asymmetric edges, where they can be read, rather than hidden inside a comparison or a guard variable.
  • Keep them flat. Anything wanting hierarchy or parallel regions is better as several machines observing each other.

Matchmaking is behind one backend seam

How players find and reach each other sits behind a capability seam instead of baking directory requests into the lobby. This repo's shipping backend publishes sessions to web_games_backend and connects peers over WebRTC. The shared surface in src/game/network/multiplayer/ is written only in terms of what the game needs (advertise a session, find the open ones, take the advert down), so a future shipping transport can replace that implementation without changing lobby consumers. Do not keep a speculative backend implementation in this repo before its real SDK boundary exists.

  • Session state belongs to the match, not to the matchmaking service. Backends are told the status; they do not model it.
  • Discovery is best-effort by contract: a directory that is unreachable yields an empty list, never an error that blocks joining by code.

Architecture selection is explicit

The active backend is deterministic-lockstep, configured before match startup by src/architecture.json. It runs the same server simulation locally in every browser and makes ordered command frames the multiplayer truth. The architecture is a startup boundary, so changing the config does not hot-flip a running match.

  • deterministic-lockstep: the ordered command-frame stream owns gameplay truth; every peer steps the same local server simulation and compares checksums.
  • Mid-match architecture migration is not supported. Future checkpoint import/export work must preserve one canonical truth or roll back cleanly.

Commands flow upward

A client issues a command and sends it into the lockstep command protocol. Commands are sanitized, assigned future execute frames, ordered canonically, and distributed as reliable command frames. The host may coordinate or relay those frames, but it does not own gameplay truth.

  • Selection can remain local because it is UI state.
  • Move, attack, guard, build, repair, reclaim, scan, production, and server-control commands must be authorized by the host.
  • Command latency should be hidden with local intent previews, not by letting clients create real gameplay state.
  • Every command path should be stable enough to work for local host play, remote WebRTC play, and a future dedicated worker or server.

One command has one implementation. The demo sandbox hands a command straight to the local server; a real battle sends it through the frame scheduler and back as part of a command frame. Those are two transports, and they are allowed to differ. What must never differ is what the command DOES: sanitizing, authorizing, and applying are single functions that both transports call. A second copy of a command's effect on the server side is how a battle setting came to work in the sandbox and quietly do nothing online — the copies agreed on the day they were written and drifted afterwards, with nothing to notice.

  • Sanitizing is shared: the two entry points differ only in which tick the command is stamped with, never in what a payload is allowed to contain.
  • Gameplay settings are simulation state and are applied by the simulation, from the same function, whichever transport delivered them. The lockstep registry of that family is the single list both sides read; a type absent from the applier is dead UI in every battle, and a contract test says so.
  • Only genuinely non-simulation control — pause, game speed, sandbox roster toggles — is handled by the server outside the command stream, because it is not gameplay truth and never crosses the wire as one.
  • Accepted commands are recorded for replay where they ENTER the simulation, so an online match and a sandbox match produce the same replay for the same actions.

Snapshots flow downward

In deterministic lockstep, root motion does not flow through a sparse snapshot correction stream. Every peer already owns the authoritative simulation. Rust/WASM retains the previous and current fixed-tick pose for each stable entity slot, while visibility-filtered snapshots carry lifecycle, fog, metadata, economy, minimap contacts, beam topology, one-shot events, and recovery state.

  • Root position, velocity, full orientation, surface normal, and turret pose are captured after every fixed simulation tick.
  • Snapshot cadence is independent of both simulation and display cadence because snapshots no longer define normal motion smoothness.
  • Lifecycle/recovery snapshots remain full visible-state packets so a renderer can rebuild after loss or startup.
  • Area-of-interest and fog filtering are server responsibilities.
  • Backpressure should drop or coarsen snapshots before it lets the browser build an unbounded send queue.

Lockstep snapshots are presentation-only

Each browser advances the same local simulation and captures render history directly from its canonical Rust/WASM slabs. Snapshots are not gameplay truth and are not the steady-state body-motion transport. Dropping one may delay a lifecycle/fog/UI refresh, but it cannot make an already visible body move less smoothly and must never change canonical simulation state. Command frames and checksums are never coalesced by snapshot backpressure.

  • Every lockstep frame uses the host-selected BATTLE simulation rate carried in the complete lobby contract and hashed initialization: 1000 / simulationTickRateHz ms. The authored default remains architecture.json's 20 Hz.
  • Missing command frames stall instead of causing peers to guess different futures.
  • Checksums are compared by frame. A mismatch pauses/desyncs the match and produces an exportable report with initialization hash, state-hash sections, peer ids, and recent command frames.
  • Lockstep support is still deliberately bounded: real battles only, bots only as deterministic-sim-driven seats (see Agent type and initial state are two seat axes below), no automatic resync, and no host migration. Late join, reconnect and spectators are supported — see Members hold connections; seats hold armies below.

Two state hashes over one truth

There is one canonical serialization of the simulation and two hashes over it. The LIGHT hash is what the living match runs on: five section hashes (world, simulation, economy, commands, entities) over the complete canonical state, with the root composed from them. It covers everything — every entity, every field — because the sections do; what it declines to compute is the per-entity, per-component, per-field diagnostic breakdown, which nothing reads until something has already gone wrong. The FULL hash is the light hash plus that breakdown, computed on demand at the moments that justify its cost: a desync being reported, an initialization mismatch, a diagnostics export.

The split exists because the breakdown was the cost. Producing it meant on the order of a hundred separate stringify-and-hash passes per entity, five-plus complete re-serializations of the entity payload per checksum, and a multi-megabyte checksum message every interval — profiled at ~110 ms per checksum at high entity counts, every nine seconds, on every peer, to compute detail that is only ever read on the desync frame. A light checksum weakens nothing: two peers whose worlds differ in any hashed field still disagree at the section level, which is what stops the match. What the light hash cannot do is name the entity — so a desync immediately escalates, computing a FULL hash of the still-live local state and attaching it to the exportable report, clearly labelled as the state at detection time rather than at the frame that disagreed.

  • LIGHT and FULL agree byte-for-byte on hash and sections, so a full hash can always be compared against a light one. Only the diagnostic payload is mode-dependent, and every reader of it already tolerates absence.
  • The periodic checksum, the late-join verify gate, checkpoints, and the replay harness all run LIGHT. Desync reports, initialization-mismatch broadcasts, and diagnostics exports run FULL. There is no runtime mode toggle — the split is structural, so peers cannot disagree about it.
  • Changing what a hash covers changes its value, and that needs no version dance: one build, everywhere (see “One build, everywhere — no protocol versioning”). The hashed initialization carries the automatic build fingerprint, so a mixed-build pairing is refused at match start rather than surfacing as a phantom desync minutes in.

Agent type and initial state are two seat axes

A seat has two independent properties, and conflating them is how the demo battle stayed a special case for so long. The AGENT TYPE says who drives the seat once the match runs: a human seat answers to a connection; a bot seat is driven by the deterministic in-simulation policy — idle factories re-picking repeat-build units from the sim’s own RNG stream — with no connection, no commands, and no wire traffic at all. The INITIAL STATE says what the seat starts the match with: a lone commander on its spawn arc, or the authored full base — building arcs, fabricators seeded to repeat-build, auto-extractors on the seat’s deposits, and the opening unit wave. The authored BASE economy includes six solar collectors and four wind turbines per seat; those counts are deliberate opening power capacity, not decorative scatter.

The axes mix freely, and the DEMO battle is the proof rather than the exception: every demo seat opens with a base, and every seat except the local one is a bot — the user’s own demo seat is a human with the bot’s opening. A skirmish can seat a bot that starts from a bare commander, or hand a human the full base. Both axes are gameplay truth — they decide what spawns at frame 0 and who the sim drives — so both are hashed into the canonical match initialization and a peer that disagrees about either is refused before the first frame.

  • Bots are lockstep-legal precisely because they live entirely inside the deterministic simulation. Every peer computes their behaviour identically from the hashed roster; a late joiner replays them for free because they add nothing to the command archive. The old support boundary said “no AI players”; the boundary now is bots: deterministic-sim-only — a bot that needed wall clocks or its own network presence would be refused.
  • A bot is a SEAT, not a member. It occupies a seat number, a side, a terrain slice, and a share of the entity cap like anybody; what it lacks is a connection, so it appears in no completion set, no ack or checksum comparison, no ready gate, and no resign path. The frame-completion universe is HUMAN seats — a match of only bots is refused, since nobody would complete a frame.
  • Deposit ownership is decided over the WHOLE roster even when only base seats spawn extractors: a commander-start seat’s deposits stay bare rather than being claimed across the map by the nearest base seat.
  • The host seats and removes bots in the lobby exactly like human seating — one writer, lobby only, announced in the same atomic roster message — and flips any seat’s initial state there too. After frame 0 the roster is hashed and closed, bots included.
  • Session VISIBILITY is the orthogonal third choice, made at hosting time: an online session lists itself in the directory and admits joiners as ever, while a local skirmish opens no signaling peer at all — nothing to dial, nothing to list, nothing that needs the internet. Same seating screen, same lockstep, same bots; the session is simply sealed. The old “offline” path this replaces was dead wiring no button reached, with an AI roster the support policy would have refused.

Members hold connections; seats hold armies

A member is one connection. A seat is a PlayerId in the match. Everyone who joins is a member; only some of them ever hold a seat, and the two id spaces stay apart. That separation is what makes “a spectator can never stall the match” a structural fact rather than a rule somebody has to remember: the frame-completion set is seated players, the frame-delivery set is every member, and a watcher is absent from the first by construction while being in the second, because it cannot simulate without command frames.

A user joins as a watcher and only the HOST moves anybody onto a team. Nobody seats themselves, in the lobby or out of it. One writer for the roster means two clients cannot disagree about it, and it means a running match needs no separate rule to refuse new players: seating is legal in lobby and nowhere else, so joining a battle already under way makes you a watcher without anything having to say no.

  • Roster changes are announced as ONE atomic member list, never as a join/leave/info trio. Merging partial roster deltas in different orders is how two clients came to disagree about where the same player sat.
  • A seat is reserved by identity — an opaque token issued when it is granted — not handed out by a counter. A counter meant lobby churn exhausted a lobby, and made rejoin impossible: a returning player cannot be given back an incrementing number.
  • Sides the host declares and leaves EMPTY survive into the match. An empty side still carves its terrain slice, deposits and spawn arc; it simply has no commander on it. The declared count is authored data and is hashed.
  • A watcher may select and inspect but authors no gameplay truth. That is refused at the command doorway, not downstream: a command that never enters the stream cannot be executed by mistake.
  • A watcher computes local periodic hashes only to verify its own catch-up replay. Those hashes are filed outside the seat range and the watcher’s desync comparison set is empty: it neither sends a checksum nor compares itself with seated players, so a spectator-only divergence cannot halt or accuse the match.
  • Chat is one room in the lobby and splits when the battle starts — allies to allies, watchers to watchers. A watcher sees the whole map, so a live channel from the bench is a coaching channel.
  • Every chat room is a bounded conversation, not a log: clients and the HOME backend retain and display only the newest 10 messages, and every input plus every authority independently enforces a 220-character message ceiling.

The match runs at the speed of its slowest seated player

Two tiers, both driven by the acks the coordinator already tracks, and neither of which a watcher can trigger. Throttling is continuous: the coordinator will not mint a frame more than a window ahead of the slowest seated player, so the match droops to that player instead of leaving them behind. Pausing is discrete, latched and has a named subject: a player who is disconnected or sustainedly far behind stops the match outright, with their name on it. The pause is bounded — a subject that spends the drop timeout making NO PROGRESS is resigned and play continues, because one closed laptop must not end everyone’s evening. Progress defers the clock: a reconnected player replaying a long match back from frame 0 acks continuously and is waited for however long the replay takes, while a dead socket, a killed tab, or a failed replay all go silent and run the clock out.

  • Connection state is SESSION state and never reaches the simulation. A disconnected player’s army keeps its orders; the only thing that removes a player from the match is an explicit, frame-scheduled resign that every peer executes on the same frame.
  • All five thresholds live in architecture.json under lockstep.flowControl. Hysteresis is asymmetric on purpose: leaving a pause needs a clearly good reading, not merely a less bad one.
  • Noticing and acting stay separate. Silence is reported after a few missed beats; a silent peer’s connection is still only closed OUTSIDE a battle, because dropping a peer mid-match would strand the frames others are waiting on.

A late arrival replays the match from frame 0

There is no simulation state serializer, so replay from genesis is not one option among several — it is the mechanism. The coordinator keeps every command frame the match has executed; that archive plus the BattleHandoff is the full history a joiner needs. The handoff it is served is byte-identical to the one the frame-0 peers received, so a late arrival takes the ordinary boot path rather than a separate initialization that could drift from the real one.

The limit that must not be discovered at runtime is the CEILING. Replay speed is bounded by simulation step cost, which grows with live entity count: roughly 18 ms/tick at an entity cap of 1000 against a 50 ms real-time frame at 20 Hz, and about 50 ms at 2500. So a joiner replays at about 2.7× real time in the first case and about 1.0× in the second, and at 1.0× the gap never closes. Catch-up therefore measures its own rate continuously, shows it, and refuses the join with the measured number rather than spinning forever.

  • Only frames that carried commands are archived or sent; the rest are reconstructed from the range. At 20 Hz a twenty-minute match is 24,000 frames and a few thousand commands.
  • History and live frames enter the joiner through the SAME scheduler queue, so catching up is an ordinary bounded advance rather than a second code path, and there is no hole between the archive and the live stream.
  • Arrival is gated on a checksum comparison against the coordinator. A replay that disagrees is a desync, and joining anyway would spread it.
  • The replay runs in the one and only gameplay-truth simulation this runtime owns, time-budgeted on the ordinary animation frame. It does not boot a second sim beside the real one and promote it later.

Fog behavior and fog visuals are separate controls

The DEMO BATTLE and REAL BATTLE bars own whether fog of war is functionally active. That battle-level FOG OF WAR control governs authoritative player vision, radar/sonar coverage, recipient-specific snapshot filtering, and whether enemy units outside vision exist in the client view at all.

The PLAYER CLIENT bar owns only fog presentation. Its DEBUG: controls may show or hide the sight boundary, the live dark shade over currently unseen terrain and environment props. The client may independently tune contact-only and fully unseen darkness, color loss, and world-space boundary softness without changing sensor truth. The complete fog presentation profile — authored defaults, tint, coverage resolution, softness, and user-facing option values — belongs in fogConfig.json. Those controls must not change gameplay truth, server filtering, radar semantics, or what entity data is delivered to the player.

There is no persistent black explored/unexplored shroud. We should not track or render “ever seen” terrain history as a separate black map state unless it is deliberately reintroduced as a gameplay feature with its own design justification. The current visual model for unseen areas is live-only: the optional shade is disabled automatically when battle-level fog is off.

Fog presentation consumes the same mounted sensor sources, source-medium row, target-medium column, allied ownership, completion state, and powered-channel state as authoritative visibility. A completed building keeps its ordinary local sight while fortified or switched off; only powered contact electronics such as radar, sonar, and detection go offline. Therefore an owned completed extractor always clears the terrain shade around its authored sight mount even while its economy production is closed. Entity models are discrete intelligence results rather than fragments of the terrain shade: allied and fully sighted entities draw normally, contact-only enemies are generic contacts on both the minimap and the battlefield, and hidden enemies are absent. The instant an enemy loses full sight its full model is destroyed on the client; model fade-out may never leak identity into a radar-only or unseen interval. Only the anonymous contact dot may retain its short fade.

Friendly jamming is painted on the terrain

Jamming follows the same separate-jammers rule as authoritative contact denial: a jammer protects its owner’s side instead of blanketing every player’s radar. The seated player therefore sees a red terrain tint over the union of every active radar- and sonar-jamming lane owned by that player or an ally. Every unit, building, or future mounted source participates through its exact authored jammer radius and mounted world position; there is no blueprint-name allowlist and no inferred replacement range. Enemy jammer footprints are not revealed. A watcher on ALL has no “our side” and sees no jammer tint; following a seat restores that team’s field.

The tint is presentation of friendly operational state, not another intelligence tier. It changes no contact denial, snapshot filtering, targeting, or sensor truth, and it stays visible independently of the optional fog shade and the battle fog debug setting. Only terrain receives it; entity identity and environment props do not. Construction-incomplete and destroyed hosts contribute nothing. Jamming uses the powered contact-electronics gate, so switching a jammer building OFF removes its tint on the next authoritative coverage update and switching it ON restores the exact same footprint. Passive local sight remaining on an OFF building does not keep its jammer tint.

Jammer coverage reuses the fog renderer’s padded, quantized, viewport-local GPU field. Sight/contact coverage occupies layer 0 and friendly jammer coverage occupies layer 1 of one texture array, keeping terrain inside the 16-fragment-texture WebGL budget while avoiding a mesh or draw call per jammer. One instanced pass per semantic layer composites rings as the same order-independent probabilistic union used by fog coverage: overlaps reinforce smoothly toward full coverage, never cancel, double-count into a harder edge, or grow a seam between emitters. The authored radius is the midpoint of the same smooth edge curve; jammer colour, opacity, and its contact-scale 192-world-unit softness live in fogConfig.json.

Sight, radar, sonar, and contacts are separate information tiers

The visibility model needs three named areas, because each answers a different gameplay question. Area of unit sight is the footprint of one full-vision source: a scout, commander, building mast, temporary scan pulse, or future sensor mount. It is useful for debug, overlays, source authoring, and local reasoning, but it is not the player’s whole knowledge of the map. Area of total player sight is the union of all full-vision sources owned by the player and their allies. It grants full entity identity, private strategic detail allowed by ownership rules (commanded intent only, never motion or render state — see Visible units render and update identically below), normal terrain/force-material sight checks, visual events, and the main snapshot entity row. Area of total player contact coverage is the contact-level aggregate: all total player sight areas plus air-radar and water-sonar sensor areas. Full sight is a stronger information tier, so it necessarily also supplies contact-level location. Contact-only coverage grants positional information only, not full identity, health, orders, animation state, or full snapshot presence.

A contact-only enemy should be represented to the player as a contact, not as the real entity. Its one canonical world/minimap mark is a white core inside a black ring: a generic radar or sonar contact at a quantized or otherwise coarse position, with no unit blueprint, no exact body dimensions, and no private state. The authoritative sim may internally associate that contact with a real entity so projectiles can collide with the real world, but the client should only receive the contact tier it earned. Losing full sight while retaining radar should degrade the player’s information; it should not silently keep streaming a full unit under another visual.

A contact is drawn in the world as well as on the minimap. Beyond All Reason jitters its radar icons by a sine of game time so that contacts read as uncertain; we deliberately do not. A shimmering blip is indistinguishable from a moving one, and a contact that has come to a stop has to read as stopped. Uncertainty is carried by what the blip withholds — no team colour, no body, no identity — and by its reduced alpha, never by moving it away from where the return was actually heard.

Contacts are the one moving visual that cannot ride the client prediction stepper, because there is no blueprint, velocity, or order set to predict from, so they arrive only on presentation snapshots — far slower than the render loop. The world blip therefore interpolates between its last two received positions, the same clamped glide the fixed-tick presentation history gives every other moving visual, and never extrapolates past the newest sample while heard. Once returns stop, only the anonymous dot may coast briefly on its last measured drift while its contact fade expires; a full entity model is never retained for that presentation grace period.

The extension is the medium. A contact carries which sensor lane earned it, and its blip sits at the surface it was heard or seen through — a sonar contact reads as a submerged return and a radar contact as an above-water one, so a player watching a coastline can tell a surfacing hull from a passing aircraft without either becoming a full entity. Both remain ownerless: a blip never carries its team colour, never selects, and never hovers.

Emissions live on the same tiers. A shot, missile, rocket or beam belongs to the side that fired it, so the recipient’s own and allied emissions are always sent and drawn in full wherever they fly — a player watches their own artillery land in the dark. An enemy emission is a point body and earns exactly what an enemy body earns where it is: inside full sight it is the real projectile; inside radar or sonar coverage but outside sight it is the same anonymous contact dot, a white core in a black ring at the point’s own altitude, with no shot blueprint, no owner colour and no trajectory; outside every lane it is nothing. A point occupies exactly one medium, so an emission earns at most one lane, and an enemy jammer covers it the way it covers a body standing there. The dot travels on the minimap contact channel, never the projectile channel, so an emission is either the real projectile or a dot and a client never receives a projectile it has not earned. The one standing exception is the incoming-threat rule: a shot homing on or aimed at the recipient’s own unit is forwarded in full so a hit never arrives from nowhere.

A source and a target answer the medium question differently, and the asymmetry is deliberate.

Every sensor and weapon source is a mounted turret. A sensor classifies from its authoritative AimFrom pivot; a physical shot or ray classifies from its selected QueryWeapon socket. Either source point is strictly IN or OUT of the water: at or below the water level is underwater, above it is above water. A partially wet barrel is not half a sensor and not half a gun. Mount radius, host hull extent, visual height, and wake never soften that classification.

A target is a body, and a body genuinely occupies whatever media its volume crosses. Target medium is therefore volume occupancy, not a center test: a hull straddling the surface is present in both media at once and is legally seen, contacted, and hit from both. A Sea Turtle is not safe from aircraft until it is fully submerged, and a Duck is not safe from torpedoes until it is fully clear of the water. The occupancy fraction is the exact submerged volume of the authored sphere or box, so the transition is continuous rather than a snap at the waterline.

Both full sight and contact sight are authored as a two-by-two matrix from source medium to target medium: above-to-above, above-to-underwater, underwater-to-above, and underwater-to-underwater. Only the row matching the source center is active on a tick. Ordinary entities usually author the two same-medium entries; amphibious entities therefore keep useful local sight when they cross the surface without seeing through it. Specialized observers may deliberately author either cross-medium entry, and an entity that can operate in both media and see both from either may author all four. A temporary scan pulse is an explicit universal override: it contributes full sight to both target media without having an entity center or an active source row.

Radar is the ordinary above-water-to-above-water contact lane. Sonar is the ordinary underwater-to-underwater contact lane. The dedicated Radar and Sonar buildings each author only their corresponding source-target entry, and construction rejects placing either in the other source medium rather than allowing a completed but inert sensor. Full sight remains the stronger identity-bearing tier and is not replaced by either contact sensor.

Those mounted sensor lanes aggregate into four exhaustive, orthogonal team-knowledge facts: team-air-sight, team-water-sight, team-air-radar, and team-water-sonar. The first two identify target volume observed above and below the surface; the latter two locate above-water and underwater target volume without identifying it. A unit or building that straddles the surface may earn both target-medium facts of a tier. A shot and a mounted turret are points for medium membership and therefore earn exactly one target-medium fact. Each fact is accumulated team-wide after the observing mount has passed its own authored sensor matrix; none carries or implies a weapon launch medium, trajectory capability, range, or line of fire.

Every directed weapon emission separately authors an exhaustive two-by-two boolean trajectory matrix: above-water-to-above-water, above-water-to-underwater, underwater-to-above-water, and underwater-to-underwater. Only the row selected by the emitting turret point is active. A unit or building target is medium-eligible when at least one true cell in that row intersects a medium occupied by any positive volume of its body; a shot or turret target is eligible only through the one medium containing its point. There is no same-medium preference, implicit fallback, inferred default, or ordering among true cells. If more than one route is legal, ordinary deterministic aim geometry and the physical trajectory solver choose a reachable hit point without privileging the source medium.

Long-range weapons should consume player/team intelligence, not pretend their own barrel can see forever. A target can be fired on when the weapon’s range, line-of-fire policy, ballistic solver, emission trajectory matrix, and required intelligence tier all pass. Team knowledge is unified and orthogonal to emission physics: a valid underwater-to-above-water missile may use above-water target knowledge contributed by any teammate’s sight or, when the weapon permits contact fire, team-air-radar. It does not need the observing sensor to share its launch medium or trajectory lane. Full sight gives exact aim and normal target selection. Contact-only radar or sonar information can support weapons explicitly authored for blind or remote fire, such as artillery, missiles, or other indirect systems, but direct beams and precision line weapons should usually require full sight and unobstructed line of sight. The ballistic solver answers “can this emission physically reach that point?” It does not by itself answer “does this team know enough to choose that point?”

This intentionally pushes scouting and contact sensors into army composition. A long-range turret with short local sight should be powerful only when supported by forward units, scan pulses, radar coverage, or allied sight. Earlier prototype behavior that derived full vision from every turret’s weapon range was a convenience shortcut, not the rule; fire envelope and sight envelope must be authored separately.

The ordinary roster baseline is weapon reach beyond local vision. Every armed buildable unit except an explicitly named reconnaissance exception should have at least one offensive weapon whose maximum range exceeds the greatest full-sight radius on its own sensor mount. Jackal is the armed visual-reconnaissance exception, and the starting Commander is the non-buildable command exception. Unarmed Kestrel, Sepia, and Strix carry deliberately broader information roles instead of being combat exceptions. This is an authored roster relationship, never a formula that derives sight from a weapon: small forward units and visual scouts extend exact team sight for precision weapons, while radar and sonar extend anonymous contacts only for weapons that explicitly accept contact fire. Construction craft are workers, not free mobile radar or sonar hosts.

  • The four exhaustive team-knowledge facts are team-air-sight, team-water-sight, team-air-radar, and team-water-sonar. Sight identifies and also counts as contact-level location in its target medium; radar/sonar-only coverage locates in its target medium; detector coverage may uncloak but does not locate by itself. The four facts are team-unified and orthogonal to every emission trajectory cell.
  • Every entity visibility and contact-radius test uses source and target centers for DISTANCE, with zero silhouette or hitbox padding — a hitbox never extends a sensor’s reach. Medium membership is separate from distance: a source is classified by mountCenter.z <= waterLevel, a target by the submerged fraction of its authored volume, and a target with any volume in a medium is addressable in that medium.
  • The same source/target asymmetry governs weapons. Every directed emission exhaustively asserts all four booleans: above-water-to-above-water, above-water-to-underwater, underwater-to-above-water, and underwater-to-underwater. A turret activates exactly its point-classified source row and may lock a unit or building when any true column intersects positive target-body volume, or a shot/turret when the true column matches that target point. There is no same-medium preference. A turret must not lock what its emission cannot physically reach.
  • Every full-sight and contact-sight radius is selected from the active source row and target column. Ordinary content explicitly authors same-medium sight; cross-medium sight is a separate explicit blueprint capability, and neither is inferred.
  • Radar contributes contacts only from above-water sources to above-water targets; sonar contributes contacts only from underwater sources to underwater targets. Their map-space coverage may overlap, but their source-target lanes never do.
  • Team-air-radar and team-water-sonar contacts are eligible inputs to weapons that explicitly allow contact fire (the current compatibility flag is named radar fire). Once team-unified, either knowledge channel may support any physically valid emission route to that target; sensor source medium never constrains weapon source medium. Contacts are not full entities in the recipient’s main snapshot.
  • Weapon range, tracking range, unit sight, radar range, sonar range, and detector range are separate envelopes. Sharing a number between them should be an authored choice, not a default coupling.
  • Team-air-sight and team-water-sight are player/team aggregates. A turret firing using another unit’s sight is using team knowledge, not gaining that other unit’s local sight radius or inheriting its sensor lane.
  • Construction-incomplete and destroyed hosts provide no sensor channels. A completed active-state building always provides passive full sight; its contact and detector channels require the powered/open state.
  • Terrain shade, environment-prop shade, friendly jammer tint, sensor boundaries, snapshot filtering, and targeting consume the same operational mounted sources. Presentation may soften an edge, but it may not invent another coverage footprint.

Visible units render and update identically

Ownership decides what strategic information a player learns about a unit; it must never decide how a unit the player can already fully see moves on the wire or draws on screen. Once full sight places a foreign unit in the recipient’s visible set, every field that drives its physical presentation is sampled from the same adjacent authoritative tick history as the recipient’s own units: world position, full body quaternion, linear and angular velocity, surface normal, turret yaw and pitch, and HP. There is no owner-conditional zeroing, omission, coarsening, or alternate interpolation policy. An enemy aircraft banks and turns through the same Rust/WASM pose path as a friendly one. Banking is the canonical example: its visual enrichment uses the centripetal product v_forward · ω_z, so withholding an enemy’s linear velocity silently zeroed its bank while ours rolled — a rendering difference produced purely by an ownership gate on a motion field, which is exactly what this rule forbids.

What ownership still gates is private strategic detail, not presentation: a unit’s order queue and move/attack/guard intent, the specific entity IDs its turrets are tracking, its current build or repair target, and factory rally points. A player watches an enemy unit turn, fire, take damage, and bank in full physical fidelity; they do not see what it has been told to do. That line — physical presentation is shared, commanded intent is private — is the rule. A motion or render field hidden by ownership is a bug; a strategic-intent field leaked across ownership is also a bug.

This changes nothing about fog of war. Sight and contact tiers still decide whether a unit appears — as a full entity, a radar/sonar contact, or not at all — and a unit lost to fog still vanishes from the snapshot entirely. This rule governs only how a unit is treated once it has earned full visibility: at that point its physical state is owner-agnostic.

Visibility computation must stay aggregate and indexed

Sight, radar, and sonar cannot be implemented as “each unit checks every other unit” work. The local server simulation should build player/team coverage from sensor sources, cache it at a deliberate cadence, and let targeting and snapshot serialization query that aggregate. The current direction is already right: spatial hashes, recipient/team visibility objects, memoized entity visibility, scheduled targeting probes, and Rust/WASM slabs. New sight/radar work should extend that shape.

The scalable model is a small set of medium-lane source pools and contact masks per player or team: full-sight sources, contact sources, detector sources, and temporary scan sources. Coarse cells answer “could this point be covered?” cheaply; precise distance and line-of-sight checks run only on candidates that survived the broadphase. Targeting should query enemy candidates from the existing spatial index by outer weapon envelope, stamp or derive each candidate’s visibility tier once per source entity/team, and reuse that answer across the source’s turrets. Snapshot serialization should reuse the same aggregate view instead of recomputing a separate truth.

  • Rebuild or incrementally refresh coverage when sources move, finish construction, die, cloak/uncloak, or change teams; do not run full source-vs-target scans every frame.
  • Use coarse bitsets or cell buckets for radar/full-sight membership, then exact radius and terrain/force-material LOS only when a candidate needs it.
  • Keep contact sensors cheaper than sight: radar and sonar coverage should be mostly geometric unless deliberate jamming or occlusion features are introduced.
  • Run expensive acquisition only for turrets that need work. Existing target hysteresis, drop grace, probe scheduling, and broadphase candidate buffers are the right pattern.

Snapshot channels match renderer semantics

Rich presentation snapshots remain recipient-filtered recovery packets for entity lifecycle, visibility, economy, fog, minimap, and other discontinuous or lower-frequency state. They are not the render clock for continuous root motion in same-process deterministic lockstep.

One-shot audio, projectile spawn/despawn, beam topology, and other sparse facts remain explicit events. Unit and travelling-shot root pose comes from adjacent local Rust/WASM ticks instead of a second 10 Hz motion-delta channel. A rich snapshot still carries enough current state to materialize a newly visible entity or recover after presentation state is rebuilt.

Dirty flags may still exist inside the simulation to mark changed systems, but they should not define the renderer snapshot contract under deterministic-lockstep.

Client presentation is adjacent-tick interpolation

The Rust/WASM simulation captures the previous and current post-tick pose for every stable entity slot. Every display frame samples those two endpoints with one shared alpha. Position, velocity, normals, full body orientation, angular velocity, turret yaw, and turret pitch all use that same clock. Position-like values lerp, orientations use shortest-path quaternion SLERP, and wrapped scalar angles use shortest-angle interpolation. The renderer neither predicts nor corrects root motion with independent EMA channels.

Client Simulation Model

Shared core, bounded client

There should be one headless simulation core for physical behavior. In deterministic-lockstep, every browser runs the full server simulation locally. That is not a second gameplay implementation: it is the same server simulation stack — WorldState, Simulation, physics, command execution, economy, construction, combat, fog truth, projectiles, and victory — driven by command frames. The renderer reads adjacent fixed-tick presentation rows directly from that local Rust/WASM simulation, so the client render path does not need a duplicate gameplay model.

  • Share physical kernels for body motion, projectile stepping, recoil, hover, turret pose, terrain sampling, and collision helpers.
  • Run authoritative systems locally on every peer and keep them deterministic through fixed frames, deterministic math, canonical command ordering, and checksum diagnostics.
  • Capture final post-tick root and turret poses in Rust/WASM, after physics, collision, and shot lifecycle work has settled.
  • Interpolate every visible root and mounted turret between the same adjacent ticks. Keep variable-length beam topology on its dedicated presentation path.
  • Use snapshots for visibility, lifecycle, economy, fog, minimap, recovery, audio, and other non-continuous presentation facts; do not serialize a competing high-rate motion stream for a same-process lockstep renderer.

Interpolation deliberately trails by one fixed tick

At simulation tick N, presentation retains the final states from N-1 and N. Render time advances a single alpha from zero to one across the next fixed-step interval and clamps at one if the next tick is late. This adds at most one selected simulation tick of visual latency, but eliminates the oscillation and per-channel lag caused by chasing a moving snapshot target. Gameplay remains exactly at tick N; only the visual sample is delayed.

This is interpolation, not extrapolation. Linear and angular velocities are interpolated for rig animation, effects, and diagnostics; they are not integrated again by the renderer. Forces, gravity, propulsion, guidance, collision, lifetime, and homing remain exclusively in the authoritative fixed-tick simulation.

One clock owns all continuous root pose

A body cannot have its position at one effective time, its orientation at another, and its turret at a third. The presentation row therefore contains all fields required to draw the same physical instant: world position, scalar yaw, linear velocity, support normal, full quaternion, angular velocity, and mounted-turret yaw/pitch and rates. All are sampled with the same alpha in one Rust/WASM batch.

  • Linear fields and normalized support normals interpolate between adjacent authoritative values.
  • Full body orientation uses shortest-path quaternion SLERP, preserving aircraft bank, pitch, and roll instead of collapsing motion to yaw.
  • Scalar yaw and turret yaw/pitch use shortest wrapped-angle interpolation.
  • A recycled stable slot snaps both endpoints to its new occupant; it never blends one entity into another.
  • If the renderer misses a simulation tick, alpha clamps at the newest state. It does not extrapolate stale velocity.

Decorative locomotion rigs, wheel spin, tread phase, smoke, recoil enrichment, and building open/close animations remain client-side because they do not affect gameplay. They may use local damped controllers, but those controllers decorate an already-interpolated physical pose and never feed back into root position or orientation.

Travelling shots use the same authoritative pose history

Every peer already runs the authoritative projectile simulation inside deterministic lockstep. The renderer must not reproduce that simulation. Every live travelling shot — plasma, mortar, rocket, missile, D-gun, reflected, or collision-spawned — publishes its final post-collision position, linear velocity, yaw, and yaw rate once per fixed simulation tick. All shot families enter the same Rust/WASM presentation history as unit roots.

Spawn and despawn remain discrete lifecycle events. While a shot is live, its motion is adjacent-tick local presentation state. The renderer interpolates it and does nothing else: no gravity, propulsion, homing, terrain following, collision, lifetime advancement, or local deletion. Its visual forward axis is derived from the interpolated authoritative velocity/orientation, so rockets and missiles point along their actual flight path.

Launch frames are explicit

A fired shot has two velocities that must not be confused. The ballistic solver works in the firing mount's moving reference frame: it receives the turret mount's world position and velocity, the target's world position and velocity, the relevant acceleration terms, and the universal gravity constant. Its launch solution is the muzzle-relative velocity vector, not the complete world-space projectile velocity.

Projectile creation converts that solution into the authoritative spawn event by adding the selected QueryWeapon socket’s current world velocity: v_world = v_socket + v_launch_relative. The same world velocity is written onto the projectile body and into the spawn event, so simulation and rendering both start from one physical initial condition. A projectile fired from a moving tank, aircraft, bobbing suspension mount, or recoil-shifted turret therefore inherits that muzzle motion at launch.

Launch inheritance is an explicit turret-blueprint policy through addTurretVelocityToEmissionLaunch. A vertical tube launcher can disable it so the authored launch vector remains exactly vertical in world space, or enable it so the shot carries mount motion. D-gun terrain waves remain specialized: their launch path suppresses vertical mount velocity so a terrain-following wave does not become a lobbed shell.

Shot families share one presentation policy

Homing is not a presentation exception. A delayed-guidance rocket and a ballistic plasma bolt both receive the same authoritative row at the same point in the fixed tick. Reflections are also represented by the final row; their unquantized impact audio may add an exact trail stamp, but projectile root motion always comes from the shared adjacent-tick presentation history.

Airborne rockets and missiles share constant-speed interception

rocket and missile remain presentation and interaction families; authoritative movement combines the shot's expanded shotLocomotion preset with its blueprint-owned turning controls. Every airborne rocket and missile uses constantSpeedGuided: it authors no propulsion, guidance thrust, linear damping, or gravity acceleration. Guidance rotates the existing world-velocity vector toward a predicted interception point, bounded by turn rate, while preserving its magnitude exactly. Tuning therefore lives in launch/cruise speed and target inheritance, plus each shot blueprint's lifetime, turn rate, guidance delay, and guidance ramp, rather than forward acceleration.

Lead is solved from the munition’s current position and complete world-speed magnitude against the target’s current position and world velocity. The munition’s current velocity is not also supplied as moving-origin velocity; doing both counts its motion twice and creates a false intercept. Non-vertical launchers use the same zero-gravity, zero-damping solve to point ahead before firing. In flight, an exact constant-velocity quadratic refreshes that speculative intercept at an authored deterministic cadence: 10 Hz for missiles and 5 Hz for the light vertical rocket, capped at the current simulation tick rate and staggered by projectile ID. The inexpensive bounded turn toward the cached intercept, ordinary integration, arming, collision, and lifetime remain fixed-tick work. Target manoeuvres therefore become smooth bounded course corrections without paying for a full prediction on every tick.

The light vertical-launch rocket preserves its authored launch signature: it travels straight upward at constant cruise speed for three seconds, then smoothly engages its turn authority and begins steering toward the same velocity intercept as every other airborne guided munition. Its 5 Hz prediction refresh remains active during the straight-up delay, so the rocket already owns a speculative future intercept if its inherited entity disappears before turning begins. The delay is a guidance phase, never an acceleration phase or a speed exception.

Shot locomotion owns movement domains and terminal decisions

Every travelling shot expands one shotLocomotionPresetId into a complete runtime profile. Air and water each state whether the shot is operational there and own their propulsion, guidance-thrust, and resistance values. A guided rocket/missile blueprint owns one explicit turning block; runtime expansion installs its turn rate only on the preset's operational media. Every shot blueprint also explicitly owns maxLifespanMs, using null when collision/ground contact rather than elapsed time limits its life. Ground is a contact domain: ordinary shots impact it, while an explicit terrain-following mode may travel along it. Water entry and exit are authored transitions, so a shell may despawn at the surface, a torpedo may continue underwater and become ballistic when it breaches, and a future munition may detonate on either crossing.

Operational medium physics and targetable trajectory routes are related but not interchangeable. Every shot and ray blueprint exhaustively asserts its four source-to-target medium booleans; locomotion and ray boundary behavior must then prove every true route physically executable. A false route forbids planned lock-on through that cell, while an authored transition may still describe incidental post-miss travel such as an underwater torpedo breaching ballistically. Travelling shots and ray samples are points and occupy exactly one medium at a time.

Shot locomotion also decides the terminal outcome for entity impact, ground contact, expiry, destruction, and reflector impact: detonate or despawn. It does not apply damage. The shot body's base.deathExplosion remains the single payload authority; combat executes that payload only when locomotion returns a detonation. Target feasibility reads the same expanded profile as flight. Ballistic presets use the ballistic solver, while powered and constant-speed presets use their active medium, launch speed, engine authority, and lifetime reach envelope. A weapon may never reject or admit a target by predicting a different motion model from the one its fired shot runs.

The named split remains deliberate: shotRocketLight is a vertical-launch rocket, while shotMissileFast and shotMissileLong are direct-launch missile profiles. They share constant-speed interception while retaining distinct launch phases, speeds, turn rates, lifetimes, visual language, and point-defense/reflection treatment.

Rendering samples authoritative presentation state

Rendering should not own simulation cadence. requestAnimationFrame is a display scheduler, not a simulation clock. It samples the adjacent authoritative ticks using the one shared interpolation alpha; it never advances projectile gameplay state. If the browser renders at 144 Hz, 60 Hz, 37 Hz, or is briefly tab-throttled, the simulation contract stays unchanged.

Physics Model

The game should be more physics based than its inspiration. BAR is the ergonomic and strategic reference point; this project should make the physical world more fundamental. The rule of thumb is F = M * A. If a gameplay feature moves, pushes, resists, falls, recoils, hovers, blocks, crushes, or explodes, it should be described through forces acting on masses and integrated into motion.

Full 3D, not decorative altitude

The sim uses a real 3D state: horizontal x/y, vertical z, velocity, acceleration, gravity, surface normals, sphere and cuboid bodies, terrain contact, building collision, unit collision, projectile collision, and hover lift. The renderer presents that state, but the local server simulation should treat altitude and contact as real gameplay inputs.

Kinematic calculations read entity position and velocity through the explicit accessors getEntityPosition3d and getEntityVelocity3d. Callers pass explicit acceleration vectors only when the underlying acceleration is authoritative; units otherwise use zero acceleration for velocity-only lead. Targeting and ballistic solvers receive raw kinematic values plus the universal gravity constant instead of entity IDs or optional lookup inputs.

Turret range is a vertical cylinder, not a sphere. Every turret range radius — fire acquire/release, minimum fire preference, tracking acquire/release, and any other turret-authored “in range” shell — uses horizontal distance as the radius. For a range R, the cylinder is centered on the turret mount in x/y, reaches up to mount.z + R, and extends downward without a lower cap. A target is inside the range shell when its body intersects that horizontal radius and it is not above the shell’s top cap. Height below the turret does not consume range budget, so cliffs, aircraft, and drop shots can target downhill or underneath cleanly. Height above the turret remains bounded by the same authored number that defines horizontal reach.

Ballistic and line-of-fire feasibility remain separate gates after the cylinder range check. The range cylinder answers whether a turret may consider, track, or engage a target; the ballistic solver still answers whether the authored projectile can actually reach the chosen aim point from the turret mount. Range overlays on the ground show the cylinder’s horizontal radius directly.

Mass must matter

  • Unit propulsion is a force profile applied to a mass, not a direct position edit.
  • Recoil applies counter-force to the firing body.
  • Explosions, beams, collisions, and impact impulses apply forces that heavier units resist differently.
  • Hover lift balances gravity through force and damping.
  • Ground contact is spring and friction behavior against terrain, not a clamp disguised as physics.

Unit locomotion is arrival control, not waypoint seeking

Movement should not be a magnetic pull toward the next waypoint. A position-only seek controller looks acceptable on slow, high-friction units, but it breaks down as soon as a body has meaningful momentum. Hovercraft expose the failure most clearly: the unit keeps accelerating toward a point even when its current velocity already guarantees overshoot, then crosses the point, gets pulled back, and oscillates like an undamped spring.

The locomotion question is not “which direction is the waypoint?” It is “what acceleration do I need, under this unit’s force limits, to arrive at the desired state?” That desired state includes both position and velocity. A final command point usually wants near-zero velocity. An intermediate waypoint may want a through-velocity aligned with the next path segment, so the unit flows through the path instead of stopping at every corner.

Every locomotion profile should therefore compute force from both position error and velocity error. If a unit is close to its intended spot but still moving quickly, the correct thrust is often opposite its current velocity, even if the target remains slightly ahead. This is controlled arrival: a damped physical controller that spends stopping distance before it runs out, saturates against the unit’s available thrust, and prevents waypoint overshoot from turning into visible oscillation.

  • Pathfinding chooses where the body should go; locomotion chooses how the body physically arrives there.
  • Waypoints are desired motion states, not magnets. They carry an intended position and, when useful, an intended pass-through velocity.
  • Final command points resolve per final-approach class: units that can stop use braking-aware arrival so the body settles without orbiting, bouncing, or springing back across the destination; forward-flight units keep their final point as a permanently active pursuit goal, always turning toward it at their constant rate.
  • Hovercraft, ground units, and air units use the same high-level arrival controller; they differ only by mass, thrust, friction, damping, turn authority, contact model, and vertical constraints.
  • Hovercraft should remain slippery because their physical limits say so, not because the controller ignores velocity until after overshoot has happened.
  • The global BATTLE arrival setting (slowDownAtFinalWaypoint, default BAR-style full-speed arrival) tunes only the middle class. Authored maintainFullThrustAtWaypoints always bypasses the final brake (plane, aerosub); authored alwaysBrakeAtFinalWaypoint always keeps it (drone and every hover chassis); the global setting decides the remaining ground and sea locomotion.

The last waypoint is an anchor, not a consumed order

Completing a movement order does not delete its point. The final move/fight point of a unit’s queue survives as a satisfied movement anchor: arrival marks it satisfied and cuts drive, and the point stays at the head of the queue as the unit’s standing goal. This is deliberate wind policy. Bodies here live under continuous external force — wind, blast pressure, collision shoves — and a unit whose queue empties on arrival has nothing left to hold; hovering units used to be blown across the whole map exactly this way. Every unit therefore always owns at least one durable goal: the satisfied anchor, a lock-on target, or a loiter center.

  • Ground and hover units re-engage ordinary approach when displaced beyond the arrival radius, then settle and hold again. Only new orders replace the anchor.
  • A hover chassis authors alwaysBrakeAtFinalWaypoint: braking-aware arrival and a standing hold at the point are what make it a hover unit, so the global full-speed-arrival setting never strips its final brake.
  • A forward-flight chassis can neither stop on a point nor hover over one, so its terminating waypoint is never marked satisfied: the plane always turns toward it at its constant turn rate, passing through, turning back, and passing again. The perpetual pursuit is the hold, and it counters wind by construction. The loiter circle exists only for a cruise unit with an empty queue — never as a substitute for a waypoint the player placed.

Body-forward waypoints have a no-turn deadzone with a front slice

The settled body-forward waypoint contract (generalized 2026-08-24). Every locomotion preset whose propulsion follows its body heading — including planes, aerosubs, Ducks, Orcas, submarines, rovers, tanks, amphibians, and bots — owns the same orbit escape interlock. A non-terminating waypoint has a no-turn deadzone: inside it the unit may not turn at all unless that waypoint sits within 45° left or right of the direction it is facing, so if it is going to miss, it misses large and straight. A stoppable chassis hands its terminating Move/Fight anchor back to ordinary braking-aware arrival and holds there. Only an authored cruise chassis uses perpetual terminal pursuit: it has no terminal deadzone and never consumes that anchor. No locomotion type receives a bespoke anti-circle mechanic.

A body whose propulsion and yaw response follow its nose has a finite turning circle. A goal inside that circle is unreachable by steering toward it — pursuit decays into a constant-speed, constant-turn orbit that never crosses the point, never completes the order, and freezes every queued waypoint behind it. The subtle part is that a pursuit orbit keeps the nose within the servo’s tracking-lag angle of the waypoint direction — always well inside the forward half-plane — so any half-plane “heading away” test never fires inside the orbit. The turn permission must be a slice narrower than the orbit’s lag angle. Cruise locomotion (plane, aerosub) rides the alwaysForward actuator, so the orbit cannot even rely on off-nose throttle loss to shrink itself; ordinary body-forward chassis can still orbit a tight pass-through point under momentum and finite yaw authority. Every non-terminating waypoint leg steers through one stateless per-tick interlock, authored per preset in motionControl.waypointDeadzone:

  • The deadzone around the current waypoint has radius turnRadiusMultiplier × R (authored as 2.5 on every body-forward preset), where R = speed / turnRate is the natural turn radius and can never be smaller than the body collision radius. For alwaysForward chassis the turn rate is the authored actuator.turnRateDegreesPerSecond constant-rate slew, so the geometry is exact — the interlock and the yaw actuator read the same number. A servo-driven chassis uses the shared critically damped yaw model’s sustainable-rate estimate (π√k/4 from the damped spring’s 90°-lag stall).
  • Inside the deadzone the unit may keep turning only while the waypoint sits within frontSliceDegrees left or right of its nose (authored, 45° per side). Anywhere else in the deadzone it may not turn at all: thrust is pinned straight along the current nose. If the unit is going to miss the waypoint, it misses large — a dead-straight line that leaves the deadzone.
  • Outside the deadzone steering is free at any angle. That is where the turn-back happens, with a full deadzone of room to complete the turn and line up a straight pass through the point.
  • Why circling cannot persist: a sustained powered orbit needs enough off-nose thrust to hold speed against damping, and the servo lag of tracking the rotating center direction pushes the nose far off the waypoint — well outside a 45° slice. The interlock therefore forbids the orbit configuration itself from turning, straightening it into an outbound line. The slice must stay below 90°: at 90° it degenerates into the half-plane a powered orbit never leaves, which is the failure the config validator refuses.
  • The lock applies only while actually moving. A body pinned against the map boundary at near-zero speed releases the lock and steers freely; at near-zero speed its turning circle is tiny anyway.
  • Terminating anchors preserve locomotion semantics. A stoppable body-forward unit uses the shared arrival controller to brake, satisfy, and hold its final Move/Fight anchor. A cruise unit has no terminal deadzone and never captures: it always turns toward the anchor, passing through and returning. Non-terminating legs capture at their existing obstacle-aware route radius, so tight ground/sea corners retain one-world-unit precision while broad legs, queues, and patrol loops advance normally. The interlock is a pure function of position, nose, waypoint, and R each tick — no latched state, no hysteresis — and every eligible locomotion type evaluates in one WASM batch per tick.

Terrain pathfinding is directional around slopes and cliffs

Terrain pathfinding separates cell occupancy from directed edge traversal. A cell is legal only when the selected unit’s force budget in that physical medium can control the complete terrain surface represented by the cell. An uphill edge must additionally fit the corresponding directed climb budget; directional mode may preserve a controlled descent that would not be climbable in reverse, while symmetric debug mode applies the uphill gate both ways. There is no global angle ceiling. The limit comes from the unit’s exact physics mass, gravity, authored actuator force, the local support normal, and Coulomb contact grip.

Among physically legal routes, A* minimizes a normalized traversal-time cost derived from the same abstract force profile as locomotion. Dry contact uses the smaller of authored ground drive and μN. Bed-supported wet movement adds the unit’s water propulsion to that contact budget; fluid-supported water and air do not inherit lakebed slope at all. The sole planning reserve is 85% of authored propulsion. These dry, wet-MOVE, and wet-WAYPOINT envelopes are derived once per immutable physics profile and exact mass, cached, and shared by route legality, smoothing, validation, cost, and debug presentation. A wet cell does not automatically receive full water thrust: bed-supported queries use the cell’s highest touched terrain, the unit’s support-point height and collision radius, and the same spherical displaced-volume equation as runtime physics to conservatively weight water propulsion. A shallow wet shoreline can therefore behave like dry contact, while a deeply immersed body approaches its full-water envelope. Uphill cost accounts for longer surface distance and gravity subtracting from available tangential acceleration; contour travel reserves force for the lateral gravity component. Medium boundaries carry no arbitrary entry or transition surcharge.

Contact load is physical rather than shorthand: N = max(mg * normalZ - nonContactForce · normal, 0). A steep surface therefore carries less normal load, powered lift unloads its contact patch, and a force into the terrain increases grip. The runtime traction clamp and arrival controller consume that same actual contact authority. Passive static friction may hold an uncommanded unit up to μN; it is not limited by the motor rating. This is why a wet MOVE cell may be traversable with active water thrust while the same cell is not a stable wet WAYPOINT after that thrust ends.

Collision clearance remains configuration-space geometry: the physical body radius is a hard legality constraint. Additional stand-off from blockers is a soft cost gradient, so a unit prefers open ground but may still use a narrow corridor whenever that is the only legal or genuinely cheaper route. Direct-route shortcuts and line-of-sight smoothing evaluate the same route cost as A* and may not erase a slope or clearance decision after the search.

Pathfinding nodes are conservative terrain summaries. A node must account for every authoritative terrain triangle that touches it, including triangles that only meet the node along an edge or vertex. Vertical 90-degree faces are common and must participate in the node’s traversal tests even when the node center samples a flat top or bottom shelf. The planner may use such a node only when the complete touched geometry is inside the selected medium’s force-derived envelope; directed edges must fit the matching climb budget as well.

Terrain is the base surface; grounded buildings are an obstacle layer on it

The locomotion grid is two layers with different lifetimes. Terrain is the expensive, near-immutable base: sampled per cell from the authoritative mesh, rebuilt only when the terrain version moves. Grounded building footprints are a cheap dynamic obstacle layer on top: the construction system already authors per-cell movement semantics at placement (structure cells block when the host is grounded, while authored non-physical clearance cells — such as a wind turbine’s blade sweep — reserve placement but never blocking movement), and the pathfinder syncs exactly that cell set whenever the BuildingGrid version moves. Building churn re-runs only the O(n) blocked/clearance/ connected-component sweeps, never terrain sampling. The match-static path-cell consolidation multiplier groups 1×1 through 5×5 canonical 20-wu build cells into one path cell (3×3 by default). The summary is deliberately conservative: any blocked build square, forbidden medium, or physically illegal touched terrain inside the group rejects the whole path cell. Coarsening may decline a narrow valid passage, but it must never invent a route through lava, water, a cliff, or a grounded structure.

A building cell blocks every non-air medium; air overflies footprints exactly as it overflies terrain. Blockage is one-way by construction: no step may ever enter a building cell, so a unit standing where a building just went up is an escape start that can route out but never back in, with no special recovery machinery. An escape start also relaxes the clearance requirement to the clearance the body already has: demanding more room than the cell it is standing in makes every neighbour illegal and strands it where it stands, which is what left a commander pinned beside the structure it had just finished. The goal still demands full clearance, so the route ends somewhere the body genuinely fits; only the way out is allowed to be as tight as the spot it is leaving. Route plans carry the BuildingGrid version they were validated against; when it moves, only each plan’s remaining legs re-validate — routes far from the change restamp for free, routes now crossing a footprint invalidate immediately, queue a fresh sliced search, and leave the unit under a physical controller hold until a safe replacement is complete.

The construction grid still answers a different question — whether a building may reserve its authored placement-cell mask — and hovering buildings still answer it while contributing nothing to locomotion: units plan and drive across the terrain beneath them.

  • Map bounds and hard blockers remain symmetric. Water is an intentional-domain boundary for ordinary land waypoints but may remain a physical MOVE/recovery medium when the unit has water propulsion.
  • Other units may be ignored by the global path calculation; local collision, steering, and arrival control handle moving-unit congestion.
  • Grounded building footprints are hard blockers, clearance sources, component splitters, and route-staleness triggers. Hovering buildings are none of these; their only ground effect is the construction reservation.
  • A structure placed during play is a physical body from the moment it is placed, exactly like one placed at boot. A footprint that blocks pathing but has no collision body is half an obstacle: nothing pushes a unit off the site, so it ends up inside the finished building — the one place the router will never route it back into.
  • Goal points inside a footprint snap to the nearest legal cell through the same passability the router uses; assaulting a base is pathable by construction.
  • Dry contact, wet commanded movement, and wet resting-waypoint support have separate force-derived surface envelopes; air and fluid-supported water are terrain-angle independent.
  • Connected-component shortcuts encode invariant obstacles plus the current building layer; unit-specific medium, mass, force, contact, and directed-edge rules remain query-time tests.
  • Line-of-sight path smoothing must run the same directed edge checks as A*, so smoothing cannot erase a necessary climb gate or clip a footprint.
  • Route costs are capability-based and deterministic: physical acceleration and clearance inputs, never locomotion rig type or presentation state.
  • Slope travel time is priced with the terminal-velocity model — the linear flat-to-remaining acceleration ratio, which the damping rate cancels out of — never the optimistic square root.
  • Intermediate corner capture is plane-crossing within a lateral corridor, not a pinpoint radius; corner speed shaping engages only for bends sharper than steering alone can round inside that corridor.
  • Medium transitions have no fixed penalty, and the base planner carries no heading-state, turn-radius, congestion, or threat-cost expansion.

Waypoints are intent; pathfinding points are disposable

A waypoint is a player-, AI-, factory-, or fabricator-authored command point. It belongs to the command queue, can be shown in the UI, can be edited, inherited, serialized, and reasoned about as tactical intent. A pathfinding point is different: it is a private movement-plan sample generated by the pathfinder for the currently active leg. Pathfinding points are not commands, not rally markers, not factory defaults, and not something a newly produced unit should inherit from the unit or fabricator that supplied its waypoints.

Factory and fabricator inheritance therefore copies only high-level waypoints. When a unit receives those waypoints, it does not receive pre-expanded path points. It plans the route from its actual current position to the first waypoint only when it starts moving, then plans from waypoint to waypoint as each leg becomes active. If it is pushed off route, stalls, terrain changes or a dynamic target moves enough to make the current leg stale, the current pathfinding points are discarded and recomputed. The durable waypoint list remains intact.

Waypoint validity and physical movement validity are different cell masks. A waypoint-valid cell is a legal intentional order destination for that unit's authored locomotion policy and a physically supportable endpoint. A move-valid cell is one the unit's actual active force profile and footprint can traverse. A bed-supported wet MOVE may combine Coulomb-limited ground drive with water propulsion, while a wet WAYPOINT must remain supportable without commanded water thrust. A thrown land unit can therefore begin in a wet cell that is move-valid but waypoint-invalid, propel itself toward land while taking its independent water damage, and re-enter its waypoint domain. Once in the waypoint domain, directed edge policy prevents ordinary routing from choosing recovery-only water as a shortcut. The CLIENT pathing overlay always retains exactly one selected unit and uses one exclusive NONE/WAYPOINT/MOVE display mode, so the selected domain is visually unambiguous without losing the unit choice when hidden.

  • Do not store pathfinder-expanded intermediate points in the same array as authored command waypoints.
  • Do not serialize pathfinding points as gameplay intent; serialize waypoints and let the local server simulation regenerate movement plans.
  • Factory rally routes and fabricator-provided routes are high-level waypoint lists. Produced units resolve those lists against their own locomotion profile and current world state.
  • Every waypoint, rally marker, connecting line, and drag preview resolves from the raw terrain-ray hit. Water is never a waypoint surface: a waypoint under a lake sits on the lake bed the cursor actually pointed at and remains visible through the transparent water.
  • Pathfinding is leg-local and demand-driven: plan the active leg, cache it while valid, and throw it away on completion, obstruction, stale progress, terrain change, or target drift.
  • Patrol and fight loops re-enter the planner per leg rather than baking one permanent expanded loop. The path should adapt to the battlefield, while the waypoint loop remains the command.

Path searches are resumable fixed-tick jobs, never frame-time bursts

The authoritative command timeline never waits for pathfinding: commands apply in canonical lockstep order and install durable intent immediately. Derived route work enters separate fresh and refresh lanes. Exactly one ally team is selected each fixed tick in stable round-robin order. That team may close at most 4,096 A* nodes, spending unused nodes on additional routes for the same team. Admission rotates by player within the selected team, so a side with more seats cannot multiply its routing throughput. Exact validated direct segments, shared formation-cache hits, and stale queue entries perform no A* work and do not consume that tick's search admission.

Fine-grid A* retains its open heap, scores, parents, best reachable frontier, and cumulative expansion count between team turns. Each ally team may retain at most one unfinished continuation. Each turn closes a fixed configured number of nodes; it is never sized from measured wall time. There is no arbitrary total expansion ceiling: a hard mountain route may take many deterministic ticks and finishes only when it reaches the goal or exhausts the reachable graph. A terrain or grounded-building version change, or a superseding unit intent, invalidates the continuation and queues a fresh job. Continuations are derivable simulation scratch and are not serialized as command or snapshot state.

A planless unit awaiting its fresh route applies no destination-directed propulsion. It is not frozen: gravity, collision impulses, slope contact, passive friction, and external forces remain authoritative. A stale plan may continue only while its remaining suffix validates against the current navigation layers; otherwise the controller holds. Physical capability and hazard policy are separate: ordinary water may use the unit's authored wet force envelope, while lava removes the water domain from both MOVE and WAYPOINT routing even for a body that could mechanically swim through it. Air traversal still overflies the liquid.

  • Never move toward the raw command point while a fresh path is unresolved.
  • Never budget authoritative search work from elapsed milliseconds or renderer cadence.
  • Each ally team owns at most one sliced A* continuation; switching teams swaps dense WASM arenas without copying them. Queued units retain intent, not map-sized frontiers.
  • A completed partial route is a proved-safe reachable frontier, not a node-budget timeout. Its endpoint must remain a physically supportable stop.

Force models answer gravity; constant-speed guidance preserves velocity

Every force-integrated body with mass feels gravity every tick. A constant-speed-guided munition is an explicit kinematic locomotion policy: vertical hold is part of preserving its authored speed vector, so its validated operational profile supplies zero gravity, thrust, and damping to the ordinary acceleration integrator. This is not a visual-family exemption or a generic “ignores gravity” switch; it is the named motion model’s defining invariant.

Thrust-guided policies still answer gravity inside their real-time guidance equation: lateral steering and vertical counter-gravity share one bounded acceleration budget. Constant-speed guidance does neither; it rotates velocity and preserves magnitude. Losing a missile seeker therefore makes that missile continue on its current vector. The light vertical rocket instead finishes its bounded turn toward its last successfully solved speculative intercept; once its velocity points at that point, it leaves the guidance batch and coasts without repeating steering math. A reflection or other discontinuous velocity change invalidates that aligned state. A thrust-guided body naturally returns to ballistic motion when its engine authority ends.

  • Gravity is applied to every force-integrated mass body every tick. Constant-speed guidance is the explicit validated kinematic policy; there is no generic ignoresGravity flag or projectile-family exemption.
  • Thrust-guided projectiles add a counter-gravity term inside the same steering update that produces lateral correction. Guidance and gravity-cancellation are one acceleration vector, not two systems.
  • The counter-gravity term is bounded by available thrust. A weak thrust-guided body should sag, not teleport — homing saturates instead of lying.
  • Spent thrust-guided bodies return to ballistic motion automatically. Constant-speed-guided bodies instead retain their last velocity vector when guidance is lost.
  • Hover and any other “defies gravity” behavior follows the same shape: a force that fights g · m, not a conditional that skips it.

Unit locomotion is one fully-abstracted force profile across ground, air, and water

A unit’s locomotion is not a closed set of discriminated chassis types (“this is a wheeled unit,” “this is a flyer”) that each carry their own private physics. It is one fully-abstracted force profile assembled from the unit blueprint and its locomotion preset: the same physically applicable groups are present on every runtime unit, while the authored unit contributes per-medium maximum propulsive force, mass, and body-specific surface-lift/gravity-counter terms. The chassis archetypes — rover, tank, amphibious-tank, crawler, bot, amphibian, drone, plane, submarine, and aerosub — survive as visual rig choices and authored default presets (see Locomotion Visuals Are Frontend), not as separate physics code paths. Two units with the same force-profile numbers move identically regardless of which rig draws them, exactly as two shapes with the same material look identically (Materials Are Independent Of Shape). A zero remains a real, meaningful unit propulsion value, but every unit deliberately authors at least a small positive water drive so an externally displaced body can attempt to recover. Intended aquatic locomotion has useful water authority; ordinary locomotion has only emergency authority. Locomotion presets provide shared contact, resistance, control, and navigation behavior without overriding unit-specific propulsion.

The world has three propulsion media: ground (a terrain contact patch, including terrain that lies under water — the lake bed is ground), air (the fraction of body volume above the water plane), and water (the fraction of body volume below it). Air and water are complementary occupancies rather than a typed switch: the simulation computes the sphere’s displaced-volume fraction fWater at the water plane and sets fAir = 1 - fWater. Every air and water force is weighted by its occupied fraction, so a body that is 25% submerged receives 25% of its water response and 75% of its air response. Ground is independent and joins the blend whenever a contact point rests on a surface, even underwater. So a unit standing on a lake bed is in ground + fractionally water/air; a unit fully submerged mid-column is water only; a surface-skimming craft can continuously transition between air and water while its skirt optionally contacts; a submarine resting on the bottom is ground + water.

Locomotion is grouped by physical responsibility. Ground, air, and water each own an explicit maxPropulsiveForce. Navigation has two cell domains: waypoint-valid cells are intentional destinations and entries, while move-valid cells are derived from actual physical propulsion and allow recovery after displacement. Neither domain disables an authored air or water force while the body physically occupies that medium. Ground also owns staticFrictionCoefficient, tangentialDampingRate, and angularDampingRate. Air and water each own linearDampingRate and angularDampingRate. There are no hidden force multipliers, reference-mass scales, global thrust scales, anisotropic direction scales, or quadratic terms between authored values and the force law.

  • Propulsion is a separate maximum directed force for ground, air, and water. Air and water forces are weighted by their occupied volume fractions, independently of route permission; when a body contacts a slope, every directed drive resolves along that supporting tangent rather than into the terrain. The simulator applies a = F / m, so mass matters directly and each medium can be tuned independently.
  • Propulsion axis is explicit actuator behavior. worldPlanar drives directly along the requested horizontal direction. waypointForward projects that request onto the nose and permits signed forward/reverse thrust; waypointForwardOnly uses the same nose-aligned drive but supplies no powered force for requests at or behind the lateral plane — the unit turns toward the waypoint before it starts moving, and standing units use it to turn instead of walking backward. Both waypoint modes throttle by the off-nose projection, which means a hard turn bleeds speed — correct for walkers and vehicles, fatal for flight. alwaysForward (plane, aerosub) therefore keeps the gas fully on along the nose every tick: the steering request only aims the yaw servo, and forward flight may turn but may never stop accelerating forward. A plane that slows in a turn is the seed of every waypoint orbit.
  • Static friction is dimensionless contact traction: ground propulsion is limited by normalLoad * staticFrictionCoefficient, and passive friction can hold or brake an uncommanded body within that same contact limit. It is not a velocity- or angular-resistance setting or a motor-force substitute; those use explicit per-second damping rates.
  • Ground damping uses explicit per-second rates. tangentialDampingRate removes residual sliding along the contact plane, while angularDampingRate removes uncommanded spin. Both are separate from static friction: friction caps contact force; damping decays existing motion.
  • Fluid resistance is isotropic linear damping relative to the medium (wind for air, still water until currents are added), plus angular damping. This deliberately keeps the model small and identifiable.
  • Attitude control has no global angular-speed limit. The critically damped servo derives torque from force the active locomotion media can actually supply, with ground authority constrained by the same Coulomb grip as translation and total lateral control constrained to one body-weight. That torque acts against the solid-sphere moment of inertia I = 2/5 m r^2, so turning is an acceleration-and-inertia result: larger or heavier bodies respond more conservatively under the same force rather than converging on a shared maximum turn speed. The closed-loop response deliberately takes twice the fastest torque-supported response time, halving angular rates while preserving those physical ratios.

Ground is a third addend, never an override

Ground is additive to air and water. Every ground term — propulsion, static friction, tangential damping, contact braking, and contact attitude authority — is one more contribution summed into the same force and torque totals the occupied fluid media already contribute. Touching a surface never disables, replaces, or suppresses the air or water response of a body that is still occupying that medium. A submarine resting on the lakebed keeps its full water drive, water damping, and water attitude behavior and gains whatever the contact adds; it does not become a ground unit for the tick.

Ground carries its own occupancy, exactly as air and water carry theirs. Air and water are weighted by displaced-volume fraction; ground is weighted by the fraction of the body’s weight the contact actually carries — normalLoad / (m · g), the same Coulomb N that already caps contact drive, so upward medium support unloads the contact continuously. A neutrally supported body near a surface has a ground occupancy of about zero and therefore behaves as the fluid says; a body whose weight rests entirely on the surface has a ground occupancy of one and behaves as the contact says. Nothing switches; the weights move.

  • Ground friction and ground tangential damping are scaled by ground occupancy and added to the fluid damping already acting on the body. A floating or neutrally buoyant body does not inherit full dry-land friction because its hull grazed a slope.
  • Ground propulsion is scaled by the same contact load through the Coulomb limit and added to the occupancy-weighted air and water drives. A body with zero authored ground force loses nothing by touching a surface.
  • The attitude leveling target is the occupancy-weighted sum of the contact normal and the fluid’s level up-vector, normalized. A tank on a hill still lies on the hill; a submarine hovering a hull’s width off a steep lakebed wall still lies level, because the wall is carrying none of its weight.
  • A contact that carries no load contributes no ground term. This is a weight reaching zero, not a branch being skipped — the same expression evaluates for every body in every medium.
  • Any code that reads “if grounded, use the ground value, otherwise use the fluid value” is a bug against this rule. The correct shape is always fluidTerm(occupancy) + groundTerm(contactLoad).

Medium is sampled rather than typed. Ground applies on a supporting contact; air and water use complementary displaced-volume fractions. Their forces are occupancy weighted and add. Waypoint navigation is an explicit preset policy (allowOnGround, allowedFluidMedia), independent of the visual locomotion mechanism. Move validity is capability-derived. A route may leave recovery-only cells and enter the waypoint domain, but may not voluntarily leave the waypoint domain for recovery-only cells. Survival policy is separate again: every unit authors numeric waterDamagePerSecond, with zero for water-safe units, and damage samples only whether the authoritative body origin is strictly below the water plane.

Surface following is a source-explicit powered support force, not a height clamp. Air blueprints author surfaceFollowingInverseForceFromGround and surfaceFollowingInverseForceFromWater; each air probe selects exactly one inverse-distance source. Water blueprints author surfaceFollowingInverseForceFromGround and surfaceFollowingProportionalForceFromWater; both contributions act together at every wet probe, the first reciprocally from the lakebed/support surface and the second proportionally to depth below the water plane. Inverse probe distance uses one positive minimum; all proposed forces are aggregated by the configured average or maximum and then occupancy weighted. The configuration deliberately retains surfaceLiftResponse: { randomizationAmount: 0, ema: 0 }: support is deterministic and unfiltered, with no hidden temporal state.

Every surface-following distance is measured from the unit’s one canonical locomotion support point, never from the rigid body center: supportZ = bodyCenterZ - supportPointOffsetZ. Ground contact already uses that datum, and air-to-ground, air-to-water, water-to-bed, and water-to-surface responses use it identically. The body center remains the center of mass and the reference for collision, inertia, water damage, and displaced-volume air/water occupancy. In other words, the support point answers “where does this chassis meet or follow a surface?”, while the body answers “where is its physical volume?”. A visual rig, locomotion type, or named unit may not select a different origin or force law.

Presentation, motion control, navigation, hazards, and physical body properties remain separate contracts. The visual locomotion type chooses a rig; it never grants route permissions or changes a force law. This leaves one rigid body acted on by gravity, contact, medium resistance, surface-following force, and direct actuators.

Discrete gameplay still enters through physical effects

Commands, economy, construction, fog, build queues, and ownership are intentionally discrete systems. They do not need fake physics. But when those systems touch the battlefield, their visible result should enter the world as bodies, forces, energy, mass, constraints, or collisions. A factory can make a unit shell discretely; once it exists, gravity, terrain, collision, and force response should own its motion.

Scale Target

The design target is thousands of active units in a browser, with a path toward larger battle scenes. That target changes the default answer to every implementation question. Expensive correctness that works for 200 units but collapses at 5,000 units is not correct for this project.

Hot paths are data-oriented

  • Prefer stable IDs, packed numeric fields, typed arrays, and struct-of-arrays storage for dense simulation data.
  • Batch numeric work into WASM kernels when it can run over typed arrays without heavy object marshalling.
  • Keep TypeScript as orchestration, UI, temporary renderer integration, networking glue, and thin browser API plumbing. Gameplay control flow should move to Rust/WASM whenever it can do so without paying more boundary cost than it saves.
  • Pool snapshot DTOs, event objects, scratch arrays, and temporary buffers.
  • Do not allocate in per-unit, per-projectile, per-turret, per-cell, or per-frame loops unless the allocation is proven irrelevant.

Spatial structure beats broad scans

Targeting, collision, capture, fog, projectile queries, and selection should use spatial indices, dirty sets, visibility masks, and area-of-interest bounds. Full-world scans are acceptable for bootstrapping, debugging, and full-state presentation snapshots. They are not the normal steady state for gameplay ticks.

Clean structure comes before visual shortcuts

There are two separate concerns: server simulation authority and client presentation. Server simulation, snapshots, and adjacent-tick presentation must keep explicit ownership and stable cadence. Client rendering should be organized around clear data flow, predictable batches, and readable assets before adding extra representation modes.

Browser Performance Rules

Browser performance is not an afterthought. The browser is the platform. Code should be written as if V8, SpiderMonkey, WebKit, WebAssembly, WebGL, garbage collection, and WebRTC buffering are part of the game engine.

  • Use plain counted loops in hot paths. Avoid map, filter, Object.entries, spread copies, and iterator churn inside tick loops.
  • Reuse arrays by setting length = 0. Grow buffers on demand and avoid shrinking steady-state buffers.
  • Use bit flags and append-only numeric wire enums for snapshot fields and blueprint IDs.
  • Serialize snapshots as compact binary payloads. Do not rely on deep JSON object trees for high-frequency state.
  • Separate debug overlays from gameplay state and throttle them aggressively.
  • Measure TPS, CPU budget, render time, presentation-preparation time, snapshot rate, and backpressure continuously.
  • Prefer instancing, shared geometry, shared materials, spatial grouping, and GPU-friendly batches over per-unit scene graph complexity.

Performance bottlenecks are measured by layer

Performance debugging must separate simulation math, snapshot work, presentation preparation, render-list preparation, WebGL submission, and real GPU time before naming a bottleneck. A single “current TPS / ideal TPS” or “current FPS / ideal FPS” number is a symptom, not a diagnosis. The canonical diagnostic path is the performance bottleneck harness: npm run performance:bottleneck, implemented by scripts/performanceBottleneckHarness.mjs and src/game/perf/PerformanceBottleneckHarness.ts.

The harness runs the same battle shape through three deliberately different loads. Sim only advances ServerSimulationCore.stepFixedTick() without renderer or snapshots, giving the fixed-step simulation headroom. Sim + snapshot + client apply adds presentation snapshot emission, wire encode/decode, and ClientViewState.applyNetworkState(), which catches serialization and snapshot-apply costs that otherwise get blamed on rendering. Full stack runs the local server, adjacent-tick presentation, Three renderer, WebGL frame profiler, GPU timer, draw-call counters, triangle counts, buffer upload counters, long-task tracking, and snapshot size tracking in Chromium.

  • If sim-only p95 approaches the fixed-step budget, optimize simulation systems first: targeting, physics, pathing, fog, projectile stepping, or broadphase work.
  • If sim-only has headroom but sim + snapshot is expensive, the bottleneck is snapshot construction, visibility filtering, wire encoding/decoding, or client snapshot apply.
  • If GPU time approaches the frame budget while sim and snapshot have headroom, reduce draw pressure, fill pressure, shader cost, or render-target resolution.
  • If GPU time is low but full-stack frame time is high, inspect JavaScript render preparation, presentation sampling, HUD work, buffer uploads, garbage collection, and long tasks.
  • Use heavier harness runs with explicit caps and viewport sizes before accepting a scale claim, for example npm run performance:bottleneck -- --unit-cap=1024 --seconds=10 --map-cells=17 --width=1920 --height=1080.

TypeScript Coordinates, WASM Computes

The absolute performance ceiling for browser 3D is set by how little JavaScript runs in the per-frame hot path. TypeScript stays in the project because the browser’s native dialect is JS — boot, asset loading, input, UI, networking glue, calling into WASM — but it should never be the layer that integrates physics, walks per-unit update loops, builds render lists for thousands of objects, or carries large serialization work. Those belong in WebAssembly, compiled from Rust, running over typed linear memory with SIMD-friendly, struct-of-arrays layouts. The renderer that consumes the engine’s output should be data-oriented regardless of backend: it may draw through Three.js, raw WebGL2, or raw WebGPU, but high-count visuals must flow through owned typed buffers, explicit update ranges, instancing, and custom shader code instead of one draw call or one object graph per thing.

This is the same commitment that Languages and Frameworks makes for language choice and Config Is Data, Not Code makes for content authoring, expressed as a runtime architecture: the layers are stacked so that hot data crosses the JS/WASM boundary as rarely as possible, and the JS side never owns the inner loop. The end-state shape is a TypeScript shell wrapped around a Rust + WASM simulation that talks to a data-oriented renderer through stable render packets and GPU-resident buffers, with Web Workers and SharedArrayBuffer separating cadences where independent stepping or true cross-thread shared memory pays for itself.

Layer responsibilities

  • TypeScript shell — application boot, asset loading, canvas creation, renderer initialization, input collection, UI / menus / dev tools, WebSocket and WebRTC setup, and the bridge that calls into WASM. This layer coordinates; it does not compute.
  • WebAssembly engine (Rust) — ECS, physics, collision, pathfinding, visibility and fog, animation state, projectile simulation, spatial queries, culling, and render-packet generation. Everything that runs every tick or every unit lives here.
  • Renderer backend — currently allowed to use Three.js, raw WebGL2, or raw WebGPU. The backend owns GPU buffers, shader programs, instanced rendering, post-processing, and optional compute work; the architectural requirement is explicit data flow and batch control, not a specific library ban.
  • Web Workers + SharedArrayBuffer — when simulation and render need to step on independent cadences, or when a kernel can be parallelized across cores against shared linear memory without copying.

What TypeScript must never own in hot paths

Each item below is a per-unit, per-projectile, or per-frame loop that compounds at scale. Running any of them from JavaScript at thousands of units gives up the performance ceiling, regardless of how careful the TypeScript is.

  • Per-unit update loops.
  • Physics integration and collision detection.
  • Projectile simulation and spatial partitioning.
  • Pathfinding and fog-of-war calculation.
  • Animation blending for thousands of units.
  • Render-list generation for thousands of objects.
  • Large serialization loops and large per-frame allocations.

What TypeScript should keep doing

  • Bootstrapping, developer tools, debug overlays.
  • Settings, lobby, and the Vue / UI layer.
  • Asset loading and input event collection.
  • Renderer initialization, asset upload, shader/pipeline assembly, and boundary glue.
  • WebSocket / WebRTC setup and the network glue.
  • Calling exported WASM functions and marshalling the few values that genuinely need to cross the boundary.

The slow architecture vs the fast one

The slow browser game architecture is the one most browser code drifts into: thousands of JS objects, each carrying methods, each updated every frame, each allocating temporaries, each issuing its own draw call. That shape pays the cost of language overhead, garbage collection, scene-graph traversal, and one-draw-per-thing at every layer simultaneously.

The fast architecture is the inversion: flat typed memory, batched updates, almost no allocations, very few crossings of the JS/WASM boundary, large GPU buffers, instanced rendering, compute shaders where the work parallelizes, and as few draw calls as the scene can be expressed in. The rule of thumb is: if you can make the loop run over a slab of bytes instead of a list of objects, you should — and that loop almost certainly belongs in WASM or on the GPU, not in TypeScript.

Languages and Frameworks

Peak performance wins over framework convenience. For simulation and rendering, the default choice should be the fastest browser-viable language and API we can own directly. Frameworks are allowed only when they do not sit inside hot loops and do not prevent us from controlling memory layout, batching, scheduling, serialization, GPU buffers, or shader code.

Simulation language

  • Use Rust compiled to WebAssembly for dense numeric simulation kernels.
  • Move physics, projectile stepping, collision kernels, pathfinding kernels, terrain sampling, targeting batches, visibility packing, and snapshot encoding kernels toward WASM when the data can be batched.
  • Use struct-of-arrays storage in WASM linear memory for bodies, projectiles, turrets, spatial indices, and other high-count state.
  • Keep TypeScript as orchestration: UI, commands, networking glue, scene lifecycle, and code that would pay too much JS/WASM boundary cost. Configuration and blueprints are data, not TypeScript — see Config Is Data, Not Code.
  • Do not use a general-purpose JavaScript physics engine, ECS framework, pathfinding framework, or game framework in the local server simulation hot path.

Rendering language and API

  • Use GPU-native code for the expensive work: custom GLSL for WebGL2 or WGSL for WebGPU.
  • Three.js is an allowed renderer backend. Use it when it provides useful camera, scene, geometry, material, or asset-loading leverage without taking ownership away from our high-count buffers, culling, shader code, update ranges, and draw budgets.
  • Prefer raw WebGPU or raw WebGL2 only for renderer paths where Three.js overhead measurably blocks scale or prevents the buffer/shader contract we need.
  • Vue is UI only. Vue must not own simulation cadence, render-loop state, per-unit updates, or per-frame battlefield data.
  • Do not introduce rendering frameworks that hide draw-call count, buffer ownership, material compilation, culling, or shader control from us.

Owned by default

The preferred implementation is owned code in Rust/WASM, TypeScript, and shader code, with libraries acting as boundaries or backends rather than owners of the game’s hot behavior. If a library saves time but costs measurable simulation or rendering throughput, that specific path should be rebuilt around owned buffers, owned shaders, and explicit batching. The end-state engine should be transparent enough that we know where every per-frame allocation, buffer upload, kernel call, draw call, and branch-heavy world scan comes from. When a scaffolded path is replaced by an owned one, the scaffolding leaves the tree in the same change — see Delete The Old Path.

Rendering Philosophy

The renderer should make huge battles legible without forcing the simulation to become fake. Units should have consistent turrets, legs, treads, chassis tilt, beams, labels, decals, and effects because those are the shapes players use to understand the fight. The renderer should organize those shapes into clean render queues, shared resources, and predictable spatial groups before adding new rendering modes.

Rendering should never ask the authoritative sim to send more data just because a visual is expensive. If a visual cannot be supported at scale, simplify the visual contract or the renderer's structure first. The sim remains physical; rendering stays downstream of that physical truth.

GPU boundary precision: the Windows/NVIDIA world-box shimmer was not a duplicate terrain plane. South and east fragments lie exactly at the positive map limits, and perspective interpolation could move them a few ULPs across exact shader bounds while the camera moved, alternately applying fog, BUILD, or HIER presentation. Boundary sampling now uses a small guard band with clamped coordinates, and top-surface overlays explicitly reject vertical walls. Treat exact interpolated world-boundary comparisons as unstable.

Fog and contacts share coverage; ground shadows use real geometry

Above-water full sight, underwater full sight, above-water contacts, and underwater contacts are map-space knowledge regions. The client rasterizes every visible region into one viewport-local GPU render target in one instanced, per-channel maximum-blended draw. Attachment zero carries above-water full sight in red, above-water contacts in green, underwater full sight in blue, and underwater contacts in alpha. Terrain selects the full/contact pair matching each fragment’s medium and takes the darker applicable shade; environment props consume the same fog/contact attachment. Ground shadows are not knowledge coverage and never enter this texture. Authoritative visibility and recipient filtering remain unchanged.

  • Radar/sonar-only terrain uses the authored lighter darkness; fully unseen terrain uses the authored darker darkness and is completely grayscale.
  • Overlapping knowledge regions combine by per-channel maximum, so fog sources do not accumulate into unintended black patches.
  • Full-sight boundaries use one smoothstep spanning 64 world units inside and 64 world units outside the authored boundary (128 world units total), so short local-sight circles retain a legible solid center. Radar and sonar contacts retain the broader historical falloff of 192 world units inside and 192 world units outside (384 world units total). Both softness values are world-authored and do not change with zoom; the viewport-scaled supersampled coverage target preserves sampling quality at every camera distance.
  • The coverage target follows the visible camera footprint and supersamples the renderer's physical viewport up to the authored GPU texture cap. This keeps zoomed-in boundary detail at every camera distance without allocating a high-resolution full-map texture.
  • Solid lit triangles from units, buildings, articulated locomotion parts, and environment objects cast one directional sun depth map onto terrain. The result follows the actual rendered silhouette and pose; a hitbox circle, footprint ellipse, or stretched coverage stamp is never an acceptable stand-in. Additive effects, debug geometry, water, and invisible rig helpers do not cast.
  • The orthographic sun frustum follows the visible battle, expands in quantized steps, and snaps its focus to shadow texels so camera pans do not make outlines swim. The CLIENT SHADOWS toggle disables the directional depth pass rather than swapping in an approximation.
  • The retired coverage-ellipse shadow path stays disabled. There is no standalone contact-shadow mesh and no CPU-stamped fog bitmap.
  • The canonical client lighting defaults are ENV 150, AMB 1500, SUN 1500, SKY 1500, EXPO 15 in both battle modes. Every light/exposure bar shares the same logarithmic ladder: 0, 15, 150, 1500, 5000, and 15000 percent. The four decade values remain exact powers of ten; 5000 is the deliberate finer tuning stop between 1500 and 15000.

One Shared Entity Detail Ladder

Entity detail is a single presentation contract, not a collection of subsystem-specific quality switches. The CLIENT LOD control exposes exactly three authored geometry levels: HIGH, MED, and LOW, plus the MIN strategic-glyph floor. In AUTO, projected screen coverage chooses between those same presentations. AUTO never invents an in-between mesh, a plasma-only rung, or a separate distance cutoff for emissions, HUD, or animation.

  • HIGH is the close rung: the complete authored visual and its high geometry tier.
  • MED is the middle rung: the same authored assembly at its medium geometry and feature budget.
  • LOW is the far rung: the same authored assembly at its low geometry and feature budget. LOW is still real geometry; it is not an implicit removal rule, and it is deliberately the widest band of the three. An entity leaves LOW only when it has become too small on screen to be worth rendering at all — a handful of pixels across — not merely when it is far away.
  • MIN is the entity-geometry floor: once AUTO takes an entity below the glyph threshold, its strategic collision-shape glyph fades in over the still-opaque LOW model and then replaces it. MIN removes unreadable entity and vegetation geometry, not gameplay events.

This ladder applies to every visual part of an entity together: chassis/body, every mounted turret and barrel, shield panels and shield emitters, construction and resource-pylon assemblies, locomotion rigs and their animation, projectiles, beams, trails, smoke, sprays, impacts, debris, health and name presentation, and static resource/environment visuals. A part may be intentionally absent at a named rung, but it may not use a private fourth mesh budget or a different AUTO threshold system.

Explosions are never removed. At MIN, hit, projectile-expiry, and death events retain the LOW explosion pattern: one large representative from each motion band. Minimum detail reduces their chunk count; it never makes a detonation disappear.

AUTO’s choice is a pure function of projected size: the same entity at the same distance in the same camera always resolves to the same level, with no latch, no per-entity memory and no hysteresis band. An earlier design carried a deadband to stop an entity parked exactly on a threshold from rebuilding every frame; it is gone, because unit motion in this game is continuously smoothed and a boundary is crossed cleanly rather than jittered across. Statelessness is worth more than the deadband was: a level that depends on where an entity was is a level that differs between two clients watching the same battle, and it is one more thing to get wrong on a camera cut. That math is only a selector for HIGH/MED/LOW. Rebuild budgets may delay a swap by a frame; they do not create a fourth quality result. The definitive tuning and feature assignments live in lod.json; renderers consume the resolved rung rather than reinterpreting camera distance themselves.

A strategic glyph never shrinks below its flip size

Once an entity has become its glyph, the glyph stops shrinking. It is drawn at whatever screen size it had at the MIN threshold and holds that size no matter how far the camera pulls back, so a strategic zoom produces a readable constellation of markers rather than a dust of sub-pixel dots that dissolves into the terrain. This is the one place the renderer deliberately breaks perspective, and it is the whole point of the glyph: past the flip it is no longer a picture of a unit, it is a symbol that says a unit is there, and a symbol you cannot see does not say anything. Position stays exact; only the size stops tracking distance. Entities still occlude and depth-sort normally, because the glyph keeps writing the depth of the sphere it stands for.

Four colors on every entity, always

Every entity carries all four of these somewhere in its presentation: white, its team color, its player color, and black. Not one of them is decoration.

  • White and black are the contrast pair. A palette of team hues alone is legible over grass and illegible over bright water, snow, or a lit explosion — whichever way the backdrop goes, one of white or black is still separating the entity from it. Black additionally does the work of an outline: it is what keeps two adjacent units from melting into one silhouette.
  • Team color answers the only question that matters in a fight — friend or enemy — and it must be readable at the exact moment the entity is smallest, which is why it is never the outermost or the innermost band.
  • Player color answers who specifically, which matters in team games for reading an ally’s army apart from your own, and matters immediately after the battle when a player wants to find their own units.

An entity that shows all four is legible against any backdrop the map can put behind it and sorts into friend, ally, and enemy without the player having to zoom to check. An entity missing one of them is readable right up until the one situation that color was there for.

Strategic glyphs carry the four colors in a fixed order

The LOD:MIN glyph is the smallest an entity ever gets and therefore the strictest test of the rule above, so its layout is fixed rather than per-shape. Every glyph, for every entity type, is drawn as concentric bands of the same silhouette, from the middle outward: a small white core, then the team color, then the player color, then a black outline. The shape itself — circle, diamond, triangle, square, cross — carries the entity kind; the bands carry the identity, and they carry it identically no matter which shape is underneath.

The order is deliberate. Black is outermost because that is where the backdrop is, and an outline only works at the boundary. White is innermost because the core is the part no neighbouring glyph can overlap, so the guaranteed-contrast color is spent where it is guaranteed to be seen. Team sits inside player because friend-or-enemy must survive further into the distance than who-specifically: as a glyph approaches its minimum size the outer bands are what thin out first, and the ordering decides which question stops being answerable first. Widths are authored as fractions of the glyph radius, so every band scales together and none of them can vanish at the floor size.

Those bands are HUD identity, not lit world surfaces. Their white, team, player, and black values are authored display colors and bypass environment light, ambient light, sun, and exposure exactly like waypoint and selection overlays. Lighting controls may change the model beneath a transition glyph; they must never dim or tint the strategic symbol itself.

Coverage is measured on the collision volume

The size that gets projected is the entity’s collision volume — the COL entry of the shared volume model, the same sphere or box physics, picking and the volume overlays already agree on — never a visual mesh extent, a render bounding box, or a per-blueprint LOD radius authored on the side. Two reasons, and both are structural rather than aesthetic. It is the only size in the entity that is already authoritative and already correct: a visual estimate is a second source of truth that drifts every time a model is re-authored, and drift there silently retunes every LOD threshold in the game. And it is the size the strategic glyph is drawn at, because the glyph is the collision shape; measuring the flip on one radius while drawing the marker at another makes the icon pop to a different size than the model it replaced. One volume decides when detail sheds and how big the thing that replaces it is.

Trail-dominated entities are the one exception, and it is a floor rather than a different source: projectiles and beams clamp the projected radius up to an authored minimum, because a shot’s visual salience is its trail and its beam length, which outrun any body volume it owns. The floor raises a too-small collision radius; it never replaces it with a visual measurement.

Coverage also belongs to the geometry that is actually on screen. A mounted part inherits its host's rung because it is drawn inside the host's silhouette and shrinks with it. A raised shield field does not: it is a world-scale force surface, routinely an order of magnitude wider than the chassis running it, so it measures its own barrier radius and resolves its own rung from that. It is a mounted attachment for placement and an independent object for coverage, and those are separate questions.

Consequently a field is never removed with its host's model. Removal is what the glyph rung does to a model that has become too small to read; it is not a statement about a barrier that still fills a quarter of the screen. If a field is raised and its barrier is in view, it is drawn — at every rung, in every LOD mode, including MIN, and including the case where the host itself sits outside the render scope while its barrier overlaps it. A field whose host drew no chassis this frame anchors to the mount origin resolved from the host's authoritative transform, which is the same origin the simulation gives the gameplay barrier; it forgoes only chassis tilt and presentation bank, which are sub-pixel on a host too small to draw. Shield panels and emitter hardware are ordinary mounted parts and ride the host's rung normally — they are unit-scale, and there is nothing left to read once the unit is an icon.

Whose fields a client draws is a separate question from how far away they are, and it is answered the same way at every rung. A side always reads its own equipment: every field this player or an ally is running is drawn unconditionally, because an unpowered shield is meant to be a visible, reversible battlefield state the player can read off their own army. Reading an enemy's fields is what the Shield Detection Lab buys, on the same per-player mask that switches the targeting gate on. Neither a distance rung nor a manual LOD pin may ever subtract from that answer.

That mask is the material's, not the field renderer's. It asks whether this client may read the force material a side is running, so it covers both shapes: a mirror plate is drawn by the unit renderer rather than the field renderer — it is unit-scale hardware and rides the host's rung, per the paragraph above — and it still answers the same detection question a dome does. The panel shape escaping the mask once made the Loris the one piece of force material every enemy could see for free, which is worth naming because the failure is structural rather than local: every question asked about force material has to be asked of the material, and a second renderer for the second shape is exactly where that quietly stops happening.

What the mask hides is the plate, never the machinery. Support arms, grabbers, and emitter housings are ordinary mounted parts and stay drawn for anyone who can see the unit at all, so a mirror host you are not cleared to read looks precisely like one whose side has no Shield Generator switched on. That collision is deliberate: those two states are supposed to be indistinguishable from the outside, and drawing bare hardware in both is what makes them so. Force material never hides information, but it does not volunteer any either.

Camera Anchoring Is Two Orthogonal Axes

The camera is pure client presentation. It lives in the renderer, samples the client terrain mesh, and never crosses the wire — like locomotion visuals it is downstream of sim authority and feeds nothing back upstream. Because it is frontend, how it anchors and how it treats terrain are presentation choices, and presentation choices in this codebase are data, exhaustively enumerated, not policy hardcoded inside a picker.

Every configurable anchor-based camera operation answers two independent questions, and each question remains its own config axis. Collapsing them into a single mode enum is the drift this rule exists to prevent. The rotate gesture honors its authored (screen, terrain) anchor pair in every movement mode, including bar-spring: Alt-drag orbit and touch twist pivot rigidly around the resolved anchor point — cursor tumbles the world around the spot under the mouse, screen-center around the 3D point at the middle of the canvas — and the pivoted point stays pinned under that screen spot through the whole gesture. Only when the anchor ray resolves no surface does rotation fall back to turning in place around controller focus. The canonical bar-spring mode keeps BAR’s remaining fixed controller semantics: pan uses controller distance, zoom-in uses the cursor ray, and zoom-out uses the center ray; its unused generic pan anchor field stays in the shared config shape but does not replace those rules.

Axis one — where on the screen (anchorPointCameraScreen)

  • cursor — the spot directly under the mouse cursor.
  • screen-center — the spot at the middle of the canvas.

Axis two — which surface in the world (anchorPointCameraTerrain)

The screen spot defines a ray into the world; this axis decides which surface that ray resolves against.

  • plane-2d — the original flat ground plane (building-zero). Elevation is ignored; the anchor is the horizontal point only, exactly as a flat 2D camera would read it.
  • terrain-3d — the actual rendered terrain heightfield, including the real basin floor below water. The anchor follows hills and valleys exactly as drawn; water is never a camera surface.

In anchor-configurable movement modes the two axes are orthogonal: two screen choices times two terrain choices is four anchor behaviors, and all four remain reachable by setting the two configs. A configurable gesture’s anchor is fully described by its (screen, terrain) pair, and one shared resolver takes that pair and returns the point. Each gesture names its own pair, so a reversal or a tumble can anchor differently from a dolly.

Movement metric is separate from anchor choice

The anchor answers which world point a gesture pins or pivots around. The movement metric answers how much camera motion an input produces. These are separate config axes because a player may want cursor-on-terrain anchoring while still wanting each wheel tick or pan pixel to move a fixed world amount.

  • bar-spring — the canonical battle mode. It follows Recoil’s SpringController/BAR contract: wheel distance uses BAR’s asymmetric factor, pan derives pixel size from controller distance, scroll-in follows the cursor, and scroll-out remains centered. Whether the focus rides the terrain bed is the separate focusHeightMode axis below. BAR’s cardinal yaw lock remains available as the independent cardinalYawLockEnabled movement config.
  • anchor-distance-relative — an alternate terrain-aware feel: wheel and pinch zoom move by a fraction of the camera-to-anchor distance, and pan derives world-per-pixel from the depth grabbed by the cursor.
  • absolute-world — pan uses fixed world-units-per-pixel, orbit uses fixed radians-per-pixel, and zoom uses fixed signed world-unit distance steps, so terrain height and current camera-to-surface distance do not change the amount of movement.
  • absolute-world-momentum — absolute-world movement with velocity-sensitive gain. Center-click pan, zoom-in, zoom-out, alt-center-click orbit, and ctrl-center-click height-pan each own an explicit momentum block with enabled, minGain, maxGain, velocityForMaxGain, and curve. This is input acceleration, not post-release camera drift; the camera stops receiving movement when the gesture stops.

Cardinal yaw locking is deliberately disabled in the canonical camera config. Unlike BAR, Alt plus middle-mouse orbit passes through north, east, south, and west without a dead zone or sticky snap. The lock remains configurable for experiments without coupling it to the rest of bar-spring movement.

Render transition is a separate config choice. bar-spring-dampened remains available and applies Recoil’s velocity-carrying spring damper to the active eye, rotation, and FOV as they chase current controller state. The canonical ema mode provides the first-order transition used for camera motion. Transition scope is independently configurable. The canonical zoom-only scope matches BAR/Recoil’s responsiveness: pan, height-pan, rotation, and follow apply on the input event, lens changes are immediate, and the short transition is reserved for discrete zoom. all-movements remains an alternate mode that smooths every channel through one shared transition. A continuous movement in zoom-only during an unfinished zoom carries the rendered camera by the exact controller delta without discarding the zoom’s remaining transition. BAR wheel input itself does not gain movement from wheel-event velocity; the continuing motion after a wheel event is active-camera spring velocity, not accelerated scroll input. bar-discrete-event therefore maps every signed browser wheel event from a notched wheel to one BAR wheel unit regardless of OS-accelerated DOM magnitude. Events are classified per device: line/page delta modes and legacy wheel-delta multiples of 120 are notched clicks; every other pixel stream (trackpad two-finger scroll, Magic Mouse surface, free-spin wheels) keeps fractional conversion, because an inertial fling arrives as dozens of small events and must not become dozens of full notches. dom-continuous-delta retains raw fractional DOM-delta conversion for every event as an explicit option.

Middle mouse is hold-to-pan in the browser battle camera. BAR’s optional quick-click locked-scroll toggle is deliberately disabled here because browser pointer lock hides the cursor and makes a short drag indistinguishable from a stuck pan. Mouse-up, window blur, or a subsequent motion reporting no held middle button must terminate the gesture.

Ctrl plus middle-mouse drag is an intentional Budget Annihilation extension retained in every movement mode. Horizontal mouse motion pans left/right relative to camera yaw, while vertical mouse motion changes world height instead of moving forward/back. Alt takes precedence when both modifiers are held, preserving Alt plus middle-drag orbit. In terrain-follow mode, inward wheel zoom scales any accumulated focus-height offset back toward the terrain together with orbit distance; in constant-altitude mode the focus altitude band bounds height pan directly, so vertical pan cannot strand the camera above the map either way.

Wheel modifiers follow the same split as drag modifiers. Alt plus wheel tilts, sharing Alt’s camera-angle role with Alt-drag orbit. Ctrl plus wheel remains ordinary zoom because macOS delivers trackpad pinch as Ctrl+wheel, and pinch must zoom. BAR’s Alt-wheel movereset overview teleport is deliberately absent: Alt is this camera’s orbit modifier, and an instant overview jump while orbit-scrolling reads as the camera flying away on its own.

This movement metric is not terrain collision. Collision decides whether the rendered eye may clip through terrain. Anchoring decides which world point a gesture references. The movement metric decides whether input magnitude is relative to the anchor distance or an absolute world amount. In absolute zoom, anchors set the ray direction but not the step length; using the camera-to-anchor distance as the step length would let terrain geometry amplify a free camera.

Minimap camera and PIP are replaced by 3D overview controls

BAR-style minimap camera switching and picture-in-picture are not the canonical Budget Annihilation camera model. The supported 3D-first replacement is: minimap click-to-center for fast relocation, camera anchors for saved tactical views, selected-unit follow for unit-centric tracking, and the map overview switch for whole-map inspection. Those controls preserve one primary 3D camera and avoid a second live viewport that would duplicate terrain, fog, water, and high-count entity rendering work. If a later spectator or replay surface needs secondary views, it should be designed as a mode-specific tool, not as the default battle camera contract.

Focus altitude is a config axis; the canonical mode is constant altitude

Bar-spring movement resolves its focus height through the focusHeightMode movement config. terrain-follow preserves the BAR SpringController contract: the focus is glued to the terrain bed plus a persistent elevation offset, so panning across hills raises and lowers the camera with the ground. constant-altitude is the canonical Budget Annihilation mode: pan, orbit, and follow never change the focus height, and altitude changes come only from explicit Ctrl-drag height pan, zoom translation toward the anchor, and the focus floor that keeps the focus out of the bed beneath it. Terrain clearance is not on that list: it moves the eye for one frame and leaves the focus alone. On this game’s terrain relief, riding the bed is a rollercoaster; constant altitude treats terrain as a floor, never as a rail the camera rides.

In constant-altitude mode wheel zoom is the anchor-scaling law: eye and focus contract toward (or expand away from) the resolved 3D anchor by BAR’s asymmetric wheel factor, so distance still scales by 0.825/1.175 per notch, cursor zoom-in descends into a valley because the anchor is lower, and screen-center zoom-out ascends symmetrically. When the anchor ray finds no terrain, the factor applies around the focus itself — a plain center zoom — never around a fallback plane at pathological depth.

Zoom anchors are depth-filtered and travel-clamped

A cursor anchor is a raycast depth, and that depth is discontinuous at terrain silhouettes: the pixel on a peak and the pixel beside it can differ by two orders of magnitude. Two invariants keep relative zoom stable on extreme relief. First, the anchor depth is reduced across the configured screen-space sample neighborhood (zoom.distanceSampling, canonically min-aggregated), so a peak near the cursor wins over the valley behind it. Second, one wheel tick’s eye travel is hard-clamped to zoom.travelClampFraction of the current controller distance — the anchor point is never moved, but no anchor, however deep, can teleport the camera.

The battle camera floors on the terrain bed, and the floor is stateless

The eye keeps its configured clearance above the terrain bed alone — under water that is the basin floor, so the camera submerges freely; the water surface is never a camera surface and never a camera floor. That lift resolves against the frame being drawn and is never written back into focus, distance, yaw, or pitch: the same controller state and the same heightfield always produce the same frame, and the eye falls back to the pose the last gesture described the moment the ground drops away. Nothing is remembered, so there is nothing to recover from either.

Committing the lift was tried and rejected. A clearance that writes back is a clearance that fights the player: brushing a hill ratcheted the focus altitude upward every frame the eye was under it, and because a zoom-in step lowers the eye toward its anchor, the commit handed back exactly what the step gave — the gesture read as dead, and the camera was left stranded high after a pan that merely grazed a ridge. The rule that falls out of it is general: terrain may decide where a frame is drawn from, never what the camera is.

Nothing else holds the eye off the ground either. There is no fixed closest-orbit rail in the canonical config (constraints.zoomInLimit is none); the distance closes all the way and terrain clearance alone decides how near the ground the view can get.

Camera state is validated at one commit point

Every gesture and driver commits through a single constraint step that replaces non-finite fields loudly, clamps the focus into the padded map and its altitude band — never below the bed beneath it, never further above that bed than the zoom-out distance rail — and keeps distance and pitch on their rails. An impossible camera pose is unrepresentable rather than recovered-from. The optional lost-map recovery EMA remains a config switch (lostTerrainRecovery, canonically disabled) and cancels the moment the player touches any camera input, so the fixer can never fight the player’s hands.

Locomotion Visuals Are Frontend

Authority owns chassis position. The renderer owns where the parts of the chassis appear in the world. The sim publishes one point — the unit’s body center, at its authoritative altitude. From there the rig is responsible for putting every wheel, cleat, foot, or fan exactly where the renderer says it should be, and that “should be” must respect terrain as a hard floor.

This is the right boundary for three reasons. One: the renderer already has the terrain heightmap loaded for shading and contact shadows; sampling it under a wheel or foot is cheap. Two: per-part terrain queries scale linearly with visible units, not authoritative units — off-screen units skip the work for free. Three: it removes a whole class of net-bug, because a chassis can never wedge a wheel under a hill that exists only on the client’s mesh. The visual rig is downstream of sim authority, never upstream.

The locomotion rigs

Locomotion discriminators use singular RTS chassis-role names, not the names of their animation primitives. The canonical schema is rover, tank, amphibious-tank, crawler, bot, amphibian, drone, plane, submarine, and aerosub. Wheels, treads, legs, flippers, fans, and wings remain ordinary component names inside those rigs; they are not locomotion-family identifiers or preset names.

  • Rover — a wheeled chassis driven through discrete rigid contact patches at fixed body-local positions. Visually: cylindrical tires, each spinning around its own axle, rolling phase derived from how far that local contact point traveled in the world this frame. Each tire owes the ground a contact patch — the bottom of the cylinder is the contract.
  • Tank — two infinite tread belts that share chassis velocity but read it as continuous tangential motion. Visually: scrolling cleat rails along the belt path; the belt itself never moves relative to the chassis. The contract is the entire underside of each ribbon sitting on terrain.
  • Amphibious tank — the tank rig paired with deliberate water propulsion and water-safe navigation. Its tread presentation remains terrain-contact machinery; medium physics, not a renderer-side mode switch, decides when water carries it.
  • Crawler — discrete step events: a foot plants, the chassis advances past it, the foot lifts and swings to a new plant. IK solves hip→knee→foot for the rendered pose. The contract is per-foot, not per-chassis — feet must touch terrain on plant and swing through air during transit. The authored hasFeet flag controls whether those endpoints also receive separate rendered foot pieces and terrain-aligned foot orientation work. A footless crawler rig retains its gait/IK endpoints but performs no foot- orientation calculations and allocates or draws no foot geometry.
  • Bot — one authored biped cycle shared by both legs, with the second leg exactly half a cycle behind the first. The shoes are ordinary lower-body animation pieces: they face with the hips, remain flat through stance, and use a small toe/heel pitch through recovery. They do not own terrain footprints or slope-solving state.
  • Amphibian — four rigid, single-hinge hydrofoils with no knee or separate foot. On land they use a diagonal, leg-like support gait; as the physical submerged fraction rises they continuously unfold into wing-like paddles. The visual transition reads the same body-in-water fraction as locomotion physics, while maximum propulsive force remains wholly owned by the unit blueprint.
  • Drone — a chassis that never touches anything; a duct array balances gravity with downward thrust against the air column underneath. Visually: spinning fans mounted above the chassis, downward smoke columns, chassis riding a target altitude. The overhead fan translation is frontend presentation only: authored locomotion mounts and authoritative lift forces stay in their original body-local locations. The contract is anti-contact: the gap is the feature, and that gap must be measurable per frame so smoke length and altitude shading look right.
  • Plane — a fixed-wing body supported and propelled in air. Wings, jets, and exhaust communicate the force profile but do not own it; their pose is downstream of the canonical full-body orientation and velocity.
  • Submarine — an underwater body propelled through water, with fins, jets, and body pose downstream of the same canonical root and medium-force profile.
  • Aerosub — one winged body intentionally capable of powered travel in both air and water. It is not a plane that swaps to a second simulation when submerged; the shared occupancy-weighted force profile continuously blends its two authored media.

One rendered root pose owns every attachment

A rig must consume the exact batched root position and quaternion used to draw its chassis. It must not independently rebuild yaw, terrain tilt, or interpolation from mutable entity state. Every attachment also has a finite mechanical envelope: wheels and tread rails have bounded suspension travel, and world-space legs have bounded reach. A teleport, recycled slot, or other root discontinuity resets history rather than integrating the gap. These are attachment invariants, not tuning knobs; no terrain sample or stale planted point may pull locomotion geometry arbitrarily far from its body.

Always animate; terrain only clamps position

Every rig integrates the same four canonical visual state channels every frame — the same channels the client-prediction layer uses for entity motion, named the same way and reasoned about the same way:

  • Movement position — where the part sits in chassis-local Y (wheel lift, tread side lift). EMA-converges toward the floor-clamp target every frame.
  • Movement velocity — rate of change of movement position; integrated implicitly from the position EMA.
  • Rotation position — rolling angle (wheel rotation around its axle) or belt phase (where cleats sit on the loop). Integrated from rotation velocity.
  • Rotation velocity — angular velocity for wheels, linear belt velocity for treads. EMA-couples toward the body-motion-derived target every frame.

The rig does not ask "is this part touching ground?" The velocity channels always couple to body motion; the position channels always couple to the floor clamp. A tire over a dip spins at the body-motion rate and floats slightly above terrain (target lift = 0). A tire cresting a hill spins at the same rate and rides up the surface (target lift > 0). When the body stops moving, the velocity channels EMA toward zero on the same tau they always use — cleats coast to rest over a beat, wheels spin down naturally. Simpler than switching coupling regimes, and visually indistinguishable in normal play.

Per-part position, not per-chassis

Floor clamping is per primitive. A four-wheeled vehicle straddling a crest has two wheels rising over the terrain and two floating in air over the dip; the rig clamps each tire independently. Treads sample three points along each side ribbon and lift the side to clear the max. Crawlers sample under each foot. A drone doesn't clamp parts but does sample a per-frame clearance scalar for fan smoke and altitude shading. A bot uses its one lower-body ground baseline rather than querying terrain beneath each shoe. The rig knows what its primitives are; uniformity is in the shape of the contract, not in the bits.

Visual contact is sticky

The renderer must not reuse the physics ground-contact epsilon as the sole answer for locomotion animation. The sim epsilon is intentionally tiny because it gates spring, friction, sleep, thrust, and collision behavior. Visual rigs need a separate, frontend-only contact band with hysteresis: acquire ground when the chassis is near the terrain, keep the grounded pose while the body remains within a larger release band or while planted feet are still reachable, and only transition to airborne posing once the visual contradiction is unmistakable.

For crawlers, the stable unit of truth is the foot, not the chassis. A planted foot keeps its world position and its complete world orientation until a deliberate step swing begins. It does not twist within its support plane as the chassis, hip, knee, or lower segment moves around it; a shoe visibly turning while loaded against the ground is a contact violation. Brief chassis bob, snapshot drift, suspension state, or a one-frame miss in strict body contact must not reset the gait or re-seat feet at their rest points. When a legged unit really leaves the ground, feet move smoothly into an airborne pose; when it returns, each foot swings to a terrain plant instead of being initialized in place.

Crawler foot orientation is resolved from consecutive footprints

An arachnid-style crawler step knows both endpoints before the foot moves: the footprint it is leaving and the footprint it is approaching. Each endpoint owns a terrain support plane sampled once at that footprint. The moving foot interpolates from the previous footprint’s plane to the next footprint’s plane over the step’s linear progress, reaching the complete destination angle before touchdown. Landing only promotes the already-rendered destination pose; it never samples a surprise angle or creates a one-frame snap. No terrain-angle sampling during the planted interval may mutate either endpoint.

The foot is an independent world-space contact: its position and its complete orientation, including heading within the plane, are fixed for the entire planted interval. At lift-off the rig freezes the next footprint’s complete terrain-aligned orientation too, then shortest-path interpolates between the two complete orientations only while the foot is in transit. Neither the moving leg segments nor a turning chassis may rotate a planted foot.

Bot feet use an authored walk cycle, not terrain matching

A bot deliberately does not participate in the consecutive-footprint terrain solver. Beyond All Reason’s Commander establishes the useful RTS reference: its feet are model pieces driven through an authored walk animation, not independently planted world-space contacts. Our bot rig follows that readable, robust approach. Both shoes use the one coupled gait clock, always point forward in the hips frame, stay flat through the planted half, and smoothly pass through a restrained toe-down / neutral / toe-up / flat pitch sequence during recovery.

A bot shoe never samples terrain height or normal, predicts a next footprint, retains a footprint anchor or plane, interpolates ground slopes, or stores any per-foot contact state across a geometry-tier rebuild. Foot position comes from the authored stride and lift over the rig’s single local ground baseline. The authoritative root/support pose still handles the unit’s large-scale relationship to terrain; a small amount of shoe clipping or floating on uneven ground is an accepted RTS-scale tradeoff for coherent motion and substantially less fragile presentation code. This simplification does not change crawler behavior.

Each arachnid-style leg explicitly owns a planted, stepping, or free contact state. Its only grounded step envelope is a sphere derived from authored attachment and segment geometry: cast a ray from chassis center through the attachment, keep the maximum-extension point along that ray, place the sphere center on terrain at the authored originExtensionRatio between attachment and maximum extension, and size its radius from radiusLegLengthRatio times total segment length. Each leg has its own chopping sphere centered on terrain directly beneath that leg’s attachment point and sized from choppingSphere.radiusLegLengthRatio times total segment length; subtract it from that leg’s foot sphere so no planted foot may enter the chassis-side volume. A planted foot leaves this chopped envelope when it exits its foot sphere or enters its attachment-ground chopping sphere. The snap-ray origin lies along the outward axis at originBoundarySpanRatio between the chopping-sphere surface and the foot-sphere’s outer surface. Its step target comes from a horizontal ray cast from that point in that point’s own frame-to-frame world velocity direction, so chassis translation and rotation both influence the target, stopping at the first intersection with either boundary and resampling terrain height there. With no planar velocity, the derived outward ray is the deterministic fallback. The reach clamp remains an emergency safeguard for rendered geometry, never a second step trigger or a way to drag a nominally planted endpoint with the chassis. Unsupported air legs tuck on ascent and extend for descent/touchdown. Unsupported water legs instead blend toward a damped, velocity-trailing pose, while legs close enough to the bed retain the ordinary planted gait on underwater ground.

Authored leftSide entries contain only an attachmentPoint. The shared segments, footSphere, choppingSphere, and snapRay objects live beside the array and govern every mirrored leg on the unit; the chopping-sphere radius is shared, while its terrain center is resolved per attachment.

Floor clamping and attachment reach are joint invariants

  • Within the part’s physical attachment envelope, the clamp is non-optional. Every rig writes renderedY = max(naturalY, terrainY + clearance) for every part it owns, then EMA-converges the part's movement-position channel toward that value.
  • If terrain support and mechanical reach cannot both be satisfied, mechanical reach wins: keep the part attached and expose the chassis/terrain contradiction rather than detaching a wheel, rail, or limb into space. The authoritative body is the system that must resolve the impossible pose.
  • Floating above terrain is acceptable; tunneling through it is not. When the sim chassis is over a dip, individual wheels are allowed to read as “slightly floating” rather than pretending to droop on suspension we do not have.
  • The clamp uses the same smoothed surface normal the chassis tilt consumes (updateUnitGroundNormal). One canonical value, no drift between “how the body leans” and “where the wheels sit.”
  • Hover gets a soft floor too: its above-body visual rest height is preserved, then the rendered rig group is clamped at least ε above terrain, so a bad snapshot can never park fans inside dirt. The authoritative chassis altitude is untouched — the renderer just refuses to draw a contradiction.

Nothing about locomotion visuals crosses the wire

Every input the rig needs — chassis transform, terrain heightmap, body velocity, surface normal — the client already has. Computing this on the server and shipping it would burn bandwidth on per-frame visual state that only matters within the next render call. Compute it locally, render it, throw it away. Putting any of it on the wire is what got us into the jump-state-on-the-wire mess in the first place. Networked suspension/contact fields may influence body presentation, but they must not be the authoritative source for whether a foot remains visually planted.

Airborne Banking Is Visual; Combat Mounts Stay Authoritative

Drone and plane units should look like they bank into their turns — the chassis rolls about its forward axis as lateral velocity builds, then unwinds when the unit straightens out. Banking is the strongest visual cue that an airborne unit is physically committed to a turn, and the renderer is the only place that needs to know about it. The authoritative sim continues to track yaw (and yaw alone) for drone/plane chassis; any extra presentation bank is derived from local body velocity at render time and never touches sim state, the wire, or combat math.

This is the same boundary as Locomotion Visuals Are Frontend: the sim publishes a chassis pose the renderer is allowed to enrich, and the rig owns every visual expression that doesn’t change targeting truth. Banking is the airborne analogue of wheel spin and tread phase — expressive on the screen, irrelevant to the simulation.

Why this is a hard rule and not a convenience

The sim’s turret-world-mount math uses the host’s full authoritative body quaternion (getTurretWorldMount). A visual-only bank is deliberately absent from that quaternion. If the renderer applied it to an off-axis weapon mount anyway, the visible turret center and authoritative shot origin would quietly diverge. The combat contract wins: a host with any turret off the body-forward roll axis does not receive presentation banking. Centerline-only aircraft may still bank because a pure roll leaves all their mount centers unchanged.

  • Airborne turret mounts may use all three authored axes; mobile fortress and carrier silhouettes are not forced into a centerline-only weapon layout.
  • The renderer checks the resolved runtime mounts. If any has mount.y !== 0 or mount.z !== 0, presentation bank is zero for that host.
  • Centerline-only aircraft retain banking because roll cannot move a point on the roll axis.
  • Ground-locomotion turrets keep the same freedom on all three axes; slope and full-body attitude already run through getTurretWorldMount.

What the sim writes, what the renderer composes

  • The sim keeps a torque-limited yaw servo on drone orientation. Its state transition is the exact fixed-tick solution of the critically damped rotational equation, not Euler integration, so a light chassis cannot enter a left/right limit cycle when nearly aligned. alwaysForward chassis (plane, aerosub) instead yaw by a constant-rate slew at the authored actuator.turnRateDegreesPerSecond — the circle turn. The rate is authored per preset and overridable per unit blueprint: the Albatros slews at a fraction of the Eagle’s rate, giving the heavy airframe a much wider turning circle at a lower speed. A damped spring’s turn rate collapses with the remaining error, so a plane chasing a moving bearing eases off as it closes and never actually aligns; the slew turns at the full rate until aligned, then snaps exactly onto the bearing. Either way, entity.unit.orientation still ends each airborne tick as a quaternion equivalent to setQuatFromYaw(yaw); target pitch and target roll remain pinned to zero.
  • The renderer derives a body-lateral acceleration — the centripetal term v_forward · ω_z — from unit.velocityX/Y projected through the current yaw and unit.angularVelocity3.z (the yaw rate, on the wire and predicted at render rate). It scales that into a target bank angle, EMA-smooths it per frame, and composes the roll about the body-forward axis on top of the chassis yaw quat. A velocity-derived bank would decay to flat mid-turn because the yaw spring continuously aligns body forward with the thrust direction, collapsing body-lateral velocity; the centripetal signal stays high for as long as the unit is actually turning.
  • The visual bank is bounded (a hard clamp keeps the chassis from doing barrel rolls under collision spikes) and decays toward zero whenever centripetal acceleration is small. It intentionally uses local render-side smoothing rather than the rotation-position channel. No sim state ever sees the value.
  • If a future visual wants pitch (nose-down when accelerating, nose-up when braking), it lives in the same place: derived from velocity at render time, never written back to the sim.

Combat Turrets Share One Aim; Beams Are Tuned Super-Snappy

Every combat turret renders a barrel and points it from the same authoritative turret aim (weapon.rotation / weapon.pitch) that travels on the wire and corrects through the rotation position channel like everything else. Guns, cannons, mortars, gatlings, rockets, the disruptor, and beam-family turrets all consume the shared target acquisition, aim solver, critically damped yaw/pitch servo, aim-error firing gate, snapshot, interpolation, and renderer pose path. An emission family does not get a private targeting path.

A building turret has no rest angle

A rest angle is a chassis idea: it says where a weapon sits relative to a body that has a forward, so a unit that stops fighting stows its gun over its own nose. A structure has no forward. Its turrets therefore never restore — no rest yaw, no rest pitch, no restore delay to wait out. When a defensive tower loses its target it stays exactly where the engagement left it, still covering the bearing the enemy came from, which is also the bearing the next one is most likely to come from. Unit turrets keep restoring exactly as they do today; this rule is only about static hosts.

That makes the first bearing the only one anything ever chooses for a structure, so it is chosen deliberately: a building’s turrets are aimed at the centre of the map the moment the site is placed — the direction the fighting comes from — rather than at whatever the blueprint’s authored zero happens to be. A turret with a limited traverse takes that bearing as far as its arc allows. The choice is derived from position, host rotation, and map size alone, so every peer computes it identically.

  • This applies to the turret’s own local yaw/pitch and to any rotating building piece it drives. Both are the same rule seen from two mechanisms; a piece that returned to the host’s facing while the turret held station would be a rest angle by another name.
  • Vertical launchers keep their pinned pose. They are not aiming, so there is nothing to hold.

Bot hosts expose authoritative piece sockets

A bot is not one rigid transform. Its upper body, shoulders, forearms, hands, and head mounts form a piece tree, and weapon geometry attached to that tree must use the tree’s current fixed-tick transform for gameplay as well as presentation. A botArm mount resolves its AimFrom pivot from the named hand plus the unit-blueprint socketOffset; a named head-piece mount resolves its authored pivot below the moving upper-body piece. The ordinary authored mount remains the rigid fallback for hosts with no piece attachment.

The bot contract requires one ordinary arm pair and permits a blueprint to add one upperArms pair. That second pair uses the same authoritative hand-socket and aiming path as the first; it is not Rex-specific renderer decoration. Each pair authors its own proportions, shoulder position, gait swing, and elbow bend direction, allowing Rex’s extra weapon arms to rise from the very top/outside of its shoulders and turn downward like antennae while its primary arms retain their conventional hang.

This follows BAR/Recoil’s separation of responsibilities. The turret owns targeting, yaw/pitch, cooldown, and firing. The host owns named transforms. BAR scripts express that split with AimFromWeapon (the aiming reference piece), AimWeapon (turn the host pieces), and QueryWeapon (the actual emission piece). This project expresses the same contract through an authoritative AimFrom pivot and one QueryWeapon socket per emission lane. Keeping turret and host as separate systems is deliberate; allowing either one to invent the other’s transform is forbidden.

The shared torso has one authoritative state row and many possible claimants. Weapon and QueryWork stations request a world yaw through an authored claim group and priority; equal priorities resolve by stable mount order. A fixed-tick bounded motor applies the bot blueprint’s maximum angular speed and acceleration, so a Human can turn briskly while a Commander and especially a Rex visibly carry more rotational inertia without a presentation-only spring. Current work intent and the preceding fixed sample’s committed weapon intent arbitrate the parent once per tick; weapon targeting then publishes the next parent sample while its child joint tracks inside the achieved parent frame. Each attached arm reads its own authoritative local yaw/pitch and never borrows the visual gait clock. Sibling stations remain independently articulated inside the moving parent.

  • The simulation resolves attached AimFrom pivots before targeting, then resolves them again after the turret servo and overwrites the targeting slab before firing. Targeting sees the start-of-tick piece pose; emission and snapshots see the final pose.
  • The waist servo angle and angular velocity are authoritative turret-host state, participate in snapshot dirtiness, and travel through the turret wire row. The renderer uses that pose, the same bot-arm geometry function, and the same torso-owner rule. It may interpolate authoritative rows, but it may not maintain a private torso spring or weapon-arm easing that changes a combat socket.
  • Every runtime turret materializes exactly emissionLaneCount QueryWeapon offsets. A unit mount may author emissionSockets explicitly in world units. Ordinary single-barrel projectiles use the barrel tip, rotating clusters share their fixed top firing station, and beam-family weapons use the broad base of their pilot-light cone at the AimFrom origin.
  • Projectile spawn, beam start, fire audio, pending post-physics launch finalization, and inherited launch velocity all query the selected lane. Sensors, target range, damage selection, and shields continue to use the AimFrom pivot because those systems address the mounted turret, not a projectile muzzle or beam origin.
  • The rendered barrel matrix publishes the matching QueryWeapon point for beam interpolation. For a beam this is the pilot-light base, so presentation may smooth between fixed ticks without pushing a live ray ahead to the cone tip.

Rocket turrets are multi-tube launchers

Rocket-family turrets use a role-readable multi-tube cluster (simpleMultiBarrel) with one stable QueryWeapon lane per tube. The slow and fast general-purpose launchers carry three broad tubes; the dedicated anti-air launcher carries six slimmer tubes and a rotating rack. Spin is an authored presentation option, not part of the authoritative socket pose. The Rex preserves those standard silhouettes: six-tube anti-air launchers are carried at the hands of its optional upper arm pair, while its three-tube vertical rockets remain on the moving backpack. They aim like any other shot turret, with the cluster tracking its target in yaw and pitch. A vertical launcher is the exception its own way: the sim pins its pose straight up while the launcher still follows its moving host piece. Because a rocket turret’s aim is a real visual, it rides the wire again — these are ordinary aiming turrets, no longer head-only.

Beam turrets use the shared servo at extreme finite stiffness

Beam-family turrets (turretBeam, turretBeamMini, turretBeamMega, turretBeamLong) use the ordinary damped turret servo with an extremely high but finite authored turn acceleration. At the fixed simulation cadence that makes them settle effectively within one tick while preserving the same state transition, aim-error calculation, and firing eligibility as every other turret. There is no instant-lock branch and no assignment that copies the target bearing directly into turret rotation.

A live beam starts from its selected QueryWeapon origin and takes that authoritative yaw/pitch pose as its nominal line. It does not construct a second clean direction from the locked target’s current center, and the renderer does not reconstruct turret orientation from the beam polyline. Once aligned, a ray still has no projectile travel time and therefore applies along its traced line immediately; what is removed is the ability to hit a target independently of where the shared turret servo is actually pointing.

Beam imprecision is authored, physical, and removed by Precision Targeting

Every beam ray authors one aimWiggle profile: a maximum world-space origin radius, a maximum angular direction error, and a fixed-tick period. Without a completed, switched-ON Precision Targeting Lab, the authoritative trace moves smoothly through deterministic random samples inside those bounds for the entire pulse. Both the start point and the travel vector move, so an inaccurate beam visibly and physically wanders off its clean barrel solution; damage, reflection, recoil, and the rendered polyline all consume that same perturbed trace. The turret servo itself remains clean.

Precision Targeting collapses both offsets to exactly zero. The four beam families do not share one generic error: some author restrained drift, while others are deliberately poor without the lab and exceptional with it. Balance and purchase value are judged from the average usefulness of those two live states — ordinary imprecise and powered precise — rather than treating the precision state as a free baseline. The samples are hashes of stable turret identity, launch tick, and fixed simulation tick, so every lockstep peer follows the same wander and no renderer or wall clock can influence a hit.

The beam cone is the beam pilot light and marks the nominal origin

The cone centered in a beam turret’s barrel assembly is its beam pilot light. It stays lit between beam shots, then hides for the entire time a live beam is being drawn. The two visuals are mutually exclusive: the live beam replaces the pilot light along the same centerline instead of appearing in front of it.

The pilot light marks the nominal beam origin: the broad base of the tapered cone at the turret’s authoritative AimFrom pivot. Beam QueryWeapon offsets therefore remain zero in turret-local space. The cone’s pointed tip is only the end of the idle visual; it is not a muzzle and must never push the live ray forward. With Precision Targeting active, simulation tracing and rendered beam interpolation use that base exactly. Without it, the ray’s authored origin wiggle moves around the base while the hidden pilot light remains the readable nominal center; the live line never gains an unrelated cone-tip offset.

Beam turrets are therefore ordinary full-barrel turrets rather than headOnly mounts. Their rotation, angular velocity, pitch, and pitch velocity use the normal turret presentation rows, and their tapered barrels use the normal turret pose pass. headOnly: true is reserved for bare utility mounts with no orientable barrel; those mounts may omit aim motion because there is no combat pose to present.

Beam barrels also use the roster’s ordinary sizing vocabulary. barrelLength is a protrusion fraction of the turret head radius, so Mini, Medium, Mega, and Long emitters scale with their own mounts instead of using host-specific world dimensions. Their base width is derived from the authored beam width through the same emission-to-barrel rule used by other weapons; beam turrets do not carry arbitrary thickness overrides. A geometry contract keeps every beam barrel visible at all detail tiers, no wider than its head, and longer from center to tip than its base is wide.

BAR Inspiration, Project Identity

Beyond All Reason is the comparison point for command ergonomics, readable large battles, queue-friendly controls, minimap interaction, and the feeling of commanding armies instead of individual pieces. This project should feel familiar to BAR players in its command vocabulary and battlefield expectations.

The project identity is different: the browser is a hard constraint, the network model is deterministic lockstep plus adjacent-tick presentation, and the world should be even more physically grounded. BAR is the gameplay fallback and ergonomics reference; this project owns its implementation, data contracts, and browser runtime.

One BAR behavior we deliberately imitate is the separation between player-visible command waypoints and private pathfinder output. In BAR, queued factory rallies, move/fight/patrol orders, and dragged waypoint markers are durable command intent; the Spring/Recoil engine expands active movement into path waypoints internally and repaths on a throttled cadence when progress or world state demands it. This project should keep that same conceptual boundary even though our pathfinder is owned by our Rust/WASM sim rather than by BAR's engine.

Commands require real systems

BAR command vocabulary is the fallback only when the command has an authoritative Budget Annihilation system behind it. A command-card button, hotkey, cursor, or preview is not allowed to exist as dead UI: the simulation, server authorization, snapshots, client feedback, and physical presentation must all have a coherent contract first.

Transports, capture, cloak/detection, manual launch, and unit-specific special-fire commands therefore appear only on entities whose authoritative mechanics and BAR-equivalent capability exist. Resurrection is the standing example of the rule’s other edge: the prototype deliberately has no wreck state — every death is an explosion and that is the end of the body — so Resurrect has no command surface anywhere (see Dormant capability is removal work, not a content prompt). Metal-extractor upgrades follow the same rule: a T1-to-T2 or area-upgrade command requires an authored upgraded extractor blueprint, resource/economy behavior, construction lifecycle, replacement rules, and render profile before the command is exposed. The prototype should prefer no button over a button that appears to promise unsupported BAR behavior.

The BAR command inventory is capability-gated

The parity inventory is the set of player-facing command descriptions supplied by BAR and its Recoil engine, not every internal command ID. Internal group/base commands and order-menu-hidden wait variants do not become buttons merely because the engine declares a numeric constant. The inventory is grouped by the capability that makes each order real:

  • Movement and queues: Move, Patrol, Fight, Stop, Wait, Guard, Repeat, Move State, and queue insertion/removal. Durable player waypoints remain separate from private pathfinder expansion.
  • Combat: Attack Unit, Attack Point (the map form of Recoil’s unit-or-map Attack), capability-authored Area Attack, Fire State, Trajectory, Set Target / Set Target No Ground / Cancel Target, D-Gun or other manual fire, and weapon stockpile/manual launch when an authored weapon actually provides it.
  • Builders: negative build commands, Repair, Reclaim, Capture, Area Mex, Builder Priority, and Morph/Upgrade. Area-capable commands may fan out into deterministic nearest-first entity orders while preserving queue modifiers. Resurrect is deliberately outside the inventory: with no wreck state in the game there is nothing to resurrect, and the command surface does not exist.
  • Factories: unit production, finite queue editing, Repeat, Wait, Stop Production, a produced-unit Move/Fight/Patrol/Guard command queue, Factory Guard, Move State, aircraft idle/land-at state, production quota, and Builder Priority where the factory supports it. The produced-unit command queue is not Factory Guard: Factory Guard is a persistent policy that assigns an otherwise-unordered eligible builder output to guard its producing factory.
  • Transports and host state: player-facing Load and Unload Unit/Area, ON/OFF, Cloak, and Self Destruct, each visible only when the selected host owns the corresponding system. Recoil’s internal/order-menu-hidden Load Onto descriptor is not a second button promise.
  • Conditional custom commands: carrier spawning, sell, blueprint placement, area ground attack, stockpile, and similar BAR gadget commands are roster/capability commands rather than universal promises. They appear when a local analogue and its authoritative behavior exist, and stay absent otherwise.

Restore illustrates the rule. Recoil adds CMD_RESTORE only when the builder can restore and map damage is enabled. Budget Annihilation terrain is currently immutable, so Restore has no command card button or hotkey; showing the BAR grid’s M binding would be dead UI, not parity. If deterministic terrain deformation is introduced, Restore must land with server authorization, queued builder work, terrain mutation, path/build-grid invalidation, snapshots, and presentation before that surface is enabled.

  • Attack Unit stores the target entity ID as host intent, refreshes the movement destination from that entity’s live center before path planning, and keeps the order until the target dies or the queue changes.
  • Attack Point stores a world-space priority point and never silently degrades into Fight. This is an intentional Total Annihilation-style exception to BAR: every host with a player-orderable weapon may receive an arbitrary world point at input, server authorization, and execution, even when its entity-target masks reject ground units. Those masks remain unchanged for Attack Unit; the weapon trajectory solver still decides whether a particular point is physically reachable.
  • Explicit Attack overrides autonomous stances. Hold Position constrains autonomous chasing, not a newly issued Attack approach. Entering Hold Fire cancels existing attack intents and locks, but a new player-authored Attack, Attack Point, or Set Target remains executable while Hold Fire stays selected. The host owns this exception; compatible host-controlled turrets consume the host priority.
  • Area Attack is exposed only for BAR-equivalent canareaattack units; per ordered unit it queues every compatible enemy in deterministic nearest-first order and becomes Fight when that unit has no compatible target in the area.
  • Guard is a durable allied-host intent. An ordinary mobile guard uses BAR’s collision-aware stopped standoff, nearby moving-formation velocity match, and bounded distant interception; a non-builder aircraft follows the guardee’s live position. When the guardee took effective hostile damage within BAR’s 40 Recoil-frame window (40/30 seconds, converted to the selected lockstep rate), an armed compatible guard inserts a real sim-authored Attack immediately ahead of Guard. That Attack targets the attacker’s root host, persists until that target dies or becomes invalid, and then pops so Guard resumes; it never copies the guardee’s own target. Builder Guard simultaneously stays ready within build range and joins eligible construction, factory production, repair, or reclaim work.
  • Builder work applies Repair and Reclaim to every selected capable constructor, including area and minimap forms. Repair consumes no energy or metal; its HP rate derives from builder power and the target’s original construction duration, stacks across builders, services allied units/buildings, and restores completed static HP as well as finishing nanoframes. Constructor Patrol temporarily repairs/assists nearby allies or reclaims nearby non-allied entities, then resumes its durable patrol loop. Capture may target enemies only and never an ally.
  • Factory output orders are durable host intent copied to each subsequently produced unit as one ordered Move/Fight/Patrol/Guard queue. Shift appends and command-front insertion prepends. Authoring output orders never changes the separate Factory Guard toggle; it merely means those outputs are not “otherwise unordered” and therefore do not receive the automatic self-guard assignment.
  • Idle constructor factory handoff follows BAR’s enabled Guard-after-build policy: an assisting mobile constructor that completes a factory and has no later queued intent receives a durable Guard on that factory. A real later command wins; mobile factories are not reassigned this way.

BAR Is Inspiration, Never A Content Source

The previous section makes Beyond All Reason this project’s ergonomics and command reference. That relationship covers design — how a command should behave, what a hotkey should do, how a large battle should read. It grants no claim whatsoever on BAR’s files. We study BAR; we do not ship it.

The rule. No asset may ship in this project if the same asset also exists in Beyond All Reason. Art, icons, cursors, sounds, music, models, textures, and fonts are all covered. An asset authored here is ours and is fine to use, and it stays fine when the native sibling copies it — but a file that came from BAR is BAR’s, and putting it in our directory tree does not change that.

This matters more here than it looks, because this repository is the content plane for both products. Assets in this project are vendored into ../annihilation-plus-plus and ship in a commercial Steam build. A BAR file that lands here does not stay here; it propagates into a product that is sold. Keeping this boundary clean at the source is the cheapest place to enforce it.

  • Identical bytes are disqualifying. If a file we ship hashes to the same value as a BAR file, it is BAR content — regardless of its filename or which directory it sits in.
  • Renaming is not authorship. Moving or renaming a BAR asset, or re-encoding it into another container, does not make it ours.
  • Replace, do not quarantine. The fix for a BAR asset is our own replacement, not an exception entry. Only filename coincidences on generic names may be acknowledged, and only after a human confirms the contents differ.
  • New assets are ours or licensed. Anything added should be authored for this project, generated procedurally, or carry a license we can point to in a release audit.

The provenance audit is automated

This rule is enforced by a test rather than by memory. scripts/bar_asset_provenance_audit.py, run as npm run audit:bar-assets, walks every tracked asset in this repository and compares it against Beyond All Reason by SHA-256 content hash and by filename. The identical script ships in ../annihilation-plus-plus as the bar_asset_provenance_audit CTest, so one fix satisfies both projects.

  • A content-hash match fails. That is BAR content, and there is no allowlist for it.
  • A filename match fails until acknowledged. Generic names (icon.png, metal.png) collide by accident, so a reviewed path may be recorded with a reason in scripts/bar_asset_allowlist.json. Acknowledging a filename never acknowledges content.
  • It runs without a BAR checkout. The audit compares against scripts/bar_asset_index.json.gz, a checked-in digest of BAR filenames and hashes. Pass --bar-root to compare against a real BAR checkout, and npm run audit:bar-assets:refresh to regenerate the digest when BAR updates.

Relationship to Annihilation Plus Plus (the native flagship)

A native C++/Vulkan sibling, ../annihilation-plus-plus, ships the same game on Steam. The relationship is one game family, two products, one content plane — not two mirrors. This project is the design lab and the free browser edition: gameplay, physics feel, balance, and content are invented here first because iteration is fastest here. The native project re-delivers the same played experience at several times the unit scale using architecture this platform cannot express (real threads, explicit GPU control).

  • Content is shared; implementations are not. Blueprints, configs, colors, LOD tables, and wire enums in this repo are canonical and are vendored/code-generated into the native build. Simulation code, renderers, and UI implementations diverge freely on each side.
  • This repo defines the network model. The lockstep design — tick and command scheduling, authority and identity negotiation, lobby and match-start handoff, hashing and desync detection, catch-up and spectator behavior — is invented here and is the high-level source of truth for the native build. The native side owns its own transports: it plays over Steam networking and a custom relay backend, behind one abstracted, modular transport interface, with cross-play among Windows, macOS, and Linux. Those are implementation concerns and carry no obligation here.
  • Behavioral parity, not bit parity. The two sims are numerically different by design (f64 + libm here; fixed-point + CORDIC there). Parity means a player cannot tell the rules apart, verified at milestone syncs — never byte-equality of state, wire, or pixels.
  • This repo carries no reverse obligation. Nothing here may be blocked on, or contorted for, the native port. Parity debt is tracked and paid on the native side at its own sync cadence.
  • The signature is the medium physics. Ground, hover, air, and water locomotion as per-unit force physics is the product’s soul in both editions. Performance work on either side buys the physics more headroom; it never simplifies what the player can see.

Atomic Gameplay Pieces

Gameplay should be built from small, atomic pieces that do one job and compose cleanly: unit, building, turret, shot, and ray definitions. These pieces should be swappable without hidden coupling. A unit should be able to vary its locomotion profile, mount different turret sets, fire different shot profiles, or appear from different factories because each piece carries a clear contract instead of leaking responsibility into its neighbors. The two things a turret can emit — shot and ray — are separate kinds, each in its own blueprint family, because only a shot is a body.

  • unit owns a mobile entity's body, mass, health, command capabilities, build cost, its own locomotion — the movement profile and RTS-named rig that produces and applies its movement forces, authored inline as part of the unit rather than as a separate piece — mounted turrets with stable mount IDs and control modes, host-owned intent/workflows, and composition slots. A unit that has a turret contract is built and exists with its authored turrets present; there is no finished weapon host with empty turret mounts.
  • building owns an immobile host body: footprint, mass, health, static infrastructure, host-owned intent/workflows, and its mounted turret set. Fabricators, radar and sonar stations, resource producers, and defensive emplacements are all buildings. A legacy blueprint ID may still contain the word tower, but that is content identity, not a separate runtime family.
  • turret is a standardized mounted combat or sensor emitter. Every unit and building mounts at least one. Every turret owns its own nested turretRange, containing the lock-on range, rangeVolume, hysteresis multipliers, and full-sight/contact-sight/detector radii. It falls into one of three emitter families by its kind:
    • combat (kind: attack) — emits a travelling munition or a sustained line, named by a single by-id reference declared by two fields, emissionKind (shot or ray) and emissionBlueprintId (the id of the emission blueprint in the namespace that kind selects). It carries firing pattern (burst and spread) and no inline emission payload — the emission is named by id, never copied in — so the same combat turret blueprint drops onto any host unchanged.
    • resource-pylon (kind: resourcePylon) — provides an optional economy-overlay origin for one resource. It is never the source of construction authority and never replaces localized economy animation.
    • sensor (kind: sensor) — emits nothing physical and acquires no combat target. It exists to give a host an explicit turret origin for sight, radar, sonar, or cloak detection. A zero in a lane means that turret does not provide that capability.
    A turret is addressable and lockable through its own EntityId, but it is never a separable body: no independent cost, no independent mass, no independent health, no death explosion, and no detached life after the host. It does not own task provenance; host, autonomous, or manual is set per mount. Emitter capabilities never change the host’s entity family.
  • shot is a travelling munition a turret fires: a plasma bolt, rocket, or missile that leaves the barrel and persists as a physical body with its own EntityId, mass, health, and a death explosion. It owns its travel behavior, inherited homing target, recoil, damage, impulse, lifetime, submunition payload, and collision behavior, and — per Shots are destructible bodies too — detonates the instant its tiny health reaches zero. plasma, rocket, and missile are its variants. Shots are authored in their own blueprint family (shots.json).
  • ray is a sustained line emission — a continuous beam — traced from the turret to its target, recomputed every tick from the turret’s aim and bound to the turret’s lifetime. A ray is not a body: it has no mass, no health, and no EntityId of its own, and is attributed through its emitting turret (see Universal Runtime Entity IDs). It owns its line behavior, damage-per-second, recoil, and duration. beam (continuous) is the single shipped variant; the timed “laser” pulse variant was deleted as dormant capability rather than kept as a second contract no blueprint authors (see Dormant capability is removal work, not a content prompt). Rays are authored in their own blueprint family (rays.json).

Keeping shot and ray as two separate kinds — not variants of one umbrella — matters because only a shot is a body. A shot has mass, health, and a death explosion and obeys the entity base ledger; a ray is a sustained emission with none of those — it exists only while its turret sustains it and is attributed to it, never minting an id of its own. That split is what lets “every shot is a destructible body” be literally true without forcing a nonsensical health or mass onto a ray of light. Each lives in its own blueprint file (shots.json, rays.json) so the two contracts cannot bleed into one another.

Vegetation is a reclaimable energy deposit, not decoration

Trees, grass, and seaweed are an atomic gameplay piece: vegetation. Beyond All Reason models trees as engine features any constructor can reclaim for energy (features/enginetrees_override.lua: reclaimable, energy-only yield, reclaimTime, and a damage work pool; gamedata/modrules.lua sets gradual reclaim, no cost to the reclaimer, and multiple simultaneous reclaimers). We inherit that whole contract and only re-express the numbers in this economy, in vegetationConfig.json. Reclaim is a default constructor capability, so a plain right-click on a prop with builders selected harvests it — no mode, no modifier — and Reclaim mode, area reclaim, and constructor Patrol all reach props exactly as they reach units and buildings.

Seaweed is this project’s addition beyond the BAR fallback: a waterline kind whose roots are sampled uniformly inside one shoreline elevation slice. Its authored range fraction is evaluated against a different terrain reference on each side; at 0.5, the upper boundary is halfway from the water surface to the main zero-height terrain flat and the lower boundary is halfway from the water surface to the seabed. This follows the complete water edge without spilling across the main flats or deep basin. Grass and seaweed stay one blade-vegetation presentation family, with seaweed uniformly scaled to 70% of its former size; placement and frond proportions carry the aquatic read, not a second material source of truth.

  • A prop is not an entity. Thousands of them must stay out of the entity map, the spatial grid, the snapshot serializer, and the slot registry, so vegetation owns a dedicated lightweight store — the same reason BAR keeps features separate from units.
  • Orders still address props through the ordinary numeric target id, above VEGETATION_TARGET_ID_BASE. That is BAR’s featureID + Game.maxUnits convention: one Reclaim command spans both stores and no command, action, or wire shape grows a second target field.
  • Placement is simulation state, not decoration. The layout kernel lives in the Rust sim crate and samples uniform horizontal candidates against the installed authoritative terrain mesh, so eligibility comes only from the authored edge, medium/elevation, height, and slope rules — never metal-deposit rings, player starts, quadrants, or other gameplay regions. Identical map inputs produce a bit-identical prop list on every peer and the layout never crosses the wire. Live prop state folds into the canonical state hash: a peer whose forest diverged has desynced.
  • Reclaim is gradual and proportional. A prop’s HP is its work pool; build power drains it at maxHp × rate / reclaimTime per second and the payout tracks the HP removed, so consuming a prop takes reclaimTime / rate seconds and yields exactly its authored energy. Several builders may work one prop at once; each tick claims only its own share.
  • Reclaim uses the same one outward, team-coloured work spray as construction and repair. There is no separate harvest visual.
  • A prop’s authored model dimensions are gameplay data now — they are its selection volume and its reclaim reach — so the asset table is shared by the simulation and the renderer rather than owned by the renderer.

Unit locomotion is part of the unit, not a separate piece

Locomotion is not a standalone atomic piece. A unit’s movement — its profile (mass, thrust, friction, damping, turn authority, contact model, vertical constraints) and its rig (rover, tank, crawler, drone, or another canonical chassis role) — is authored inline on the unit blueprint, in the same definition as the body it carries. There is no separate locomotion blueprint family and no separate locomotion entity. The decision is deliberate: a drivetrain bolted to a chassis is not a thing the game ever needs to point at, cost, or kill on its own, so making it a first-class entity bought addressability nobody used and cost real complexity everywhere. Concretely, locomotion is folded into the unit on every axis the base ledger touches:

  • No separate id. Locomotion is not an addressable entity. It mints no EntityId, appears in no host hierarchy as a child, and is never a parent_id / root_host_id link. The unit is the body and its drivetrain together.
  • No separate cost. Movement carries no metal or energy line item of its own. A unit’s build cost already includes its locomotion; the drivetrain is paid for as part of the body, not billed and built as a distinct sub-part.
  • No separate health. Locomotion shares the unit body’s health. There is no “kill the drivetrain to immobilize the tank” sub-target — the unit moves until the unit dies.
  • Dies with the unit. When the body’s health reaches zero the whole unit comes apart at once; its locomotion explodes alongside it rather than persisting as loose, still-addressable debris.
  • Not lockable. A turret cannot lock onto a unit’s locomotion, because there is no locomotion entity to target. locomotions is not a lock-on family and there is no per-name locomotion narrowing — see Lock-on eligibility.

What survives unchanged is locomotion as a behavior and as a visual: the unit still answers the arrival-control question (see Unit locomotion is arrival control, not waypoint seeking) and still drives its rover/tank/crawler/drone rig (see Locomotion Visuals Are Frontend). Those are properties of the unit, computed from the unit’s own state — not the contract of a separate entity that has to be spawned, costed, healed, and torn off beside it.

Every body shares one base ledger

Before a physical body is a unit, a shot, or a building, it carries the same small base ledger. The kind-specific fields above sit on top of this floor; they never replace it. Turrets are deliberately different: they are addressable mounted emitters, not separable bodies, so they keep an id, mount metadata, lock-on state, and aim state, but they do not carry independent cost, mass, health, or death explosions. (ray is also absent: it is a sustained emission attributed to its emitter, not an addressable body.) The body ledger is:

  • id — the universal runtime EntityId (see Universal Runtime Entity IDs). Every entity is addressable.
  • cost — a { metal, energy } pair. Everything that can be produced has a price in both resources. A unit or building’s cost includes its authored mounted turret set; the turrets themselves do not carry separate cost lines and are not built or paid for independently.
  • mass — every entity is a body the physics solver can push, and F = M · A needs an M for all of them — a travelling shot included.
  • health — every body has hit points and can die. A unit, building, and travelling shot all take damage and all reach zero the same way. What happens at zero is kind-specific — a shot detonates, a host body dies and takes its mounted turrets with it — but turrets themselves have no independent health pool. (A unit’s locomotion has no health of its own either; it is part of the body and dies with it — see Unit locomotion is part of the unit.)
  • death explosion — a { radius, force, damage } blast the entity detonates the moment its health reaches zero. Every entity explodes when it dies (see Every death is an explosion); within the radius the blast applies an outward force and damage to everything caught in it. A turret does not detonate separately; it disappears with the host body that carries it.
  • geometry — three radii, one per physical role: a radiusVisual (drawn size), a radiusHitbox (the damage-receiving hurtbox), and a radiusCollision (body-versus-body no-overlap contact). See Entity geometry is three radii.

Treating cost, mass, and health as a shared body base — not as per-kind bolt-ons — is what lets the rest of this document make blanket statements about bodies. Lock-on is broader than damage ownership: a turret can still be locked onto because it is an addressable mount with aim and emitter state, but damage to that mount resolves through the host body unless a future mechanic explicitly says otherwise.

Entity geometry is three radii

Geometry is part of the base ledger too, and it is exactly three radii — one per physical role — carried by every entity of every kind. Keeping them as three named, single-purpose radii, rather than one “size” doing triple duty, is what lets a body be drawn large, hit on a tighter core, and kept apart at a wider stand-off without any of the three lying about the others:

  • radiusVisual — the drawn size. Presentation only: how big the body reads on screen. It has no say in damage or physics.
  • radiusHitbox — the damage-receiving volume (the hurtbox). A shot, beam, or explosion that reaches inside this radius deals damage to the entity; everything that tests “did this hit?” tests against it.
  • radiusCollision — the body-versus-body contact radius: how close two solid bodies may get before they resist sharing space. This is the radius that keeps units out of each other and that a body collides on. It is hard contact, not a force at a distance.

The same three names mean the same three things on a unit, a building, and a shot — one vocabulary, not a per-kind grab-bag of ad-hoc radius fields, so the collision and damage kernels read one contract for every body they touch. A turret may expose an addressable aim/selection volume for lock-on and line targeting, but that volume is a mount target on the host, not an independent physics body with its own health. The death explosion’s own radius (inside its { radius, force, damage } field) is a fourth, separate thing — it is the blast the body throws on death, not a property of the standing body — and must not be folded into these three.

radiusCollision is deliberately named for hard contact so that the word push stays reserved for a future push field capability: an optional, authored, sustained force that shoves other bodies at a distance — a heavy unit’s bow-wave, or a launched piece plowing through a crowd. That is a force-over-distance, not a no-overlap radius; when it is added it will be its own capability layered on top of radiusCollision, never a rename of it.

Turrets are inseparable mounted emitters

A turret is addressable because targeting, source provenance, aim state, and renderer inspection need a stable thing to point at. It is not a separable body. A host does not carry decorative turrets with their own cost, mass, health, or death explosions; it carries mounted emitters that live and die with the host body. Destroying a host destroys the host’s authored turret set. There is no finished host missing its authored turrets, no turret-only wreck that keeps fighting after detachment, and no intermediate body-with-empty-hardpoints construction state.

Per-turret lock-on remains useful, but it means “aim at this mounted emitter” or “use this emitter’s targeting policy,” not “remove this turret’s private health pool.” A disarming or precision mechanic can still target a turret ID to aim at the mount, interrupt firing, or apply a host-level effect, but the health, cost, and mass accounting stays on the host body.

Every piece is an agent; the player commands only hosts

Every host body is an agent — it has its own health, its own death, and, where its kind allows, its own behavior — but agency and command are different things. The player issues orders to exactly two host kinds: units and buildings. Everything mounted below a host is driven by that host, never by the player’s cursor directly. Control runs down a chain:

  • The player controls units and buildings — the orders on each type’s action panel (move, fight, build, set lock-on, ON/OFF, and so on).
  • A unit moves itself and controls its own turrets: the player’s order to the unit becomes thrust through its own (intrinsic) locomotion and a host lock-on offered to the turrets.
  • A building controls its own turrets the same way, but does not move (it has no locomotion). Its turret capabilities decide whether it senses, produces, constructs, or attacks.
  • A turret executes one typed effect. Its mount control mode determines whether it consumes a host task, runs autonomously, or waits for a manual ability. It is always governed through its host, never by a separately selected turret command.
  • A shot, once fired, runs itself — ballistic or homing toward its inherited target, detonating on contact or at zero health. Nothing commands it after launch.

So the player never reaches past a host to puppet a turret or a shot directly. You command the unit; the unit commands its parts; each mount is host-controlled, autonomous, or manual, but the line of control always runs through the host that carries it.

Because turrets are inseparable mounted emitters, the chain does not survive without its host. A turret has targeting agency only while the host exists and carries it. When the host dies, its mounted turrets die with it as part of the same assembly; there is no detached turret agent and no hostless turret control hierarchy.

Every death is an explosion

Death is never a quiet despawn. Every body carries a death explosion in its base ledger — a radius, a force, and a damage amount — and when its health reaches zero it detonates that blast into the world. The explosion is a physical event first (per the Physics Model): within the radius it applies an outward force that heavier bodies resist more, and it applies damage to every entity caught in it, friend or foe. A shot’s detonation is the smallest instance of exactly this rule; a commander’s is the largest. Turrets are not bodies, so they do not have separate death explosions.

The client must present a core fire blast for every delivered death event at every detail level. The CLIENT MATEXP toggle controls only the optional breakup and tumbling of the body’s individual textured pieces; switching that detail off can never turn a death into a quiet fade or suppress its fire blast.

The defaults matter because they make a killed host read as one physical event. A unit’s or building’s mounted turrets are part of the host assembly, so a dying host does not leave intact guns behind and does not launch autonomous turret pieces into the battle. Its drivetrain and mounted emitters end with the body. The host explosion is still free to damage other nearby entities; it simply does not manage its own turrets through separate health pools.

Because the blast is authored data, not a fixed rule, a blueprint can deliberately break the default. A unit built to be a bomb can carry an oversized radius, a vicious force, and heavy damage so that its death shreds everything nearby — a designed suicide weapon rather than an accident. A fragile scout can carry almost nothing. Either way the contract is identical: health hits zero, the body explodes, and the radius spends force and damage on whatever is standing in it.

Shots are destructible bodies too

A shot is an entity, so a shot has health — a deliberately tiny amount. A shot dies the instant its health reaches zero, and dying means it detonates: it runs its normal explosion / splash / submunition path exactly as if it had reached its target, just wherever it happened to be. Two things drive a shot’s health to zero:

  • Contact — touching the ground, another shot, or any other solid body forces the shot’s health straight to zero and detonates it on the spot. This is the ordinary “it hit something” case expressed through the health field rather than a separate collision flag.
  • Incoming fire — because the health is small but real, a weapon can whittle it down before contact. A point-defense turret that locks onto enemy shots (its inclusion object includes only enemy_entities and shots) chips that tiny health to zero and pops the round in mid-air, short of its target.

This unifies “the projectile hit the dirt,” “two rounds collided,” and “a flak turret shot the missile down” into one rule: a shot is a body with health, and zero health detonates it. Travelling shots publish continuous authoritative motion while live, with discrete spawn and despawn lifecycle events, per Travelling shots use authoritative motion streams. This applies to shot emissions only: a ray is not a body, carries no health, and is never “shot down” — it simply stops when its turret stops sustaining it.

Shot arming is a host-centered safety volume, not source exclusion. Every physical shot is emitted from its selected authoritative QueryWeapon socket and begins unarmed. The firing host's ARM volume is derived from its HIT volume: it has the exact same center and shape, with every extent enlarged by at least 1.5 times. Where a unit's collision sphere is larger than its damage sphere, the derived uniform scale grows further so ARM retains 1.5 times the collision reach. Unit sphere HIT volumes therefore produce sphere ARM volumes; building box HIT volumes produce larger box ARM volumes. There is no separately authored radius that can drift from HIT. The shot becomes active only after its complete hitbox has cleared ARM. The authoritative crossing point starts its first active collision sweep. While unarmed, the shot does not test solid-body contacts or ground impact. Once armed, it collides with every solid entity hitbox or reflector, including the host that fired it. Source provenance remains for attribution and replay; it is not a collision immunity list. The VOLUMES: ARM diagnostic renders the same derived host volume used by this rule. All entity-bound TURR CIR and VOLUMES diagnostics are selection-scoped: enabling one never paints every matching entity, vegetation prop, or unowned terminal impact across the battlefield.

Materialization: BAR-faithful build-in, alpha death-out, one build channel

Every host body and every mounted turret visual carries a per-host build fraction (0 → 1) and a presentation alpha that runs 1 → 0 as it dies. Construction and destruction share one materialization module (the renderer’s entity-fade channel), but the two directions no longer look identical: build-in follows Beyond All Reason’s construction language, death-out remains the alpha de-rez. It applies to the two assembled host kinds (buildings, units, and their mounted turret visuals); a shot is exempt (see below).

Build-in is the BAR nanoframe. A queued-but-unfunded build site renders as the full team-tinted model at BAR’s queued-ghost alpha (0.24). Once resources flow, the assembly materializes bottom-to-top through four rising height bands at pow(buildFraction, {3, 1.5, 0.7, 0.35}) — finished material below the lowest band, pulsing team tint between bands (1.0×↔1.78×), flat translucent team color (alpha floor 0.4) above the highest — with white scan lines climbing at each band and a pulsing team-colored construction grid that shrinks as progress rises and fades over the final 5%. The numbers are data in constructionVisualConfig.json (nanoframe). Backends that carry a single alpha (instanced detail/leg pools, custom shader parts) ride the same envelope as one curve: ghost alpha at fraction 0, the top-alpha floor rising with the fraction, opaque at completion. The body and authored turret visuals materialize together because turrets are not separate construction pieces (see Hosts build as complete assemblies). A host counts as complete once the host body is complete; its mounted turrets are present as part of that product, even if their firing logic remains disabled until completion.

Death-out. The same channel runs backward, but death is still an explosion first — never a quiet fade-to-nothing (per Every death is an explosion). The dying model itself becomes the material explosion: every retained textured render part separates, tumbles, and fades on the death clock. Random launch vectors open the silhouette while the killing attack’s penetration direction, force, projectile velocity, and the victim’s inherited velocity bias the whole cloud. There is no second approximate debris copy and no intact shell dissolving underneath it. Mounted turrets are part of that host visual breakup, not live pieces.

The material explosion uses the host’s actual pieces, not generic shapes. Every atomic visual part as rendered — unit hull lobes, turret heads, barrels, treads, wheels, individual leg segments and joints, team ornaments, and every authored building wall, vane, rotor, pylon, dish, or brace — is thrown as itself. Those pieces are presentation artifacts, not live turret agents. The explosion applies gameplay force and damage to external bodies in its radius; the host’s own mounted turret visuals simply participate in the material breakup and then fade.

Simulation owns the truth; the renderer owns the look. The damage, the radial force, and the destruction of the host body are deterministic and authoritative — force changes future positions, so all clients must agree. The opacity ramp, the tumbling debris, and the fireball are client-only cosmetics driven off the death event; non-deterministic randomness is fine there because nothing downstream of the sim reads them (cross-ref Locomotion Visuals Are Frontend). The fade is rendered as continuous alpha with depth writes kept on, so a multi-part body still writes depth and self-occludes through the transition without a transparent-queue sort cost at scale.

Shots are exempt from build-in. A shot is spawned whole from its turret, not assembled piece by piece, so it has no materialization ramp. Its “death” is its detonation (per Shots are destructible bodies too) — a small fire blast and, at most, a single shard of debris.

An unattended build site rots away

An unfinished structure is not permanent scenery. A shell that nobody is answering for starts losing progress on that same lifecycle tick and is removed outright when it reaches zero. The rate begins at 3% of its own full progress per second and follows BAR’s inverse-build-time idea through a bounded reference-cost scale: cheap frames rot faster, expensive frames linger, and health falls with progress.

  • Completion wins before attendance and decay are evaluated. A shell whose required cost has been fully paid becomes a completed building on that lifecycle tick even if its builder moved, its queue advanced, or attendance disappeared between payment and lifecycle processing. Decay applies only to incomplete investment; it can never undo a paid building.
  • Attendance, not funding, starts the clock. A site is attended while construction work lands on it and while any living builder still carries it in an order queue — a shift-queued site is placed the instant the order is issued and must be allowed to stand until its turn.
  • Abandoned and cancelled invested frames both decay immediately and slowly. A zero-progress frame with no remaining queue reference disappears on the first orphan tick. Decay is the only way a partial assembly leaves the map on its own; an interrupted shell has no other exit.
  • Reaching zero is a removal, not a death: no explosion, no wreck, no death event. Nothing that was never funded should detonate.
  • Factory unit shells are exempt. A factory owns its shell’s whole lifecycle, including pauses, so a second timer would be a second authority over it.
  • The delay and rate are authored in buildConfig.json and hashed into match initialization like every other gameplay constant. BAR enables construction decay with a 9-second grace period and a 0.03 base speed; this game deliberately sets the grace period to 0 seconds while retaining the slow 0.03 rate.

Sensor coverage belongs to turret origins

Full sight and contact sight are authored as explicit source-medium by target-medium radius matrices; cloak detection remains a separate capability and cannot activate a target lane the source lacks for full sight. The matrix lives directly inside each turret blueprint’s turretRange.sensors; it is not a host field and is not a reference to a reusable sensor suite. Zero is explicit absence. Current hosts use one host-specific, sensor-only turret as the single source of their migrated coverage. A future host may put that one source on an attack, spawn, or utility turret instead; multiple simultaneous sensor mounts require an explicit native aggregation extension before authoring them.

Coverage is centered on the authoritative world position of the mounted turret, and the turret origin decides the source medium. Target medium is decided independently from the target body center. Thus the four full-sight lanes are above-water to above-water, above-water to underwater, underwater to underwater, and underwater to above-water. Contact sight uses the same matrix; ordinary radar authors only the above-to-above lane and sonar only the underwater-to-underwater lane. The validated per-host source aggregates with every other friendly host source for the team.

Weapon lock-on range remains independent. Changing ammunition, attack range, or rangeVolume never changes sight because sensor radii are sibling authored facts, not multipliers of weapon reach. Targeting requirements such as requiresFullSight consume the team aggregate; they do not create coverage. This permits long-range artillery with short local sight, a short-range weapon backed by long radar, and a sensor-only building without coupling any of those distances.

Lock-on policy lives on turrets, not guided shots

A turret is the only piece that acquires a lock-on target. A rocket or missile can inherit the exact entity the spawning turret was locked onto at launch, and it can home toward that inherited target while the target remains alive in the sim. The guided shot must not run its own target acquisition pass, scan for replacements, or choose a new victim after launch. Lock-loss behavior is explicit shot data. Missiles and torpedoes clear the dead inherited lock and continue on their current vector. The light vertical rocket retains the inherited entity ID as provenance and flies toward the last solver-produced speculative future intercept. That cache is never replaced by the entity’s actual last-known position. It turns only until aligned, then coasts; a swept authored arrival sphere at the intercept uses the shot’s normal expiry outcome so a fast rocket cannot step across the point. Neither policy reacquires.

Host intent is not turret lock-on

Units and buildings carry host-owned intent chosen by the player, AI, or command system: attack an enemy, guard an ally, construct or repair an entity, produce a product, move, or run a queued workflow. Intent is not stored as one overloaded target ID. A single adapter projects it into typed per-mount tasks, and each task may use the same opaque entity-ID representation without confusing friendly work with hostile fire.

A mount accepts a task only when its emitter kind supports the operation and its control mode permits that source. Attack tasks then pass team-aware relationship, entity-family, visibility, range, line-of-sight, and shot-compatibility gates. Construction, repair, and production remain host workflows and never become mount tasks. This is why a bare “lock-on ID” cannot be the complete command model even though entity tasks share one ID representation.

Guard is likewise host intent. The guarded ally remains the movement/service anchor. When that ally takes effective hostile damage, the sim inserts an actual Attack order in front of the durable Guard, aimed at the attacker’s root host; it does not copy whatever target the ally happened to be attacking. The temporary order carries stable Guard-return provenance through action hashing and snapshots, never participates in Repeat rotation, and is removed when its attack target dies or becomes invalid so the Guard beneath it resumes. Builder work remains a separate lane: while the weapon lane retaliates, an in-range builder may still construct, assist production, repair, or reclaim for the guarded workflow. The 40-frame eligibility window is authored in Recoil’s 30 Hz time domain and converted to the match cadence, rather than treated as 40 prototype ticks.

Mount control mode is explicit

Every turret mount on a unit or building requires a stable mountId and a controlMode: host, autonomous, or manual. Host mounts consume compatible host tasks. Autonomous mounts ignore host tasks and run their own effect policy. Manual mounts wait for their named ability. The role lives on the mount rather than the reusable turret blueprint, so the same emitter can occupy different roles on different hosts without blueprint duplication.

Host attack tasks are evaluated independently per mount. A compatible mount retains the priority target or point. Every armed unit and building has exactly one host-controlled combat mount: this is the BAR-style bridge that makes the body obey Attack Unit and Attack Ground orders. Any additional combat mounts are autonomous or manual; an autonomous sibling is never overwritten and may acquire a different compatible target in the same tick. The host-overridden mount keeps the compatible host target ID while range, line-of-sight, ballistics, or a force field prevents firing; it remains in a non-firing tracking state instead of silently reverting to autonomous acquisition. Non-combat construction, resource, and spawn mounts may still be host-controlled by their own typed workflow and do not count toward the one-combat-mount rule. Thus one commander or building can attack, construct, and spawn concurrently through separate lanes without sharing mutable turret state or requiring the host to choose one universal lock.

Fight-move and patrol halt behavior remains separate. Unit attack-emitter mounts can set requiredEngagedForFightStop; every marked mount must be engaged before the unit stops. Utility emitters never participate in combat halt logic.

Shield-aware targeting is an earned, per-player upgrade

The battlefield has two targeting brains, and which one a player’s entities use is earned, not toggled. NAIVE is the default: turrets ignore force material when choosing targets, lock straight through shield spheres and mirror panels, and spend their fire on shots the field will absorb or reflect. SHIELD-AWARE is granted to a player while they own at least one completed, switched-ON Shield-Aware Targeting Tech building and is lost the tick the last one dies, closes, or is captured away. Both tech structures are ordinary ON/OFF active-state buildings — the upgrade is a powered channel exactly like radar’s contact coverage, following BAR’s on/offable Targeting Facility (armtarg): a fortified or switched-off tech building keeps its local sight and its 10× damage resistance but grants nothing, and sustained damage force-closing it suppresses the upgrade until the building reopens. The BATTLE bar’s TARGETING: readout displays this per-player status; it is not a setting, and there is no global battle flag behind it.

Shields are powered equipment, not a production unlock

A shield belongs to the side that is running it, not to the unit wearing it. Every shield a team owns is raised while at least one of that team’s completed, switched-ON Shield Generators is up, and every one of them lowers — through its authored transition, not a blink — the tick the last generator dies, closes, or is switched off. One generator is enough for the whole side; a second one switched off takes nothing down. A shield host still under construction has no field either: equipment runs on a finished body, so the field comes up with the unit rather than with its scaffolding.

“Every shield” means every shape. Powering is a property of the material, so a directional mirror plate answers to the generator gate and rides the authored transition exactly as a dome does: dark side, no plate; last generator switched off, the plates lower with the domes; unfinished hull, nothing at all. The Loris ran outside that rule for a while — reflecting and obstructing on its own hit points, snapping on and off with no ramp — and the reason is worth recording, because it was not a missing line so much as a missing list: the powered-equipment pass walked the hosts that own a barrier, and a plate has no barrier, so the one shape that is not a closed surface fell out of the one pass that says what force material costs. Anything asking “which entities are running force material” must ask for the emission, never for the barrier geometry; the barrier list answers a narrower question — which hosts have a field surface to draw and collide — and the two are not interchangeable.

Nothing is gated at order time. Shielded units and buildings are buildable whenever their factory or builder can make them, and a side with no generator simply fields them unshielded. That is deliberately the opposite of a tech unlock: a production lock is invisible until the player tries to click something and is told no, whereas an unpowered shield is a visible, reversible battlefield state that the player can read off their own army and fix by turning a generator back on. The BATTLE bar’s SHIELDS: readout names it, and it is derived from building ownership every read, so completion, destruction, capture, and the ON/OFF switch all land the same tick with nothing stored.

“Obstructs direct sight” has one exact meaning. After the ordinary line-of-sight and ballistic gates pass, a shield-aware turret tests the straight segment from its mount aim pivot to the raw aim point against every active force surface — one material, two shapes, so spheres and panels answer through a single clearance query. This shield gate is deliberately not folded into the authored requiresNonObstructedLineOfSight flag: that flag is per-weapon terrain policy, and the arcing weapons that author it off (mortars, artillery, vertical launchers) are exactly the ones whose shells a shield dome eats — they must still respect the shield gate. Nor is it a sampled-trajectory test: a shield sphere is a closed surface, so every path from outside to a target inside it crosses the material and the straight segment already gives the physically correct answer at slab cost. Refining the rare mid-field-dome and panel-edge geometries with a descending-leg test for high-arc weapons is an allowed future refinement, not the baseline contract; its kernel (shield_clearance_arc) is written and walks both shapes through the same panel walk the segment gate uses, but nothing calls it, and the shipped gate stays the straight segment until something does.

That gate is directional, and the direction is the barrier’s rather than the sight system’s. A closed dome obstructs a sightline only where the line enters it, because a dome intercepts what comes at it and lets its own side’s fire out; a flat mirror panel has no inside at all, so it obstructs from either face. Both readings are just the authored reflection policy restated — every barrier authors reflect-outside, every panel reflect-both — and that is the point: sight and shot must agree about which way a piece of material is opaque, or the turret refuses shots that would have landed. The obstruction test therefore reads as “does this sightline enter the field”, not “does it touch the boundary”.

Concretely: a gunner standing under a friendly dome can acquire targets outside it, a gunner outside cannot acquire targets under it, a sightline that passes clean through a dome is still blocked by the inbound half of its crossing, and two units under the same dome see each other normally. The symmetric rule this replaced got the first of those wrong, and because the clearance walk excludes nothing — not even the shooter’s own field — a shielded unit could not acquire anything outside its own bubble while its rounds left that bubble unimpeded. Nothing is special-cased to fix that; the geometry now answers it. The directional test is also strictly the cheaper one, since “starts inside” is the sign of a term the intersection math already computes, decided before the discriminant, the square root, and two divisions.

  • A shield-blocked pair is treated exactly like a sight-blocked pair. Autonomous acquisition never admits a candidate whose shield gate fails; an existing autonomous lock holds fire immediately and is dropped after the shared sight-drop grace, and re-acquisition then runs over candidates that can actually be hit. A shield-aware unit therefore never parks on an unhittable target — if every candidate is shielded it goes idle and keeps re-scanning as fields move, drop, or die.
  • Player-ordered priority targets are the one exception, per the host-retention rule above: an explicit Attack on a shielded enemy keeps the commanded target in the non-firing tracking state and waits for the field to drop rather than wandering to a different enemy.
  • NAIVE players skip the shield gate entirely — their locks and fire are shield-blind, and reflector panels punish them for it.
  • Shield-only emitters keep their authored exemption: a turret whose emission is pure shield material must hold its own barrier and never treats force material as obstruction. Shield emitters with offensive submunitions obey the same gate as every other attacking turret.
  • Fog, sensors, and intelligence are untouched. Force material never hides information; terrain remains the only fog occluder. Shield-awareness changes what a turret is willing to attack, never what a player knows.
  • The Shield Detection Lab decides whether a side reads shields, never which way they are opaque. It carries no direction of its own; it switches the gate above on, and that gate’s direction comes from the material. If a barrier is ever authored inside-out or per-emission-family, the sight kernel must start reading that policy instead of assuming outside-in.

Lock-on eligibility is authored as an additive inclusion object. A turret carries one for its own acquisition, while units and buildings carry one for player-authored host intent. The default is identical for every locker and deliberately as narrow as it can be: a locker with no lock-on inclusions can lock onto nothing. Lock-on is off by default and additive from there: a turret never silently inherits a family it might hit; it locks only onto the kinds, relationships, and names it explicitly opts in to. A fully-permissive locker that has added every relationship and every family can lock onto any living entity in the game that has an ID, of any kind — any friendly or enemy unit, building, turret-mount, or travelling shot — but that breadth is authored, never assumed. A passive building can author no targets while an armed building authors the same host policy as an armed unit. The same eligibility rule applies whether the lock-on is a unit’s or building’s host-level target set by player command, a turret’s inheritance of that host target, or a turret’s autonomous acquisition: one additive schema, one shared targeting kernel across units, buildings, and free-acquiring turrets.

  • includeLockOnLevel0FriendsAndEnemies admits whole ownership relationships before scoring. Valid high-level entries are friendly_entities and enemy_entities; a relationship that is not listed is never lockable.
  • includeLockOnLevel0Entities admits whole target categories before scoring. Valid high-level entries are units, buildings, turrets, and shots — every addressable entity kind, so any kind can be added and, by omission, any kind is excluded by default. (There is no locomotions entry: a unit’s locomotion is part of its body, not a targetable entity — see Unit locomotion is part of the unit.)
  • includeLockOnLevel1Units narrows an already-included unit family to only the named unit blueprints; an empty list applies no name restriction.
  • includeLockOnLevel1Buildings narrows an already-included building family to only the named building blueprints.
  • includeLockOnLevel1Turrets narrows an already-included turret family to only the named turret blueprints.
  • includeLockOnLevel1Shots narrows an already-included shot family to only the named shot blueprints — e.g. a point-defense turret that should pop only heavy rockets, not every plasma bolt.
  • lockOnRequiresTargetLockedOntoSelf is a four-state enum, separate from the family lists, deciding how an otherwise-admitted enemy is weighed by whether it is itself locked onto this locker. "ignore" (the default) does not care; "require" admits a candidate only while it is itself locked onto this turret or its host, and drops it the instant it re-targets; "preferReacquire" ranks such threats above every other candidate and rescans when the current target stops reciprocating; "preferHold" applies the same threat ranking during normal scans but does not rescan solely because the current target stops reciprocating. The shield panel reflector ships on "require"; every other blueprint stays on "ignore". See Reciprocal lock-on: only hit who is hitting you.

The hierarchy should be evaluated in order: ownership, aliveness, and visibility decide whether something can be considered; the relationship inclusions admit friendly or enemy candidates; the entity-family inclusions admit whole kinds — units, buildings, turrets, or shots; level-1 inclusions, when present, narrow a surviving family to specific authored names; range, line-of-sight, and scoring then pick the best lock from the survivors. Host-owned construction does not enter lock-on at all. A fighting turret that should only attack hostile targets includes enemy_entities. A normal weapon turret that should ignore turret mounts simply leaves turrets off its family list. Because lock-on is off by default, targeting a specific piece is just a narrow inclusion object: a point-defense turret that should shoot down incoming munitions and nothing else includes only shots; a disarmer that should strip weapons includes only turrets. Most ordinary weapons, in turn, include the whole-body families — units, buildings, and turrets — and leave shots off so they spend their fire on whole bodies. Specialist weapons can then use the level-1 lists to restrict a family to named unit, building, turret, or shot blueprints without changing the shared target acquisition code. A unit or building runs its own host-level inclusion object through this identical hierarchy before its host lock-on is set; each mounted turret then runs its own object again when it decides whether to inherit that host target.

We do not want mixed or overlapping roles. A turret should not secretly define locomotion. A shot should not secretly define a unit. A building composes combat, production, resource, and sensor behavior only through explicit turret mounts; those capabilities never create a second static-host category. A unit should not duplicate shot physics. Cross-piece behavior should be expressed through explicit references and narrow data contracts, so designers can recombine pieces freely and the simulation can keep hot paths simple. These pieces are authored as data, not code — see Config Is Data, Not Code.

Reciprocal lock-on: only hit who is hitting you

The inclusion object carries one mode beyond the family lists: lockOnRequiresTargetLockedOntoSelf, a four-state enum — "ignore", "require", "preferReacquire", or "preferHold" — that decides how a locker weighs an otherwise-admitted enemy by whether that enemy is itself locked onto it. "ignore" is the default and the value every ordinary turret, unit, and building uses: reciprocal lock has no bearing on candidacy or scoring, and the locker does not care whether its prey is shooting back. "require" admits a candidate only while that enemy is itself locked onto this turret or its host; an enemy not aiming at us is simply not a candidate, no matter how close or how otherwise valid it is. The two preference modes treat enemies locked onto us as a strictly higher priority tier without making them mandatory: if any are aiming at us during a scan, the locker engages those alone, and only when none are does it fall back to the ordinary candidate pool. One shipped blueprint leaves the default: the shield panel reflector uses "require", so it tracks exactly the enemy turrets currently locked onto it or its host. Every other turret, unit, and building stays on "ignore"; the preference modes remain reserved for future retaliation-style specialist weapons.

"require" and "preferReacquire" are both evaluated in real time, not just at acquisition. The locker re-checks against the reciprocal condition exactly as it re-checks range, line-of-sight, and aliveness. Under "require" the instant the enemy re-targets — locks onto a different body, drops its lock, or dies — the condition fails, the locker loses that lock the same tick, and re-acquisition runs over whatever else is currently aiming at it. A "require" locker therefore tracks whoever is shooting at it right now and follows the threat as it changes; with nothing aimed at its host it has zero candidates and sits idle, which is the intended counter-fire behavior — it punishes focused fire and is trivially sidestepped by not shooting at it.

Under "preferReacquire" the same re-evaluation re-sorts the two tiers instead of emptying the pool: the instant an enemy starts firing on the locker it jumps to the threat tier and is engaged ahead of any opportunistic target, and the instant the current target aims away the locker scans for a better reciprocal target while still falling back to the general pool rather than going idle. Under "preferHold", reciprocal threats still form the strict higher tier whenever a normal acquisition or scan occurs, but an existing valid target is not disturbed solely because it stopped reciprocating. Within either tier the ordinary scoring — including current-target stickiness — still picks the single best lock, so a preference weapon does not thrash between equally-ranked threats. The tiering is strict by default — any threat outranks any non-threat — with a softer scoring-bonus variant available if a weapon should let an overwhelmingly better opportunistic target win. A reciprocal preference weapon retaliates first and suppresses second.

“Locked onto us” means locked onto either this turret or its host (self_turret or self_host) and is read from the lock-on state committed at the end of the previous tick, so the check is order-independent and cannot form an intra-tick cycle when two reciprocal lockers face each other; “the same tick” above is therefore the next resolution tick, imperceptible at simulation rate. The matched state is “currently holds a lock onto us”; reacting only to enemies actively firing rather than merely aimed would be a separate future refinement, not part of this enum. The targeting kernel reads prior committed target ids from candidate turrets and checks whether any point at this turret or host, avoiding same-tick retarget cycles without relying on a speculative inverse set. Any value but "ignore" is meaningful only alongside enemy_entities: a "require" locker that admitted no enemy relationship would be inert and a reciprocal preference one would collapse to ordinary opportunistic targeting — both authoring smells the loader can reject.

If a specialist turret ever needs a second, explicit targeting contract layered on top of the ordinary inclusion object — behavior the additive lists cannot express, such as ranking threats by sustained DPS or aiming by a derived geometric rule — it gets a validated secondaryLockOnProfiles entry with its own regression tests, not a special case buried in the shared targeting kernel. Large targeting regularization passes must preserve any such profile, its validation, and its tests instead of simplifying the turret into an ordinary scanner.

The reflector panel aims by the threat’s own trajectory

The shipped secondaryLockOnProfiles entry is the shield panel reflector (the Loris’s mirror). It locks, via reciprocal "require", exactly the enemy turret currently locked onto it or its host. Its rankBy: "threat_turret_sustained_dps" rule makes the strongest admitted incoming weapon the preferred threat, while rescorePeriodTicks: 16 makes an already-engaged panel periodically compare its still-valid lock against newly reciprocal threats. Refreshes are deterministically phase-staggered by host entity id, so every Loris does not query on the same tick. The inclusion object remains the hard eligibility gate: an omitted turret blueprint, a turret that is not currently locked onto the panel or host, an unseen target, or a target outside the authored range cannot win regardless of DPS. A refresh replaces the current lock only for a strictly higher sustained-DPS score; equal-power threats keep the existing lock and cannot cause churn.

The reflector’s aim rule exists to send the selected turret’s fire back at the attacker’s own body. Because reflection off the panel is specular — one shared mirror formula for beams and travelling shots — the aim rule is entirely a question of choosing the panel normal, and the correct normal depends on how the incoming fire travels:

  • Line-of-flight weapons (beams and any other threat whose fire travels the straight ray from its barrel) use the straight-line bisector: the panel faces the bisector of the ray to the threat turret’s mount and the ray to the threat host’s body, so the specular bounce returns the beam from the turret onto its own host.
  • Ballistic threats (any turret whose own aim requires a ballistic solution — plasma guns, cannons) arrive on an arc, not on the barrel ray, so the straight bisector throws the bounce off-target. The panel instead mirrors the threat’s own ballistics equation: it runs the threat’s authored shot parameters (muzzle speed, gravity, linear damping rate, arc preference) from the threat’s mount to the panel to predict the incoming arc’s arrival direction and speed, then solves the return arc from the panel — at the reflected (arrival) speed, with the same parameters — to the 3D midpoint between the threat turret’s center and its host’s body, and faces the panel along the bisector of the reversed arrival direction and the return launch direction. The specular bounce therefore leaves exactly along the return arc and lands the shot back on that midpoint. The rule is abstracted, never per-weapon: whatever ballistic shot is being fired is reflected back by its own equation.

When either ballistic solve has no solution (the panel sits outside the arc’s reach), the panel falls back to the straight-line bisector rather than going idle — a best-effort mirror is still a mirror. Constant-speed guided munitions and vertical launchers are not ballistic threats under this rule; they keep the straight bisector.

Roster Coverage And The Fabricator Matrix

The engine supports more gameplay than any particular roster size implies, and the roster goal is written accordingly: a compact roster in which every important movement medium, information tier, weapon family, counter, economy system, and work command has a clear host and a deliberate showcase. Beyond All Reason is a coverage check for that sentence — do we have the counters, the intelligence loop, the naval economy, the connective air roles? — never a target unit count. Before the roster grows substantially in any direction, the existing content is reworked into explicit tech tiers with costs and firepower that respect them; growth without tiers just adds more of what is already over-represented (ground direct-fire bodies, capstone giants that bundle weapons, detection, shields, and production, and continuous beams relative to rockets, clusters, point defense, and underwater counters).

Every unit authors one tier and its production domains

Production identity is unit-authored data, exactly like locomotion and sensors: every producible unit blueprint authors one production fact — a techLevel (1, 2, or 3) and one or more production domains from bot, vehicle, aircraft, and naval. A pure tank is vehicle only; a pure walker or crawler is bot only; a pure plane is aircraft only; surface ships and submarines are naval only. Cross-medium units author every domain they genuinely serve — an amphibious tank is vehicle + naval, a torpedo gunship is aircraft + naval, a water-striding crawler is bot + naval. Tick and Bee are ordinary tier-1 products in the bot and aircraft domains respectively, even though their Queen may also emit them. Only a unit that is never produced at all (the Commander) authors null and appears in no fabricator menu.

Tier is a role statement, not a price bracket: tier 1 is the opening army and its constructors; tier 2 is the advanced army, specialist tech, and the four Advanced Construction crafts; tier 3 is the small experimental capstone set. The Loris and Daddy Longlegs are tier 1; Latrodectus is tier 2; Tyrannosaurus, Microraptor, Queen Bee, and Queen Tick are tier 3. Costs and firepower follow from the assignment rather than defining it.

Five Fabricators at T1/T2, one Universal at T3; menus are derived

Production has exactly five fabricator buildings at tier 1 and the same five at tier 2: a Universal Fabricator plus Bot, Vehicle, Aircraft, and Naval specialists, and their Advanced counterparts. A fabricator blueprint authors only its own factory identity — a tier and a domain (one of the four, or universal). Its production menu is computed: a specialist’s roster is every unit whose authored production facts match its tier and domain, and a T1/T2 Universal’s roster is the deduplicated union of its tier’s four specialist rosters. Tier 3 has exactly one fabricator, the Experimental Universal Fabricator, and no T3 specialists; its roster is every authored T3 unit. No fabricator may produce units from another tier. Because each roster is derived, a cross-domain unit can sit in two specialist menus without ever creating a duplicate Universal entry, and adding a unit to the game is adding it to the right menus — there is no second list to update and therefore no list to drift.

  • Cost rule. The four specialists at a tier start at comparable cost and build power. A same-tier Universal costs about 3× its tier’s specialist baseline in energy, metal, and (through the shared build-power model) build time. The Universal pays for flexibility, not throughput: it stays near a specialist in build power, durability, and footprint efficiency. Tier 2 has its own higher specialist baseline, and the Advanced Universal is 3× that baseline, not 3× the tier-1 Universal.
  • T3 cost rule. The Experimental Universal costs 3× the Advanced Universal, doubles its build power and durability, and pays for access to the capstone roster rather than adding a second T3 production path.
  • Placement rule. All three Universal tiers keep the hovering ground-or-water placement. Naval fabricators are water-surface structures. Bot and Vehicle fabricators are ordinary grounded structures. Aircraft fabricators carry the hovering building type and place anywhere, exactly like the Universal.
  • Progression silhouette rule. BAR’s representative 6×6 T1, 9×9 T2, and 12×12 T3 factory footprints establish the progression grammar, while this game keeps domain-specific proportions: every T2 fabricator is wider, deeper, and taller than its T1 peer, and the sole T3 Universal is wider, deeper, and taller than the T2 Universal. The radial Universal body widths are exactly 10, 16, and 24 build-grid cells at T1/T2/T3. Each ring’s hover height is derived from the tallest authored visible envelope in that exact production roster, including raised turret/barrel geometry, plus the larger of 8 world units or 8%; collision diameter is not a height proxy. The T2 Aircraft Fabricator’s flight deck also sits higher than the T1 deck.
  • Menu-size target. About five entries per T1/T2 specialist — twenty specialist menu entries at each of those tiers, counted as entries rather than unique units, since cross-domain units legitimately appear in each domain they author.
  • Form and output rule. The three Universals are the only radial, quarter-turn-invariant fabricators: they keep the annular body, hold a nanoframe at its exact center, and release it there. Every specialist has a BAR-informed directional machine hall with a U-shaped build yard, side-mounted nano arms, and an open local +X mouth. Its facing rotates the complete yard, sockets, held product, and exit lane. On completion the product receives a mandatory move beyond that mouth before any rally route or factory-guard order, so a rally behind the building cannot turn the unit through the machinery.
  • Demo/full-base rule. Each initialized full base places one same-tier Universal per enabled producible unit, never a specialist. Each factory repeat-builds exactly that unit with an otherwise empty queue and quota state. T1, T2, and T3 units therefore receive T1, Advanced, and Experimental Universal hosts respectively, and no active unit can silently lose its production line. Factories place outside-in by tier: T1 is the rear/farthest row, T2 the middle row, and T3 the most forward row toward map center (smaller map-oval radius). Ground rows use radius fractions 0.88, 0.82, and 0.76; offshore rows use 0.96, 0.92, and 0.88. Water-required unit lines must place their complete Universal footprint over water; land-required lines must place over land.

Construction crafts start the advanced tier

Each domain has a tier-1 construction craft — the Construction Bot and Construction Rover on the ground, the Construction Drone in the air, the Construction Submarine at sea — and a corresponding tier-2 Advanced Construction craft. The gate on tier 2 production runs through the T1 craft: each authors its own domain’s fabricator at both tiers plus the T1 and Advanced Universals. The gate on tier 3 runs through every T2 construction craft: Bot, Rover, Drone, and Submarine all author the sole Experimental Universal Fabricator in their ordinary build roster. There is no animal-named constructor and no domain-specific T3 fabricator. The Commander starts the five T1 fabricators and nothing Advanced or Experimental. Assist needs no rule at all: construction assistance has never consulted the assisting builder’s roster, so any builder can keep an advanced frame growing once it exists — starting is gated, finishing is communal, which is exactly the BAR-parity behavior. The construction crafts themselves are ordinary units of their domains, so each same-tier Universal produces its construction crafts by derivation, with no special case. Construction craft are the deliberate naming exception to the animal roster: a tier-1 builder is named Construction <X>, while a tier-2 builder is named Advanced Construction <X>. The functional name does not exempt its visual design — each construction craft still owns a unique chassis silhouette.

Construction craft are workers, not combat hybrids. The Commander is the sole mobile unit allowed to combine a structure-build roster with classical attack turrets. Every Construction and Advanced Construction craft mounts sensors and a work emitter but no attack turret; Reclaim remains its hostile economic tool. A mobile factory such as a Queen may remain armed because producing its one unit is a factory workflow, not a structure-build roster or construction-craft capability.

Unit identity is visible, unique, and tier-coded

Every unit and building authors two player-facing identity fields: fullName for prose and roomy UI, and an exactly five-character shortName using uppercase letters, digits, or hyphens for fixed-width UI. Short names are unique across the combined unit/building catalog. A narrower internal three-letter tinyName may remain for portrait fallbacks, but it never replaces either player-facing field.

Every non-construction unit has one explicit animal identity and a unique player-facing animal name. Every tier-2 animal uses its authored Latin taxonomic name; Formik is the restored name of unitFormik. Every tier-3 unit uses a dinosaur name and carries the dinosaur animal class; a non-dinosaur T3 identity or a dinosaur assigned outside T3 is invalid. Construction craft remain the sole functional-name exception and use exactly Construction <X> or Advanced Construction <X>. Every display name is unique, and every unit authors a distinct body shape and a distinct strategic niche. Unit blueprints are complete, orthogonal records: a unit may not $extends another unit or rely on a parent to supply locomotion, armament, cost, media traversal, construction authority, or presentation. Shared implementation belongs in imported code and shared presets; shared authored values remain explicit on every unit. Niche review considers the complete playable combination — tier and domains, cost, mass, durability, propulsion and damping in each medium, route permissions, sensors, weapons, work/factory capability, and special commands — so a cosmetic rename or tiny stat delta cannot disguise a duplicate. The blueprint loader rejects inheritance, duplicate names, and duplicate body-shape geometry, turning roster identity into a contract instead of a review convention. The support crawler’s complete identity is Daddy Longlegs; shortening it to a different animal name is invalid even though its fixed-width code remains DADDY.

Canonical entity images are tight three-quarter views

Every generated unit or building image consumed by build and production buttons, selection portraits, loading screens, and other static entity cards uses one camera contract. The camera views the entity from its front-right at 45 degrees horizontally and looks downward at 45 degrees. The complete rendered bounds are centered and fitted with only a tiny safety margin: the image uses contain semantics, fills as much of its square as possible, never crops any geometry, and never distorts aspect ratio. The Entity Lab opens on that same canonical view even though its diagnostic controls may then rotate or animate the model.

Transports carry one visible passenger, friend or foe

Every transport carries exactly one unit. Transport identity, cargo eligibility, and tuning are generalized blueprint data, but capacity is a design constant: one visible passenger, never a hidden six-pack. The passenger never disappears into cargo state — it stays in the world, fully visible, fully targetable, taking damage, and free to fire its own weapons the whole time it hangs in the beam. Eligibility is categorical, not diplomatic: a transport may lift any unit, friend or foe, and a hostile passenger keeps every combat right it had on the ground — including shooting the transport that is carrying it. Kidnapping a unit is paying for the privilege of a live, angry payload.

Sensing and attacking stay independent

A unit being able to detect a target must never imply it can attack it, and a weapon reaching a medium must never imply its host can see into that medium alone. Hippopotamus and Sea Turtle hear underwater without owning an underwater weapon; a torpedo aircraft may attack submarines while leaning on allied sonar for its targets; long-range artillery consumes team radar knowledge without owning a long-range sensor. The sensor matrices, emission trajectory matrices, lock-on masks, and team intelligence tiers stay separate authored facts (see Sight, radar, sonar, and contacts are separate information tiers); this separation is one of the project’s strongest features and no convenience coupling may erode it.

The information-counter loop deserves mobile hosts on both sides: mobile radar (a dedicated scout, not a repurposed gunship), a fragile radar-stealth/cloak scout, a detector with modest ordinary sight and no radar, and a mobile jammer with weak combat value — three narrow roles rather than another all-purpose super-unit — alongside the static Radar, Sonar, and jammer buildings and the existing stealth hulls. Narrow hosts teach systems; capstones hide them.

Sepia occupies the biological version of that stealth niche: a water-required, water-column scout with no land route, no ground propulsion, and no classical weapon. Its camouflage/cloak, radar and sonar stealth, underwater sight/contact contribution, compact body, and water propulsion let it approach and report from inside the naval medium. It may use ordinary contact when physically resting on the bed, but it never walks ashore or rides the water surface as a land gait. A marine animal name is not permission to inherit an amphibious turtle’s movement profile.

The compact roster names one readable host per gap

  • Information and work: the tier-1 Kestrel AWACS is an unarmed mobile-radar aircraft; Construction Bot, Construction Rover, Construction Drone, and Construction Submarine are the four tier-1 domain constructors. Tier 2 carries the fragile cloaked/radar-stealth Sepia Scout, the modest-sight/no-radar Strix Detector, and the Mobula Jammer with a deliberately weak light gun.
  • Weapon and counter showcases: the tier-1 Swift SAM Rover is air-only mobile defense; the Hedgehog owns the straight, never-turning dumb rocket; the tier-2 Brachinus fires the heavy mortar whose split produces medium-mortar submunitions. The Interceptor Tower is the only host permitted to target travelling shots, and it targets exactly controlled rockets, dumb rockets, and medium/heavy mortar shells. Ordinary beams and anti-air weapons no longer provide incidental point defense.
  • Water and cross-medium coverage: the tier-1 Water Strider is a crawler-domain + naval-domain body, supported at the water surface by both water-related lift channels while retaining stop-and-hold arrival behavior on land and water. It carries local same-/cross-medium full sight but no contact-only sonar annulus: its underwater contact radius is merely coextensive with the local underwater sight required to identify submerged targets. The Patrol Corvette is a water-only surface hull with an above-water gun and sonar; it authors no air lift, so a released Barracuda falls out of its Fabricator under gravity until its proportional in-water support catches it at the surface instead of hovering over the bay. The tier-2 Procellaria is aircraft + naval: its air-launched torpedo enters the water and attacks underwater, while its own sensors deliberately provide no sonar contact.
  • Naval economy: the Tidal Generator is a water-only energy producer, buildable by the Construction Submarine, so a naval expansion has extraction, energy, sonar, defense, construction, and production without a land dependency. Construction Submarines contribute only short underwater full sight and the coextensive contact needed to locate what that sight identifies; they must build or accompany a dedicated sonar source instead of inheriting an attack-submarine contact-only envelope.

Dormant capability is removal work, not a content prompt

A system nothing authors is not an invitation to invent a unit that justifies it; it is a second contract rotting next to the live one, and the rule for it is Delete The Old Path. Units are never added merely to exercise dormant functionality. Standing applications of the rule:

  • The timed “laser” ray variant is gone. The four continuous-beam families are the entire ray catalog. No blueprint ever authored a timed laser, so the variant’s branches, wire code, and material-response lane were deleted rather than answered with a Pulse Laser unit.
  • The cylindrical shield shapes are gone. The infinite vertical cylinder and aimed cylinder barriers had no host; the shapes that remain are the ones with meaningful hosts — the Daddy Longlegs and Widow spheres and the Loris’s aimed reflective panel. Shared force-material code that spheres and panels still use is untouched.
  • Resurrection is gone, wrecks and all. Death is an explosion and the end of the body: no wreck entity, no resurrect command, no resurrect UI, no wreck branch in reclaim. The battlefield lifecycle runs on construction, repair, reclaim of live entities and vegetation, and decay of unattended frames.

The mirror rule also holds: capability that is exercised somewhere must be showcased deliberately. Projectile health and interception get a dedicated point-defense host instead of staying incidental on general AA; the submunition path gets one readable cluster weapon; the unguided-rocket class stands beside the controlled rocket so aim, guidance, and point defense read as a contrast. One clear host per system beats three accidental ones.

Chat Is A Bounded Room, Not A Log

Every chat room retains and displays only its newest 10 messages. Every message is normalized to one readable line, empty results are rejected, and text is capped at 220 characters. The browser enforces those limits for immediate feedback and bounded local state; the network authority and the HOME chat backend enforce them again at their own trust boundaries. A client-supplied long history or oversized message can therefore never turn a room into an unbounded log.

The HOME conversation belongs to the sidebar

HOME chat is part of navigation, not battlefield chrome. It sits at the bottom of the sidebar’s content sections, immediately above the three permanent reference buttons (Entity Lab, Game Controls, Game Info). The title and section boxes use compact padding so the conversation remains visible without displacing the lobby directory. The Enter chat shortcut opens the sidebar when necessary and focuses that same input. Lobby chat remains the lobby’s shared room, while battle ALL and TEAM/SPEC communication remains in the battle console.

A diagnostic belongs to the system it describes

Match-wide live entity count and its cap are server/simulation capacity telemetry, so the ENTITIES meter lives in the SERVER bottom bar. The BATTLE bar owns game rules and player-facing battle controls; it does not duplicate server health metrics.

Universal Runtime Entity IDs

Blueprint IDs identify authored definitions. Runtime entity IDs identify live instances. They are different contracts, and the game needs both. Every addressable thing in the simulation gets a runtime EntityId, and the test is addressability, not category: if anything can point at it, remember it, lock onto it, damage it, or explain that it came from it, it is not anonymous. That covers units and buildings (top-level hosts), every mounted turret as an addressable emitter, every travelling munition — a plasma bolt, rocket, or missile that has left the barrel and now persists, spawns submunitions, and can be hit — and every build site. It does not automatically mint an entity for every emission. A ray projected by a live turret is a sustained emission of that turret, recomputed each tick from the turret’s aim and bound to its lifetime; it is attributed through the emitting turret’s id and the emission’s source record, not by allocating a separate id. (A shot is the opposite case — a travelling munition that does carry its own id.) Transient detail — a ray’s polyline vertices, resource balls in flight — stays anonymous for the same reason. Give one of these its own id only when the design genuinely needs to point at that specific instance; the default is to attribute it to its emitter.

Opaque handle, explicit metadata

EntityId is an opaque runtime handle, preferably generation-checked. It is not the place to encode player, team, host, blueprint kind, or storage layout as authoritative meaning. Those values are mutable, contextual, or implementation details; baking them into the numeric ID creates stale IDs when a unit is captured, a team relationship changes, a storage slot is reused, or a projectile outlives the turret that spawned it. The ID resolves through the entity registry into a dense metadata row. The metadata row carries the meaning. 

EntityMeta {
    id,
    kind,              // unit, building, turret, shot, ...
    blueprint_kind,
    blueprint_id,
    owner_player_id,
    team_id,
    parent_id,         // immediate containment parent, if any
    root_host_id,      // top-level unit/building, or self
    mount_index,       // turret/pylon slot when mounted
    storage_pool,
    storage_slot,
    generation,
    alive,
    targetable,
}

Systems may cache storage slots for speed, but the cache is never the identity. Commands, selections, lock-ons, projectile provenance, damage attribution, replay events, resource movements, debug tools, and audio events all speak in EntityId values and resolve them through the same registry.

The host hierarchy is complete

Every entity stores both its own EntityId and the host ids it belongs to, so the chain from a shot back to the unit or building that fired it is always explicit data, never an inference. The rule is uniform across all addressable kinds:

  • Unit, building — top-level hosts. Each carries its own EntityId; parent_id is null and root_host_id points at itself. A unit’s locomotion is part of that unit body, not a child entity — it carries no id of its own.
  • Turret — carries its own EntityId, its immediate parent_id, its root_host_id (the unit or building it is bolted to), and its mount index. It is addressable and lockable, but its lifetime, resources, and damage are owned by the host; it cannot detach into a hostless entity.
  • Shot — a travelling munition (plasma, rocket, missile) carries its own EntityId as a real body. A ray is a sustained line emission with no body of its own: it is bound to its emitter and attributed through it rather than minting an id. Either way the emission’s source record names both the turret id that fired it and the host id that turret was mounted on (see Shots carry immutable source provenance).

A building-mounted construction emitter, for example, stores both the turret slot it occupies and the building that carries it. This hierarchy is not inferred from blueprint order, array index, mesh ownership, or a renderer object tree. It is simulation data, validated at spawn, and available to every hot-path query that needs it.

The terms are deliberately narrow. parent_id means immediate containment. root_host_id means the top-level unit or building that owns the mounted assembly. owner_player_id and team_id describe gameplay ownership. They are stored beside the ID, not inside it.

Player, team, ally team — three words, three different jobs

Ownership is not one concept. Beyond All Reason (and the Recoil engine under it) splits it into three levels, and conflating any two of them produces a game that cannot express a 2v2v2. We use the same split and the same vocabulary:

  • Player — a client seat. A human or an AI holding a connection and issuing commands. Players are who talks; they are not who owns.
  • Team — the owner of units and of an economy. Every unit, building, shot belongs to exactly one team, and metal and energy are pooled per team. A team normally has exactly one player, which is why the two are so easily confused — but the engine allows several players to share one team (BAR calls this comshare), and when they do they drive the same units out of the same bank. Team is the unit-ownership answer.
  • Ally team — the alliance. Several teams that do not damage each other, that share vision, and that spawn inside one start area. This is what a player means by “my team” and what the lobby labels TEAM 1, TEAM 2, TEAM 3. Ally team is the friend-or-foe answer.

So a 3v3v3 is nine players, nine teams, three ally teams. Every question about the game resolves to exactly one of those levels, and the level is never inferred:

  • Who owns this unit, who pays for it, who gets the reclaim? Team.
  • Can this weapon damage that body? Does this guard order apply? Is this a valid capture, assist, transport, or shared-vision source? Ally team. Every one of these goes through the single alliance predicate; none of them compares player ids directly.
  • Whose cursor issued this command, and is that seat allowed to? Player.

The map follows the same split. Terrain dividers carve one slice per ally team, not per player, because a slice is a defensible frontage shared by allies — giving each player their own ridge-walled wedge would put a wall between teammates and make an alliance mean nothing on the ground. Inside its slice, an ally team spreads its teams evenly across the arc, so two allies start shoulder to shoulder behind one shared front rather than stacked on one point or split by terrain.

A one-player game is not a special case: it is one player, one team, one ally team, one slice. The general path runs it.

There is one path, and every surface that carves a map runs it. The home demo authors its seats per side; the game room hands its preview the host’s declared side count and the seat-to-side table the roster panel shows; the match builds the same table from the canonical, hashed initialization. All three resolve through the same roster builder, so the ground behind the lobby roster is the ground the match starts on: two seats on TEAM 1 share one slice in the preview exactly as they will in the battle, and a side the host declared and left empty is cut in both. A preview that counted seats instead of sides would put a ridge between teammates that the match then removes — a lie about the map.

A build site is the product, carrying its own id from frame one

A unit or building under construction is not a placeholder that later hands off to the “real” entity. It is the real entity, alive from the first frame in an under-construction state, carrying the EntityId it will keep for its whole life. Health, completion fraction, and buildability ramp up; the id never changes. A builder workflow targets that id directly, the player can select it and queue commands on it, and those selections and orders survive completion because nothing is swapped underneath them. There is no separate “build shell” id pointing at a “product” id — one continuous identity from nanoframe to finished structure. That is what keeps construction, damage, capture, lock-on, and command all speaking about the same entity, with no re-id handoff bug at the instant it completes.

Hosts build as complete assemblies

Construction no longer builds turret mounts as separate paid or damaged pieces. A unit or building under construction is still the product from frame one (per A build site is the product), but its authored turret set is part of that host assembly for the whole construction span. The host’s body health and build progress ramp together; its turrets may remain visually dim, disabled, or non-firing until the host reaches the authored readiness threshold, but they are not separate construction targets with their own cost or health.

A finished unit or building must therefore have its authored turret set present. Interrupting construction leaves an incomplete host, not a coherent finished body with empty turret mounts. Every host has at least one mounted capability. Attack turrets are materialized as targetable sub-entities; sensor-only and extraction-flow mounts are lightweight attachments with no firing state machine.

Shots carry immutable source provenance

A shot is not contained by its turret after launch, but it must retain exactly where it came from. Every shot, beam, projectile, submunition, and spawned child effect carries a source record: 

ShotSource {
    source_turret_id,
    source_host_id,
    source_root_id,
    source_player_id,
    source_team_id,
    source_turret_blueprint_id,
    source_shot_blueprint_id,
    spawn_tick,
    parent_shot_id,
}

Source provenance is immutable for the life of the shot. If the source turret dies, the host is captured, or the owning player is eliminated while the projectile is in flight, the projectile keeps its launch attribution. Damage, friendly-fire decisions, replays, submunition inheritance, audio, and debug traces read the source record; lock-on and collision read the projectile's current entity row.

Lock-on resolves entity refs

A turret lock, host target, command target, homing target, assist target, repair target, and build target all store an entity reference, not an array index. The reference is resolved through the registry and generation-checked before use. If the row is gone or the generation no longer matches, the reference is stale and the source drops or reacquires according to its normal rule. Turrets, units, and buildings can therefore lock onto any targetable EntityId in the world of any kind — a whole unit or building, a single mounted turret, a build site, or a travelling shot — that their own inclusion object admits, while the targeting kernel still gets fast access to kind, blueprint, owner, team, hierarchy, position, radius, and storage row.

This is a major design requirement, not a debugging convenience. A universal runtime ID system is the spine that lets targeting, selection, commands, resource flows, projectile inheritance, kill attribution, save/replay, desync diffing, and renderer inspection all talk about the same world without inventing local ID schemes.

Buildings Are Static Turret Hosts

A building is the immobile peer of a unit. It has a body, footprint, mass, health, host intent, and at least one mounted capability, but no locomotion. There is no separate tower entity type, blueprint catalog, lock-on family, selection type, or targeting pool. The former defensive towers and fabricator are ordinary building blueprints whose mounted capabilities make them attack, observe, or exchange resources.

Static infrastructure and turret behavior compose on the same host. A solar collector can mount lightweight extraction-flow and sensor attachments; a radar station mounts a sensor; a fabricator owns production/build power and mounts a sensor; a defensive emplacement composes its sensor profile onto its attacking turret. Capability checks decide which commands and systems apply. A building never changes family because a turret is added or removed from its design.

Build footprints are authored cell masks, not bounding rectangles

Every building blueprint owns one top-to-bottom footprintMask on the shared 20-world-unit build grid. A structure cell is both reserved and, for a grounded building, submitted to the locomotion obstacle layer. A clearance cell reserves construction space without inventing collision or path obstruction. Empty cells inside the mask’s bounding box are genuinely empty: placement, map bounds, terrain/plateau checks, resource coverage, build ghosts, queued build planning, demo placement, construction occupancy, and pathfinder sync must all iterate the same authored cells. The bounding width and height exist only for centered snapping and quarter-turn rotation; treating them as a filled rectangle is a bug. A building rotation is always normalized to exactly one of four canonical yaw values (0, π/2, π, -π/2) at input, command sanitization, simulation construction, footprint lookup, and rendering. Rectangular local render dimensions rotate with that yaw while authoritative world-axis bounds swap; no consumer may preserve a noisy near-quarter angle or rotate an already-swapped mesh.

Footprint silhouette follows visible plan-view silhouette. The three Universal Fabricators reserve progressively larger 12-by-12, 18-by-18, and 26-by-26 pixel-circle masks around their T1, T2, and T3 annular bodies. Specialist fabricators instead reserve authored rectangular U-shaped yards whose construction-clearance channel opens at local +X; a quarter turn swaps their width and height and therefore has real gameplay meaning. Extractors and radial defenses use chamfered or round masks; the converter uses its diagonal hex-like mask. The two shield research labs use distinct 12-by-12 campus masks and polygonal foundations, making them nearly Fabricator-scale without hiding a square visual base underneath either one. The solar collector has a 5-by-5 physical footprint, is natively yawed 45 degrees, and reserves a 7-by-7 diamond: twenty-one structural cells plus four construction-only tip cells beneath the fully opened panels. The wind turbine follows the same rule for its circular blade-sweep clearance.

A builder must remain completely outside the target’s rotated structural and construction-clearance cells before it can apply build work. If a build command creates a shell around a builder, the builder first receives a deterministic escape point beyond the reserved mask (including its own collision radius), and the new static body temporarily ignores every dynamic body it initially overlaps until that body exits. This is an escape guarantee, not permission to build through the footprint: work begins only after clearance. Repair, reclaim, capture, and ordinary build-range checks retain their own range semantics.

Build-square classes and exhaustive placement sets

Every build-grid cell has exactly one authoritative medium classification. A GROUND BUILD SQUARE has terrain at or above the waterline over the entire cell. A WATER BUILD SQUARE has terrain below the waterline over the entire cell. The host computes the exact minimum and maximum height over every piecewise-planar terrain triangle intersecting the cell; if both media occur anywhere in the cell, it is a split square and belongs to neither class. Center or corner probes are not allowed to turn a shoreline-crossed cell into a build square.

Medium classification is independent from flatness. The authoritative grid records the square class and whether the terrain surface or sea bed satisfies the shared flatness rule. “Flat” means no intersecting terrain face exceeds a 10-degree slope and every sampled support point resolves to the same plateau level. Relaxing this threshold from three degrees intentionally makes mountainous maps such as BOULDER MOUNTAIN substantially more buildable without weakening shoreline classification.

Every building blueprint authors a non-empty exhaustive placementSets list from exactly five values: ground-build-squares-hover, ground-build-squares-surface, water-build-squares-sea-bed, water-build-squares-sea-on-surface, and water-build-squares-hover-surface. Validation rejects unknown or duplicate values, more than one value for the same square class, non-canonical ordering, and any list whose values imply different physical anchors. This is a set of valid placement behaviors, not a taxonomy that forces duplicate building blueprints.

Ground-surface and water-sea-bed share the terrain-bed anchor and require flat terrain. Ground-hover and water-hover-surface share the visible-surface hover anchor and ignore bed slope; water hover also has no minimum-depth rule. Sea-on-surface has the water-plane anchor, ignores bed slope, and requires the whole cell to have enough depth for the submerged half of that particular building. Thus water-square classification answers “is this wholly water?”, while depth clearance separately answers “does this water-surface body fit?”.

Ordinary structures declare ground-surface only. Both metal extractor tiers declare ground-surface plus water-sea-bed, so one extractor blueprint works on a dry deposit or an underwater deposit and anchors to the real bed in both cases. Sonar declares sea-on-surface; the torpedo tower declares water-sea-bed; and the Fabricator declares both hover sets. Radar, sonar, and torpedo placement additionally verifies that the operative mount is in its required sensor medium, preventing a legal-looking but inert completed structure in shallow water. hoveringType remains a separate physical/body classification (fabricator for the radial Universal body and directionalFabricator for a specialist flight deck), not a placement policy.

A hovering building keeps the shared z-model — transform.z remains the ground-centered box center so build squares, snapshots, and the renderer base agree with every other building — and derives its floating body from it. Anything that touches the building as a physical or combat object MUST go through the anchor helpers (getBuildingCombatCenterZ, getBuildingVisualTopZ, getEntityTargetPoint): targeting cylinders, projectile and beam volumes, area damage, death explosions, audio, selection picking, and health bars all live at the floating body, never at the ground. Reading raw transform.z for a combat or presentation consumer is a bug by definition.

A hovering building’s ground-level presence is exactly one thing: its construction reservation. It has no ground collision body, blocks no locomotion cell, and casts no clearance. Its physical presence is a static annular ring floating at the combat center that matches the visible torus — aircraft collide with the ring, ground units drive underneath (the hover height clears the tallest unit by design), and released production shells fall through the open center hole. Units that spawn overlapping the footprint carry the standard ignore-static pair until they leave, so the structure never traps what it builds.

Mount control and typed tasks

Every mount has a stable mountId and a mount-owned controlMode of hostPreferred, hostOnly, autonomous, manual, or slaved. hostPreferred consumes a compatible host attack target before its own lock and may fall back autonomously; hostOnly never falls back; autonomous ignores host locks; manual waits for explicit ability fire; and slaved follows a named sibling’s target intent while re-running its own legality, range, intelligence, line-of-sight, ballistic, and shield gates. Build, repair, and production are host workflows rather than turret tasks.

One owner, three spatial envelopes

An attacking turret owns an engagement envelope for target legality, an observation envelope for its contribution to team intelligence, and an effect envelope for actual ray, projectile, or field reach. Effect inherits engagement unless explicitly authored otherwise. Observation never caps engagement: allied full sight may let a precision beam engage beyond its own sensor radius, and allied radar/contact sight may let a radar-capable weapon do the same. Required intelligence never expands engagement range.

Persistent shield spheres are passive mounted equipment and do not enter attack acquisition. Directional shield panels remain attacking mounts because selecting and aiming at the incoming threat is their defining behavior.

Identity creation is not a spawn turret

A build or production workflow creates the product’s permanent identity as a nanoframe, then applies construction work to that same incomplete entity. Identity allocation is an internal lifecycle step, not a mounted capability, aim participant, beam, or visible “spawn” effect. The host owns rosters, queues, placement, resource authorization, work rate, and workflow order.

Construction hosts carry restrained hazard markings

Every unit or building with a positive constructionRate carries one permanent yellow-and-black construction marking. The marking identifies build power without replacing the host’s team colour or turning the whole silhouette into a warning sign. Placement is authored once in constructionVisualConfig.json: the Commander uses a small dorsal collar, the Construction Drone a tail-boom sleeve, the Construction Submarine its rear propeller guard’s mirrored side plates, both Queens a neck collar, and the three Universal Fabricators exactly 1, 2, and 3 evenly spaced chamfered clamp boxes at T1/T2/T3. A thin stationary inner race supports a larger rotating outer race; each box is mounted on the outside of that outer race, carries a striped tangent face, and has a compact top emitter head. A zero-thickness or visibly floating Fabricator marking is invalid. Its geometry must also simplify visibly and monotonically with building LOD: High uses the chamfered housing, top latch, and paired corner fasteners; Medium uses a plain box and the top latch; Low retains only the mounted box and its essential striped identity face.

Every yellow/black boundary is a linear stripe at exactly 45 degrees in physical surface coordinates. Sleeves are open-ended, and circular hardware uses mounted boxes with tangent striped faces: coloured radial caps, ring sectors, wedges, and sunburst patterns are forbidden because they do not read as construction hazard tape. The browser and native renderer generate the same clipped stripe polygons rather than approximating the rule with unrelated shaders or renderer-specific geometry.

Both colours remain legible at close, mid, and far geometry tiers, and the marking follows the host through visibility, nanoframe, completion, and death-fade presentation. Coverage is capability-derived and exact: the set of marking profiles must equal the set of blueprints with positive construction rate, with one profile per host and no decorative extras.

Fabricator production has one non-negotiable host-relative invariant: from the instant a unit nanoframe exists until construction completes, its authored hold pose is immune to physics, locomotion, collision response, wind, and partial construction. For a Universal that pose is the exact horizontal and vertical center of the ring, independent of facing, with zero velocity. The stationary inner race and rotating outer race remain seated at one height during production. Each box stays attached to the outer race while its top emitter head telescopes upward; each work-spray emission begins at the top of one of those rotating extended heads and travels inward. Idle heads return to their seated box pose. For a specialist the hold sits in the visible build yard, rotates with the building, and receives spray from the authored side nano-arm sockets. Completion releases the hold and routes specialist output through the rotated local-+X exit before applying subsequent factory intent.

Selection Menus Are Uniform Per Host Kind

The action panel that appears when the player selects something must be small, consistent, and host-kind-aware. The selection distinguishes only units from buildings; mounted capabilities determine which standardized action categories are available. A blueprint never adds a bespoke button outside that capability vocabulary.

Uniformity applies to the command categories, not to the contents of a build or production menu. Builder rosters follow the BAR buildoptions model: each builder exposes the structures its own blueprint authors, and the panel displays that roster without broadening it to every player-buildable option. Fabricator production rosters are the one deliberate departure: they are derived, never authored per building — a fabricator’s menu is computed from its authored tier and domain against the units’ own authored production facts (see Roster Coverage And The Fabricator Matrix), so a roster change can never drift a menu.

Mixed selections (units + buildings) reduce to the intersection of the per-kind action sets, plus an explicit “select-only-X” affordance to drop down to a single type. The panel must never show an action that the active selection cannot execute.

Unit selection panel

Every category below is gated only by a type-defining capability the blueprint either has or lacks — the same shape as “build menu only if the unit is a builder.” A capability gate is sanctioned vocabulary, not panel creep: the rule this section forbids is a bespoke button on an arbitrary subset of blueprints with no capability behind it. A unit that lacks the capability simply does not show that category; a unit that has it shows the identical control as every other unit with the same capability. Each capability below is backed by a real authoritative system (cloak affects sensor coverage, the trajectory toggle drives the ballistic arc, manual launch forces an eligible weapon volley, transport load/unload moves real carried bodies, capture is a commander ability) — no entry here is dead UI.

  • Movement orders: Move, Fight, Patrol, Attack-Area, Attack-Ground, Guard, Stop, Wait.
  • Queue management: Undo Q, Clear Q, Ping.
  • Fire control toggle: Fire at Will / Hold Fire.
  • Trajectory toggle (only on units with an arc-selectable weapon): high-arc / low-arc / auto fire solution.
  • Cloak toggle (only on cloak-capable units): request cloak / decloak; the authoritative cloak state gates detector-vs-radar visibility.
  • Build menu (only if the unit is a builder): the build roster filtered to what this builder is allowed to construct.
  • Manual launch (only on units with eligible weapons): force one weapon volley at a clicked ground point.
  • Transport load/unload (only on transport units): load a selected unit / unload carried units at a point.
  • Commander specials (only on commander units): D-Gun, Repair, Reclaim, Capture.
  • Self-destruct.

Building selection panel

  • Set Lock-On Target (armed buildings): click any entity with an ID the building’s host lock-on inclusion object allows. The selection becomes attack intent; compatible host-controlled attack mounts consume it independently, while autonomous and manual mounts ignore it.
  • Clear Lock-On and Fire at Will / Hold Fire (armed buildings).
  • Production menu (factory buildings): the unit-build roster filtered to what this building is allowed to produce.
  • ON/OFF toggle (buildings with an active-state capability).
  • Self-destruct.

That is the full vocabulary. Adding a new action category requires a design decision about which entity type it belongs to, a real authoritative system behind it, and an update to this section. Once enumerated here, a category may be gated by a type-defining capability (builder, commander, cloak, transport, arc weapon, launcher) exactly like the build menu is gated by “is a builder.” What is not allowed is a bespoke button stuffed onto an arbitrary subset of blueprints with no sanctioned category and no capability behind it — that is the panel creep this section retires, and a command with no real system behind it is forbidden outright.

Producer Buildings Are ON/OFF

Solar collectors, wind turbines, and metal extractors carry a single binary state: ON or OFF. The state means exactly one thing and gates two outcomes together:

  • ON — the building can produce its resource (energy or metal) and takes normal damage.
  • OFF — the building cannot produce, and incoming damage is multiplied by 0.1 (10× more fortified).

Production and survivability are intentionally welded to the same flag so the player tradeoff is legible: keep producing and stay vulnerable, or stop producing and ride out the hit. The ON/OFF state is the single authoritative input for both the renderer’s open/closed pose and the economy’s production accounting; they must never disagree.

Materials Are Independent Of Shape

A surface material is a contract about how a surface interacts with the world: reflectivity, line-of-sight occlusion, projectile response, hit sound, shader treatment, particle reactions. Two pieces that mount the same material must look identical and behave identically. The only thing they are allowed to differ on is geometry — where the surface sits and what shape it takes.

The canonical example is ice. A frozen pond and a cuboid ice block are the exact same material: same reflectivity, same line-of-sight occlusion rule, same projectile response, same shader, same visual treatment. One piece carries the material as a flat sheet of terrain; the other carries it as a block. Beyond that geometric difference, a player should be unable to tell them apart by behavior or by eye, and there should be no code path that treats them differently.

  • A material is defined once, with all of its physical and visual properties — reflectivity, refraction, occlusion, hit response, sound profile, shader inputs, particle reactions.
  • Shapes carry materials. A cuboid block and a frozen pond can both be made of ice; a flat panel and a sphere can both be made of the same metal. Geometry and material are orthogonal axes of composition.
  • When a projectile encounters a surface, the material decides what happens to the projectile; the shape decides where the encounter is and what the surface normal looks like. The two questions are answered by different systems.
  • Line-of-sight queries treat every shape carrying the same material the same way: if one shape carrying a material occludes or reflects a sight ray, every other shape carrying that material does so under the same rule. The intersection math reads from the shape; the policy reads from the material.
  • Visual identity is part of the contract. Same shader, same material parameters, same reflection probes, same hit reactions. The player should see immediately that the pond and the block are made of the same stuff.

This is Single Source Of Truth applied to physics surfaces. If a feature ever seems to require a material to behave differently on one shape than on another, the right answer is almost always two materials with different parameter values — not a branch inside one material that switches on which piece owns the surface. Branches inside material behavior are how reflectivity drifts between two surfaces that the player still perceives as identical.

Every Surface Is Textured, At One World Texel Density

Surface texturing is not decoration applied to whichever models someone got around to. It is a property of the world: every face of every unit, building, turret, locomotion part, and ornament carries the faction’s surface vocabulary, and it carries it at exactly the same physical resolution everywhere. There is no untextured surface, no “flat colour” fallback tier that a blueprint can quietly land in, and no surface that is sharper or coarser than the one bolted to it.

Texel density is measured in world units, never in pixels

One constant — TRIM_SHEET_TEXELS_PER_UNIT — fixes how many texels one world unit of surface receives, on both axes, on every entity. Equal volumes of the battlefield carry equal texture: a 5×5×5 slab of a scout’s hull and a 5×5×5 slab of a Queen’s hull hold the same number of texels, so a Queen — roughly twelve times the scout’s linear size — genuinely carries about a hundred and forty times the texture area.

The consequence is deliberate and must not be “fixed”: a large entity viewed from far away reads as more detailed than a small entity viewed from close up, even when the two occupy the same number of screen pixels. That is what it means for detail to belong to the object rather than to the camera. Any scheme that normalizes texture resolution per entity — giving each model its own unwrap budget, or scaling a chart to whatever part mounts it — makes a scout’s rivets and a Queen’s rivets different physical sizes, and the roster stops reading as one faction built out of one stock of metal.

  • Density is a single constant applied on both axes to every charted and grained surface. There are no per-entity, per-blueprint, or per-part density overrides.
  • Raising the constant sharpens the entire game at once and costs sheet area quadratically. It is a global dial, never a local one.
  • Screen-space resolution is the camera’s business, and the detail ladder’s. It never feeds back into how much texture a surface owns.

One reference host, and a repeat

Every band on the trim sheet is drawn against one host — its hull lobes fix the plate, its head the sensor dome, its barrel the tube, its legs the strut and knuckle, its kit the livery. That host is the reference, and its charts are exactly one wrap of their surfaces, so it renders precisely as the bands were drawn.

Every other host wears the same bands, repeated by its own size against the reference’s. A hull twice as big wraps the plate band twice, so the plate is still the same number of world units across; a hull half as big shows half the band rather than a squeezed copy of all of it. The band never changes — only the wrap count does. That is the entire mechanism by which one drawn sheet dresses a roster whose parts differ in size by more than an order of magnitude, and it is why the reference host is a fixed point in the code rather than a special case.

Which axes may repeat, and why

Repetition is decided per band and per axis, by what that band draws on that axis. Two different things are wrongly called “texture” and this is where they separate.

  • An axis carrying only material — panel columns, plate courses, bolt rhythm — repeats. That is what holds a plate at its authored world size on anything it is bolted to.
  • An axis carrying a placed feature cannot. A sensor dome’s pitch slot is one opening at one azimuth running one full meridian; repeat either of its axes and the head grows a ring of slots or a stack of them. A barrel’s breech is at one end and its bore at the other. A strut’s collars are at its two ends, a knuckle’s flange across its middle, a livery band’s piping along its two edges. Those axes hold one wrap and let the structure scale with the part, because a bigger turret has a bigger slot, not more slots.
  • A repeating axis that wraps around a closed surface — a sphere’s azimuth, a cylinder’s circumference, a track’s loop — must repeat a WHOLE number of times. Band content is authored continuous across its own edge, so a fractional repeat lands the surface’s seam mid-band and mismatches the plating along one meridian. Rounding costs at most half a repeat of feature size and removes the seam entirely.

Structure scales; material repeats. Stating it per axis is what makes the invariant implementable instead of aspirational — a placed feature cannot be tiled without duplicating something that exists once on the real object, and material cannot be fitted to a part without breaking density the moment two parts differ in size.

Surfaces no chart claimed

Not every surface has a natural parameterization to chart against: a building’s walls, a wheel, a fan, a cone, an end cap, a generated ribbon. Those carry a projected substance grain instead — the same plating vocabulary at the same authored plate size, read from the fragment’s own position in the object’s frame rather than through a uv. Nothing has to be unwrapped or labelled, which is what makes total coverage reachable rather than a labelling campaign nobody finishes.

  • The grain’s plate is the hull’s plate. A structure and the unit parked beside it must be visibly the same stock of metal; a grain drawn at its own scale would be a second material pretending to be the first.
  • It is a fallback, not a default. Anything that is not plated armour — a barrel, a tyre, a track — gets its own band rather than the grain, because dressing rubber and running gear in hull plate reads as a unit built from one material and then cut into parts.
  • Detail goes where the camera can spend it. A part seen only edge-on — a track’s grousers and the rim they ride on, a couple of world units deep and scrolling past — gets a deliberately plain band; structure drawn there cannot be resolved and, on a moving belt, reads as noise rather than as structure. The track’s flat face, which has real area square-on and does not move relative to the hull, is where that budget is spent instead. One mesh may carry both: the label is a per-vertex property, so saying so costs no extra draw call.
  • Grain and chart are exclusive. A charted band already draws its own plating, and multiplying a second panel grid into it turns one material into mush.
  • “Untextured” is not a reachable state. A surface with no chart is not bare; it is plain material, and the grain is what plain material looks like.

The grain projects in the object’s own frame, corrected for scale

This is Materials Are Independent Of Shape made literal: the same steel lands identically on a sphere, a box, a swept ribbon, and a cone, because the projection reads position and normal rather than a chart.

  • The projection frame is the object’s, not the world’s. World-space projection makes a moving unit swim through its own texture and a turning unit rotate inside it. Object space is welded to the model.
  • The projection coordinate is scaled into world units by the instance’s own scale, including non-uniform scale. A barrel stretched to (radius, length, radius) must not show the grain stretched with it; that stretch is exactly the density violation this section exists to forbid.

The Formik is the reference model, not a special case

The Formik — its hull lobes, its legged locomotion, its rapid mortar, and its team kit — is the host every band was drawn against, because it is the one place where hull, nose, sensor head, barrel, strut, joint, and both livery surfaces were authored together. It is therefore the host whose charts resolve to exactly one wrap, and it must keep rendering exactly as drawn while everything else is derived from it.

That makes it a reference, not a privileged blueprint. No code path may branch on the Formik’s blueprint id to decide whether a surface gets textured or ornamented; charts are assigned by what a part is — a lobe, a nose, a head, a barrel, a strut, a knuckle, a tyre, a track grouser, a track frame, a strap, a collar — so a new unit is charted because it has those parts, not because somebody listed it. Whatever the Formik demonstrates, the roster receives, at the Formik’s scale.

Team ornamentation follows the host’s visual grammar

Team colour is carried by added geometry, not by recolouring the body: the body keeps the player colour and the ornament carries the ally team colour, so a unit reads as its alliance without giving up its owner (see the player/team/ally-team split). Mobile units share one designed body kit, and the Formik’s is the reference: swept shoulder rails tied together by arched cross ribs and seated into the hull with a spine ridge. Buildings do not share that body kit. Their silhouettes and moving machinery differ too much for one fitted visual to read as intentional, so each building authors team-colour geometry at the part that explains its function. Turrets still share a collar where their barrels emerge, because the turret interface is genuinely common across hosts.

  • Every mobile unit wears the rail-and-rib kit fitted to its own body extents; a unit never falls back to a plain box, slab, stripe, or fin.
  • Every building blueprint owns a distinct ornament treatment integrated into its machine: collector inlays, turbine bands, fabricator clamps, extractor seams or crown plates, sensor rims and collars, converter bridges, and defense-specific pedestal or emitter armour. A generic building roof frame is forbidden.
  • Every turret wears a collar sized from its own head radius, whatever blueprint mounts it.
  • All ornament pieces carry one semantic team-ornament role, ride host visibility and ownership changes, and obey the same Team Trim toggle even though their geometry is authored separately.
  • The unit kit degrades by shedding thickness and then ribs; building ornaments simplify with their owning meshes. Neither path sheds team colour before the host becomes a distant glyph.
  • Unit kits and turret collars use livery charts. Building ornaments use the same world-density surface material as the machine part they are integrated with, so they remain geometry rather than decals.

Nothing In The World Has A Clean Edge

A boundary between two materials is the single most reliable tell that a world was authored rather than found. Every other cue can be right — the palette, the density, the lighting — and a smooth contour of constant width will still read as a decal pasted onto the surface underneath it, because a smooth contour of constant width is a thing only a stencil produces. Weathering is therefore not a finishing pass somebody applies to whichever boundaries looked bad in a screenshot. It is a property of every place two materials meet, and it is generated from the same three terms everywhere.

The maths lives in one place (SurfaceWeathering3D) and every treatment calls it, because two weathered boundaries that meet on screen have to look like the same weather. Three sites use it so far: the ore region’s edge (MetalDepositEdgeBlend3D), the top and bottom rims of a plateau wall (TerrainWallWear3D), and everything that grows (VegetationWeathering3D). They differ only in which quantity is being weathered — a signed distance in world units, a geodesic distance to a rim, a height above a plant’s own base — and in what substance they paint, which is one shared soil tile read through different tints. What follows is the recipe, stated generally, because every boundary in this game is supposed to receive it.

Three terms, and they are not interchangeable

Each one fixes a different thing about a clean edge, and a boundary that gets only one of them still reads as authored. Displacement alone gives a wiggly stencil. Dissolve alone gives a fuzzy stencil. Grime alone gives a stencil with a line drawn along it.

  • Displacement moves where the boundary is. Two scales at least: broad lobes, and finer bites eroded into those lobes. It is applied to the metric quantity that defines the boundary — a distance, a coverage, a height — not to the colour that results, so the surface genuinely extends and retreats rather than smearing.
  • Dissolve destroys the boundary’s uniformity. Across a transition band the material is either present or absent, and a granular field decides which, rather than distance deciding it evenly. The band’s own width is sampled from a broad field too: a transition that is the same thickness along its whole length is still one authored number, however ragged its edge.
  • Grime buries the join. A band straddling the boundary, reaching different distances into the two materials, jittered along its length, thinned in patches, painting a third substance over both sides and darkening toward the contact. The two reaches must differ and both must be non-zero — grime that only lands on one side is an outline of the other.

Grow before you erode. Displacement that is symmetric about the authored boundary makes small instances of a thing smaller, and the smallest instance is usually the one whose size mattered. Push the boundary out first by roughly the displacement amplitude, then let the noise eat back into the slack.

The reflective term is the one that actually works

This is the part that is easy to leave out and impossible to substitute for. A dirtied boundary that keeps its material’s specular response still reads as a crisp edge, because the environment highlight traces the true contour exactly, at full contrast, underneath however much dirt is painted on top of it. The albedo terms are cosmetic next to this one.

So a weathered surface carries two coverages, and the difference between them is the whole point: the geometric coverage that says where the material is, and a second one — the geometric coverage minus the grime — that the PBR terms read. They must be separately named identifiers, and the shader source must be readable by a contract test, because handing the wrong one to a reflection term compiles perfectly and looks almost right.

Weathering is measured in world units, never in uv or pixels

The same rule as texel density, for the same reason. A boundary treatment sized in uv makes a big instance and a small instance of one material weather at different physical scales, and the world stops being made of one substance. Sized in pixels, it changes as the camera moves, which makes it a post-process rather than a property of the ground.

Sizing in world units also buys the level of detail for free. Sampled from a mipped texture, the granular field averages toward its own mean as the camera pulls back, so the dissolve resolves back into the smooth ramp it was perturbing instead of sparkling. A weathering scheme that needs an explicit distance fade to stop aliasing is reading its noise from something that does not filter, which is usually a hash function.

Noise is a baked field with named channels

Analytic hash noise in the fragment shader filters badly, costs more than it looks like it costs, and cannot be inspected. Bake the fields into a tileable texture instead, one scalar per channel, each channel authored for the ROUGHNESS its role wants rather than differing only in the world scale it is read at — two roles sampled from one field at overlapping scales stay correlated, and correlated roles produce a pattern the eye finds immediately.

  • Three channels, three jobs, three independent lattices: the smooth mottle that displaces, the granular field that dissolves, the broad blotch that sets thickness.
  • Alpha is not a fourth channel. A Canvas 2D surface premultiplies, so a field stored in alpha scales the three stored in RGB. Pin alpha at 255 and take three.
  • The dirt is its own authored material with its own palette, not the nearest existing tile recoloured. Reusing the cliff-rock tile for the soil at a boundary gives the grime the same slab vocabulary as the cliff behind it, which is the “two authored surfaces meeting” read the whole treatment exists to break.

Weathering never moves the thing it dirties

It is presentation, always. The displaced ore contour disagrees with the authoritative metal cells by the full displacement amplitude, and that is correct: the build-square overlay says where an extractor fits, and the ore’s silhouette says what the ground is made of. The moment a weathering term feeds back into placement, pathing, or a hash, it has stopped being weathering.

The exception that proves it: deliberately crisp lines stay crisp. Overlay rings, build squares, selection volumes, and HUD geometry are instruments, not terrain, and an instrument with a weathered edge is a broken instrument. Weathering belongs to material boundaries in the world.

Two lessons from the second and third sites

The ore edge could read its distance from a baked world-XZ field. The wall rims could not: at the shipped wall slope the top and bottom rims are a few world units apart in XZ, a field cannot tell them apart, and they want opposite treatments. Distance had to be measured over the mesh instead. Where the quantity comes from is per-site; only the recipe is shared.

And a weathering treatment will find every discontinuity in whatever it samples. Fed world XZ, it streaked down a vertical wall, because XZ barely changes there. Fed the geometric face normal, it drew the mesh’s own triangle columns down the cliff, because neighbouring wall triangles face slightly different ways. Fed a per-vertex ramp on a face with no interior vertices, it smeared over the whole drop. None of those were visible in the maths and all three were visible in one screenshot — which is the argument for looking at the surface rather than at the terms.

Where this has to land next

Three sites down. Every one of these is the same clean contour still waiting to be spent:

  • The biome ramp’s own transitions — grass to rock, upland to dry, and the shoreline band, which currently change over a smooth height/slope gradient with no displacement or grain at all.
  • The water line, where the liquid surface meets the beach.
  • Every mark a body leaves on the ground: burn marks, blast scorch, track prints, crater rims.
  • The contact between a grounded building’s slab and the terrain it sits on, which is currently a hard geometric join.
  • Wear on the hosts themselves — the plate edges, the joints, and the ground-contact surfaces of running gear, which the trim sheet draws clean.

Traps, all of which compile. Derivatives (fwidth, dFdx) are undefined in non-uniform control flow, and a weathering treatment is nothing but branches that neighbouring fragments disagree about — measure the screen width once at top level and pass it down. A field with a saturating encoding stops varying past its range, so a grime band that reaches further than the field encodes terminates in a perfect circle at exactly that radius, which reads as a rendering bug rather than as a tuning mistake; pin the treatment’s total reach against the encoding. And gate the whole thing on an early-out at that same reach: it is what makes eight extra texture taps affordable on a full-screen surface, because the fragments that pay are the thin fraction of the screen near a boundary.

A Shader Interface Is A Contract, And GPUs Disagree About The Rest

We write our own shaders, so we own the parts of them the language leaves underspecified. When a rendering fault appears on one GPU and not another, the useful assumption is never that the second GPU is broken. It is that our shader asked for something the spec does not guarantee, and one driver happened to answer the way we hoped.

A discrete value must never ride an interpolated varying

This cost real time, so it is written down. The surface-texturing shader passes a band code — which rectangle of the trim sheet a fragment reads — and it travelled as an ordinary interpolated varying, decoded with int(). Every vertex of a triangle carried the same code, so a perspective-correct interpolator should return it exactly. Nothing requires it to. A fragment landing on 5.99999 truncated to 5 and sampled a different band entirely; for a leg strut that neighbour was the whitest content on the sheet, so the miss appeared as bright white specks crawling over every legged and tracked unit — on NVIDIA, and not on Apple, because interpolation precision is a property of the hardware.

  • Anything used as an INDEX, an ENUM, or a BRANCH CONDITION is declared flat. Interpolating a selector is a category error: there is no meaningful value between two array slots.
  • Round rather than truncate when a float must become an integer, so an off-by-one-ulp value fails toward the right answer instead of silently reading its neighbour.
  • Pin it in a test. Shader source is the one place a contract cannot be expressed in the type system, so the contract test parses the patched source and asserts the qualifier is present in both stages.

Everything the shader declares, the host must supply

A uniform that is declared and used but never uploaded does not fail. The program links, the material renders, and the value is silently zero. That is the worst failure mode a shader has, because it looks like a rendering decision rather than a bug — a zeroed sampling ceiling once pinned an entire atlas to its sharpest mip and read as more aliasing, which is the opposite of the fix it belonged to.

  • Assign shared uniforms by iterating the object that defines them, never by writing one line per name. An omission then cannot be expressed.
  • Bound anything a driver may compute differently. Screen-space derivatives are the usual suspect: a ratio of two derivatives explodes where the denominator collapses (a silhouette) while the numerator does not (a texture sample). Clamp to what the effect can physically mean — relief cannot tilt a normal past 45 degrees, and an atlas cannot be sampled below the mip its gutters protect.

The machine that shows the fault must be able to bisect it

A fix for hardware-specific behaviour cannot be verified on the machine that does not show it. Ship the diagnosis, not just the patch: expose each suspect term as a development-time runtime knob so the person in front of the broken GPU can restore the old behaviour for one term at a time and answer the question in a line, rather than in a rebuild-and-guess loop.

  • Compare a surface that shows the fault against one that does not, and prefer comparisons that break several theories at once. Tracked units sparkling alongside legged ones eliminated the transparent pass, the instanced path, and curvature in a single observation, because tracks share none of those with legs — only a chart.
  • Test in the real scene. Preview and lab harnesses build their own materials and their own rigs; a locomotion shading fault cannot reproduce in a viewer whose legs are a different material on a different code path.

Resource Accounting and Work Presentation Are Separate

The resource-movement ledger is the source of truth for accounting, UI, replay, and diagnostics. It records typed metal and energy movement with amount, direction, source, target, and reason. Presentation is a consumer of that ledger, not a mandatory physical reconstruction of every accounting entry.

Economy buildings should communicate their role through localized authored motion — turbine rotation, collector articulation, extractor activity, converter state — while a pylon-ball view may exist as an optional economy/debug overlay. Normal battlefield rendering does not require every ledger entry to create world-space balls.

Hard invariant: construction and repair show build power

Builders and factories own one build-power capability and one or more authored work-emitter points. Construction and repair emit the same outward particle stream. Particle density follows realized work: construction progress or restored HP converted through the target’s original build duration. It never follows independent metal and energy rates.

Build spray is bright green, as in Total Annihilation — not the builder’s team colour. Nanolathe work is the same physical act whoever performs it, and one fixed colour makes “something is being built here” readable across the whole map at a glance, including on a team whose colour is dim, blue-grey, or already carried by the structure being built. Team identity is already written on the builder, the frame, and the HUD; spending a fourth channel on it costs the read and buys nothing. Repair keeps its own white so the two acts stay distinguishable, and pylon resource balls keep their per-resource colours — those encode which resource, which green would erase. Build spray, plasma heat, and hot explosion tetrahedra are self-luminous gameplay cues: they remain at their authored display brightness when scene exposure is low instead of being multiplied into darkness.

  • The spray colour is authored in resourceConfig.json, not derived from the player, and applies to construction, assist, and reclaim alike.
  • Spray particles are presentation only. They carry no simulation state, are never serialized, and no gameplay decision may read one. Their count, jitter, spin, and lifetime are free to differ between clients.
  • Build particles use the tetrahedron silhouette at a stable orientation and spend no CPU or instance-matrix work on visually insignificant tumble. Their moving path and changing screen silhouette already read as thrown material.
  • Spray is depth-tested against solid world geometry, so a unit, building, or terrain surface in front hides it. The transparent water surface draws after the spray, allowing submerged nanolathe work to remain visible through water without granting the effect x-ray visibility through solids.
  • Construction consumes metal and energy as one coupled work step. If either resource is unavailable, that step scales down or stalls and neither lane may advance by itself.
  • Repair of a completed entity consumes no metal or energy. It is limited only by build power and the target’s original construction duration.
  • Applying Repair to an incomplete entity is construction: it consumes coupled resources and advances the nanoframe instead of entering the free-repair path.
  • Metal and energy remain separate accounting records and UI facts, but they do not create separate construction sprays, emitter rigs, or doubled particle streams.

Optional pylon overlay contract

When the optional economy overlay is enabled, its pylons retain the conduit rules below. Those rules describe the overlay faithfully; they do not require pylons on builders or factories and do not make pylon balls the normal view’s sole economy indicator.

  • A pylon is tagged with exactly one resource type: energy or metal. A host that touches both resources mounts one pylon per resource — not one combined pylon with a polymorphic type. Per-resource pylons keep the player’s read of "what is flowing where" decomposable.
  • A pylon’s flow is communicated entirely by its pylon resource balls: discrete coloured spheres that visibly flow either INTO the pylon head or OUT of it. Their density — how many are in flight per second — encodes the magnitude of the resource rate, and their direction encodes which way the resource is moving within the optional overlay.
  • A pylon’s direction encodes the local physical flow of the resource at the pylon’s tip — the head, where the pylon meets the world. Inbound balls mean the world is feeding the tip and the resource then rides down the tube into the pool — a solar collector pulling energy from the sun, an extractor pulling metal from the deposit beneath it, a converter’s metal tip catching the metal its energy tip just made. Outbound balls mean the resource first rises up the tube from the pool and the tip then projects it into the world — for example a converter’s energy tip ejecting the energy it is consuming. Down the tube is always gaining and up the tube is always spending, so the net effect on the player’s stockpile is recovered from the host’s role plus this single direction; it is not encoded by some second orthogonal field on the pylon.
  • A pylon that has a discrete economy target aims its ball flow at that target. A pylon that interacts with "the pool" or "the environment" as a whole — solar, wind, extractor, converter — uses random world-space directions for the inbound or outbound balls. The absence of a target is a real configuration of the contract, not a missing field.

A pylon is a conduit: root, tube, head

A pylon is not a point; it is a conduit with two ends and a tube between them. The root is the bottom, where the pylon taps the player’s shared resource pool. The head — the tip — is the top, where the pylon meets the physical world: the sky, the wind, a metal deposit, or another economy endpoint. The tube is the visible shaft the resource balls travel along between the two. Inbound and outbound, defined above at the tip, are simply the two ends of one journey: balls travelling down the tube mean the host is gaining that resource (production, reclaim, conversion output), and balls travelling up the tube mean the host is spending it (conversion input, upkeep, or another overlaid economy debit).

The tip conserves. It is a pass-through, never a spawn and never a sink: every ball that travels up the tube must leave through the tip, and every ball that enters the tip must travel down the tube. Resource balls are created and destroyed only at the two real endpoints — the root, where they fade into or out of the abstract pool, and the world point (deposit, sky, build target) on the far side of the tip. So a producer ball’s whole life is world-source → into the tip → down the tube → gone at the root, and a consumer ball’s whole life is born at the root → up the tube → out the tip → onto the target. Nothing appears or vanishes at the tip itself; if a ball reaches the tip, it has somewhere it must go. Every ball is accounted for before and after the tip.

Within the optional overlay, the moving stream carries both direction (which way along the tube) and magnitude (how densely the balls flow). In normal play, localized machine animation and the economy UI remain the primary indicators.

Rate gates a ball’s birth, not its flight

The resource rate has exactly one job: it sets how often new balls are born — the spawn cadence, and therefore the density of the stream. It must never reach into the tube and retune, relocate, or destroy a ball that is already moving. A ball is committed the instant it is created. From then on it travels its whole documented life at a constant pace — born at the root → up the tube → out the tip → onto the target, or world-source → into the tip → down the tube → gone at the root — even if the rate drops to zero or spikes the instant after it spawned. A rate change retunes the cadence for the next balls; every ball already in flight is immune and finishes its journey.

This is what makes tip conservation literal and one-to-one. The tube leg and the free leg outside the tip are not two independent rate-driven animations that happen to line up at the head; they are one conserved stream rendered in two pieces, handed off ball for ball. A ball climbing the tube that reaches the tip disappears there and spawns exactly one ball that continues — the outbound free-leg ball that flies from the tip onto the build target. Symmetrically, an inbound free-leg ball that arrives at the tip from the world disappears and spawns exactly one ball that continues down the tube toward the root. The hand-off is the whole point: nothing is created or consumed at the tip, a ball merely changes which leg — and which renderer — is drawing it, and the count on each side of the tip stays balanced over time.

The failure this rule forbids is a tube whose live ball count is recomputed from the current rate every frame. Lower the rate and the surplus balls — ones that were already halfway up the shaft — simply wink out mid-tube; raise it and balls pop into existence in the middle of the bore. Both read as resource that was accounted for and then evaporated, or that appeared from nowhere — the exact opposite of every ball is accounted for before and after the tip. The free-leg balls outside the tube already obey this rule: each carries its own start point, end point, and lifetime, so a stalled or finished build never strands a ball in mid-air — it finishes its arc and only then stops being replaced. The tube balls must live by the same contract.

Density is the absolute transfer rate, scaled by one global knob

How many balls a pylon spawns per second is set by the absolute resource transfer rate — resources per second actually moving — not by the fraction of the host’s per-tick cap it happens to be using. A large factory paying hundreds of metal a second and a tiny builder paying a handful both spawn balls in direct proportion to what they move, so the factory’s tube visibly runs thick while the builder’s only trickles — even if both are nominally “at 100% of their own cap.” This is the resource-ball reading of two pieces that move the same resource at the same rate must look identical: balls measure throughput, and throughput is absolute, not relative to the mover’s size. Reading the rate off a cap fraction is exactly the drift this retires.

The mapping from transfer rate to ball cadence is a single global scalar, authored once in resourceConfig.json as ballsPerResourcePerSecond: balls per second = resourceTransferRatePerSecond × ballsPerResourcePerSecond. Raising it makes every stream on the map denser for the same economy; lowering it thins them all out. It is the one toggle for resource-ball density, and it changes only how finely a flow is sampled into discrete spheres, never what a ball means. Because it feeds a spawn cadence and never an in-flight count, turning it down mid-flow lets the balls already travelling finish and just slows the births behind them (see Rate gates a ball’s birth, not its flight). All resource-ball tuning — this scalar plus the cosmetic spray/tube constants — lives in resourceConfig.json rather than as literals scattered through the renderers (Config Is Data, Not Code).

Who carries which pylons

Economy hosts may author pylon origins for the optional overlay. Builders and factories do not mount construction pylons.

  • Solar collector — one energy pylon, inbound: balls fall in from the sun/sky direction, enter the tip, and ride down the tube into the pool; rate tracks current production.
  • Wind turbine — one energy pylon, inbound: balls stream in horizontally from the upwind direction (the same wind vector that drives turbine rate), through the tip and down the tube; rate scales with wind speed and the open/closed state.
  • Metal extractor — one metal pylon, inbound: balls rise from the metal deposit cells beneath it, into the tip, and down the tube; rate scales with deposit coverage.
  • Builders and factories — no construction pylons. They show one team-coloured work stream from host-authored emitter points to the entity being built or repaired. Metal and energy payment remains available to the ledger/overlay without becoming two battlefield sprays.
  • Resource converter — one energy pylon and one metal pylon running as a back-to-back consumer and producer. Converting energy→metal, the energy pylon runs outbound (balls up its tube, out its tip) and the metal pylon runs inbound (balls in at its tip, down its tube), joined by a taxed arc that recolors energy into metal in flight (see The converter is two tubes and a taxed arc). There is no separate "converter art" — the converter is two pylons running in opposing modes, and the same rig reversed would be a future metal→energy converter.
  • Any new economy mechanic publishes the same typed resource-movement record. It may add a localized animation or optional overlay origin when that improves legibility; it does not automatically add a permanent battlefield pylon.

The converter is two tubes and a taxed arc

A resource converter is the clearest test of the conduit model, because it is a consumer and a producer bolted back to back. Running energy→metal, its energy pylon draws balls up from the pool and ejects them out its tip in every direction (an outbound, consuming tip); its metal pylon receives balls at its tip and sends them down into the pool (an inbound, producing tip). The metal pylon therefore reads exactly like an extractor and the energy pylon exactly like a builder — same rig, opposing modes.

What ties the two tips together is a single taxed arc. Of the energy balls thrown from the energy tip, only the fraction set by the conversion ratio after tax arcs across to the metal tip; the remainder disperse into the air and are gone. The balls that cross change resource in flight, lerping from the energy color to the metal color in mid-air, and arrive at the metal tip to ride down its tube into the pool. The visible ratio of crossing-and-recoloring balls to dispersing balls is the conversion efficiency made physical — the tax is something the player can watch leak away. The arc still obeys tip conservation: a recolored ball that reaches the metal tip goes down that tube, and a ball that disperses never entered a tip to begin with.

One channel in the sim, one rig in the renderer

On the simulation side, every per-tick stockpile delta — production loops, build payments, converter ticks, reclaim recovery, anything — is recorded through a single resource-movement channel whose payload identifies the resource, the magnitude per second, the direction (inbound or outbound at the source pylon), the source entity, and, when applicable, the target entity. The accounting code that reduces those movements to per-player stockpile updates is the only code that touches stockpiles; there is no helper, no shortcut, no building-type-specific bypass that adjusts a player’s pool outside that channel.

On the renderer side, every optional overlay pylon is the same rig type configured by resource + direction + rate + optional target, driven by the same channel the sim publishes. The pylon mesh and the resource-ball emission pipeline are shape- and host-agnostic. Production-rate indicators and converter visuals all collapse into this one rig. When a new feature is tempted to add another resource-flow indicator, the answer is to render it as a pylon, not to invent a parallel visual.

This is the resource-side counterpart to Materials Are Independent Of Shape and Single Source Of Truth. The material rule says the surface contract is constant across shapes; the pylon rule says the resource-flow contract is constant across hosts. Two pieces that move the same resource at the same rate must look identical and accumulate identically. Branches that move resources outside the pylon channel are exactly the drift surface this philosophy is trying to retire.

Config Is Data, Not Code

Blueprints, tuning tables, and authored content belong in language-neutral data files — JSON today, possibly a more compact schema-validated format later — not in TypeScript modules. As the simulation moves toward Rust and WebAssembly, every piece of TypeScript-only data is a wall between the current code and the end-state engine. A blueprint authored as a .ts file forces TypeScript to stay in the simulation loop forever, because Rust cannot import it. The same blueprint authored as .json is read by both, owned by neither, and survives the language migration intact.

This is the data-side counterpart to Languages and Frameworks. That section commits the hot kernels to Rust/WASM. This section commits to making sure the data those kernels need is not trapped inside a TypeScript module that prevents the migration from ever completing. Configuration in code looks convenient on the way in; it becomes a permanent dependency on the language you were trying to leave.

Entity blueprint JSON files are the single source of truth for authored entity facts. units.json, buildings.json, turrets.json, shots.json, and rays.json own the gameplay numbers and atomic composition of those entities. Loaders may resolve references, validate shape, and compute runtime derivatives such as scaled force or packed bitmasks, but they must not re-author the same value in code. Tests likewise assert schema, transforms, and invariants by reading the JSON source; they do not carry a second table of expected blueprint values that can drift from the data.

What belongs in JSON

  • Unit, turret, shot, and building blueprints — every field on every atomic gameplay piece (a unit’s locomotion among the unit’s own fields).
  • Tuning tables: damage curves, hover constants, friction values, mass tables, range tables, cost tables, build-time tables, recoil profiles.
  • Maps, scenarios, starting layouts, preset compositions, AI tuning, and any other authored content.
  • Wire codes, enum value-to-name maps, and cross-language identifiers that both TS and Rust must agree on. One file, two consumers, zero drift.

How to express behavior as data

Blueprints must not contain TypeScript functions, closures, or computed references. If a behavior requires a decision — damage falloff over range, turret aim style, shot trajectory shape, hover response curve — it is encoded as a discriminated union of data shapes that the simulation interprets, never as a callback smuggled into a blueprint. The blueprint says { "shape": "parabolic", "peak": 40, "gravity": 9.8 }; the simulation knows how to read that shape. This keeps every blueprint serializable, diffable, hot-reloadable, and parseable by Rust without a JavaScript runtime in the room.

Schema is the contract

  • One schema per atomic piece, declared in one canonical place, lives next to the data it describes.
  • TypeScript types and Rust structs are generated from the schema. They are not hand-maintained in two languages — that would just relocate the duplication problem from data to types.
  • Loaders in both TypeScript and Rust validate against the schema at startup. A blueprint that fails validation is a build error or a startup failure, not a silent runtime divergence.
  • Adding a field is a schema change. Both code generators run. Both languages see the field at the same time. There is no “I added it on the TS side and Rust never saw it” class of drift.
  • Defaults live in the schema, not in the loader. Every consumer reads the same defaulted shape.

Migration direction

Every blueprint file moved from .ts to .json is a step toward removing TypeScript from the simulation entirely. The shape stays the same; the syntax changes; the callers stop importing a module and start loading a file. As blueprints become data, the Rust/WASM simulation gains the ability to consume them directly, and the TypeScript blueprint modules disappear under Delete The Old Path. The end state is a simulation written entirely in Rust, loading entirely from JSON, with TypeScript surviving only as UI, networking glue, and orchestration — exactly the role Languages and Frameworks reserves for it.

Single Source Of Truth

No gameplay rule, command builder, validation path, physics formula, serializer shape, blueprint contract, UI label, or tuning table should be duplicated. If two systems need the same atomic action, that action belongs in one small module with one clear owner and every caller imports it. Copying logic between client, server, renderer, lobby, tests, and debug tools creates drift, and drift is a correctness bug.

File size is part of that source-of-truth discipline. Large files are not a neutral inconvenience; they are a signal that responsibilities have piled up and the code is harder to audit, test, port to Rust/WASM, or delete cleanly. When we touch a large file, we should split cohesive behavior into small helper files with named exported functions and import those functions at the call site. Do not copy a block into a second place to avoid an import. Do not leave a large file large when a clean helper extraction is available. The default shape is always small files, imported helpers, and one implementation of every behavior.

  • Extract shared helpers before copying code into a second place.
  • Split large files into small helper files with imported functions; never duplicate code to avoid a helper import.
  • Keep constants, enums, labels, thresholds, and wire codes in one canonical module.
  • Put command construction, authorization, and sanitization behind shared functions instead of reimplementing branches in components.
  • When duplication is temporary during a migration, delete the old path in the same change that proves the new one. See Delete The Old Path.

Delete The Old Path

Migration is not done when the new path works. Migration is done when the old path is gone. As we remove libraries, port hot kernels from TypeScript to Rust/WASM, replace framework helpers with owned code, and rebuild renderer paths around owned buffers or lower-level GPU APIs, the old implementation must be removed in the same change that lands the new one. Two implementations of the same behavior is two sources of truth, two places to fix bugs, two places to read when something looks wrong six months later, and a near certainty that one of them will drift.

This is the active counterpart to Single Source Of Truth. SSoT is the static rule: do not write the same logic twice. Delete The Old Path is the dynamic rule that keeps SSoT true while the codebase is in motion. Every time we replace a system, the replacement is incomplete until the predecessor file is deleted, its imports are gone, its config flags are gone, its wire codes are gone, and its tests are gone or repointed.

No legacy fallbacks

Budget Annihilation is served as one current build from one source. The working tree must therefore contain no legacy compatibility paths: no old packet or schema decoders, no deprecated argument shapes, no stale config migrations, no previous asset formats, and no runtime branch that substitutes an obsolete representation when the current representation is missing. A version change is atomic across the one producer and its consumers. Once the new contract lands, the previous contract and every test dedicated to it are deleted in the same change.

Missing or mismatched current data is an error and must fail loudly at validation, build, or startup time. It must never be guessed, silently defaulted, projected onto an older shape, or accepted because an earlier release once emitted it. Git history is the only archive. This prohibition applies to every layer of the project, including networking, save/state data, configuration, simulation APIs, rendering inputs, tools, and authored content.

One build, everywhere — no protocol versioning

The no-legacy rule has a stronger corollary that we now state as an explicit assumption: every frontend in a session is the same build, and the backend is always current. The game is served from one origin as one bundle; the peers a session connects are, by construction, running identical code, and the one backend we operate is deployed alongside it. We therefore maintain no protocol version numbers, no version handshakes, and no version-mismatch refusals anywhere — not on the lockstep messages, not in the connection metadata, not on the battle handoff, not as a schema tag inside the hashed match initialization. Versioning is compatibility machinery, and compatibility between builds is a problem we have declared out of scope: there is never a second build to be compatible with.

This is not a leap of faith — the system already enforces the assumption at a deeper layer for the one case that matters. The canonical match initialization hashes the automatic build fingerprint, so if two different builds ever did meet (a tab left open across a deploy), their initialization hashes differ and the lockstep hello/ready exchange refuses the match at frame 0. That guard is free: it is derived from the build itself, requires no discipline, and can never be forgotten. Every hand-bumped version string we used to maintain on top of it (lockstep.v7, match-init.v13, ba-battle-handoff-v2) carried no additional information and demanded a human remember to bump it — so they are gone. What remains are self-identification tags on saved artifacts (replay files, checkpoints, desync reports) and shape discriminators on packed wire sections, which name what a blob is, not which build wrote it.

One language per behavior

The most common shape of this rule in practice is the JavaScript/TypeScript-to-Rust migration. The moment a Rust/WASM implementation works — or a JS/TS library has been replaced by owned code that covers its functionality — the predecessor TypeScript file, JavaScript module, or third-party library must leave the tree in the same change. Two language implementations of the same behavior is not a transition state we are allowed to rest in: exactly one of them becomes the path that actually runs, and the other rots silently while still being importable, callable, and grep-visible.

We need one version of code, not separate code between multiple languages or libraries. A physics kernel ported to Rust deletes the TypeScript physics kernel it replaced. A renderer path rebuilt around a direct typed-buffer or custom-shader contract deletes the older per-object renderer path it replaced, whether the final draw still goes through Three.js or a lower-level API. A custom data structure or algorithm that supplants a library removes that library from package.json, its lockfile entry, and every import only when the library itself is no longer part of the chosen architecture. “Working in Rust” is the trigger; there is no “we’ll keep the TS version for safety” pause, no “leave the library installed in case we need it,” no parallel-paths phase that lingers across more than one commit.

This is an immediate deletion rule, not a cleanup preference. When a Rust/WASM version is working, the old JavaScript or TypeScript implementation is no longer allowed to coexist as duplicate functionality. It must be removed before the change is considered complete, because this codebase must never contain two versions of the same behavior split between JavaScript/TypeScript and Rust/WASM.

The end-state shape is one implementation per behavior, written in the language that layer commits to: Rust/WASM for simulation, physics, and dense numeric work; TypeScript for coordination, UI, and IO; custom GLSL / WGSL / GPU-buffer code for renderer hot paths. A behavior that exists in two of those languages is a half-finished migration, not a redundancy worth preserving. The moment the replacement works, the predecessor is dead code — and dead code in the working tree is treated as a bug to be fixed in the same change, not a TODO for later.

Why this matters here specifically

  • We are actively moving from JavaScript object loops and JavaScript physics math toward Rust/WASM kernels over typed-array linear memory. Leaving the JS implementation alongside the WASM kernel guarantees one becomes the de-facto path and the other rots, undetected, until something invokes it and produces a result that disagrees with the live path.
  • We are moving from per-object Three.js convenience helpers toward owned buffers, owned shaders, and direct instancing. Three.js may remain the backend, but a renderer with two active paths for the same visual makes it impossible to reason about draw-call count, allocation behavior, material compilation, or culling — the two paths interfere even when only one is supposed to be active.
  • Pooled DTOs, prediction state, snapshot buffers, and entity-state shapes are sensitive to dead code paths that still write to them. A “removed” system that still touches pooled fields is a class of zombie-write bug that does not surface in normal tests.
  • Future readers — including future-us — should never have to ask “is this the current path or the old one?”. The codebase should answer that question by only containing the current path.

Rules during a migration

  • The change that introduces the replacement is the change that deletes the predecessor. Not the next change. Not a follow-up cleanup ticket.
  • If parity proof genuinely needs more than one change, the predecessor lives behind a single named flag, with a single owner, and a recorded removal target. There is no “we’ll come back to it.”
  • Do not keep “just in case” copies of the old implementation in legacy/, old/, _unused/, or sibling files with a .old suffix. Git history is the just-in-case copy.
  • Delete the imports, the dead branches, the feature flag, the legacy wire codes, the unused config knobs, and the tests that exercise only the dead path. A half-deleted system is worse than an undeleted one because it looks intentional.
  • Never retain a compatibility decoder or default for an earlier packet, schema, config, save, argument, or asset shape. The sole current contract is required and version mismatches fail loudly.
  • If a library is being replaced, remove the dependency from package.json, Cargo.toml, and the lockfiles — not just the call sites. A still-installed library will be re-adopted by the next person reaching for the easy answer.
  • Renaming files is not a migration. If the new path lives next to the old path with a slightly different name and both still compile, no migration has happened — only confusion has been added.

What “removed” means

Removed means the code is not in the working tree, not behind a flag, not in a legacy/ folder, not in a sibling file with a .old suffix, and not in commented-out blocks. Git history is the archive; the working tree is the current truth. When someone greps for the name of an old function and finds zero matches, the migration is done. When they find one match in the active path and one match in a stale path, the migration is still in progress, and the next person to touch either file should finish it.

Explicit Absence

We are moving away from optional properties and optional chaining in our own simulation, server, prediction, and entity-state code. Absence should be declared, not inferred. A field should always exist with a typed value, and the absence of a value should be expressed as null (or a numeric sentinel in hot paths), so every site that reads it must make an explicit decision about what to do when the value is missing.

The problem we are solving is "seemingly ready when actually not." An optional field collapses three different failure modes into the same silent no-op: not yet initialized, semantically inapplicable, and previously torn down. An entity.turret?.fire() chain swallows all three. The unit just does not shoot, no stack trace, no symptom anyone can grep for. In an online multiplayer RTS with pooled state and high-frequency presentation snapshots, that class of bug compounds.

Why this matters more in this codebase

  • Pooled objects (snapshot DTOs, prediction state, audio events, scratch buffers) carry zombie fields between users when those fields are T? rather than T | null with an explicit reset on release.
  • V8 deoptimizes when objects have shape variance. field: T | null = null keeps the hidden class uniform and the JIT happy, which is measurable in 5,000-unit per-tick loops.
  • Snapshot serialization already encodes presence explicitly on the wire. Aligning the in-memory model with that contract eliminates a category of "I sent it but the receiver never had the property" drift bugs.
  • Determinism requires that absence is a decision, not a coincidence. ?. hides the decision; if (x === null) forces it into the code under review.

Scope of the rule

  • Inside our own simulation, server, prediction, networking, and entity-state modules: no ?: on properties, no ?. on access. Use T | null with explicit guards.
  • At third-party boundaries (Three.js, browser APIs, WebRTC): pragmatic optional chaining is acceptable. Wrap the boundary; keep our domain strict.
  • Function parameters with defaults (fn(x: number = 0)) are a different concept and remain allowed.
  • "Field is semantically inapplicable to this kind of entity" is not an optional field. It is a discriminated union. Express it that way.
  • In numeric hot loops, prefer a sentinel value (targetId = -1, tetherId = -1) over number | null. It avoids both the boxed null check and the shape variance, and it composes with WASM SoA storage.

Migration direction

This is a direction, not a hard cutover. We are not freezing the codebase to flip a lint switch. The rule we live by is simple: every file we touch should leave with fewer optional properties and fewer optional-chaining accesses than it had on the way in. Convert the field, fix the callers in that file, and move on. Over time the migration completes itself, the lint rule follows once the burden is small, and we stop shipping bugs that hide behind silent absence.

What New Code Should Optimize For

  • Keep the authoritative sim headless and portable. It should not depend on DOM, Vue, or Three.js.
  • Describe physical behavior once in the authoritative simulation; presentation consumes its outputs instead of reproducing gameplay systems.
  • Keep client motion work bounded to adjacent-tick presentation interpolation. Travelling shots and ray paths never run a second gameplay simulation in the renderer.
  • Keep rendering decoupled from simulation cadence; requestAnimationFrame samples state, it does not define truth.
  • Keep commands small, direct, validated, and host-owned.
  • Keep presentation snapshots recipient-aware and bounded in cadence for visibility, lifecycle, recovery, fog, economy, minimap, audio, and other non-root state. Same-process lockstep root motion reads local Rust/WASM history directly.
  • Capture authoritative position, velocity, full orientation, angular velocity, support normal, and turret pose for every live body after each fixed tick. Interpolate adjacent rows in one Rust/WASM batch and never extrapolate projectile state.
  • Use one presentation alpha for every continuous root and turret field. Do not reintroduce independent EMA correction channels that make parts of one body represent different effective times.
  • Make mass and force first-class fields in gameplay designs, not decorative metadata.
  • Keep entity blueprint JSON files as the single source of truth for authored gameplay facts. Runtime loaders may derive validated forms from those files, and tests may verify those derivations, but no test, TypeScript helper, Rust table, or renderer path should restate the same entity numbers as independent expected values.
  • Drive locomotion with velocity-aware arrival control, not position-only waypoint seeking. Units should brake against their current velocity when stopping distance runs out, and ground, drone, and plane profiles should share this controller while differing through physical limits.
  • Make locomotion one explicit physical profile expanded onto every runtime unit: actuator, motionControl, surfaceFollowing, two-domain navigation, and separate environmental hazards. Every unit has positive emergency water propulsion. Waypoint-valid cells own intentional, supportable destinations; move-valid cells are derived from active physical propulsion, and directed recovery edges allow a displaced body to return without authorizing water shortcuts. Terrain angle has no global ceiling: dry, bed-supported wet MOVE, and bed-supported wet WAYPOINT envelopes use exact mass, gravity, the local normal, μN, medium propulsion, and one 85% actuator reserve, while air and fluid-supported water ignore lakebed slope. Ground has dimensionless static friction plus explicit tangential and angular damping rates; air and water each have one named isotropic linear/angular damping profile. Surface-following sources are unit-authored forces and their required surfaceLiftResponse is exactly { randomizationAmount: 0, ema: 0 }, so the force is deterministic and unfiltered. Air and water use complementary occupancy fractions, navigation is explicit rather than inferred from the visual rig, and every acceleration is force divided by actual mass. Water damage is a universal numeric rate sampled only at the body origin; water-safe units author zero. The loader validates this hierarchy and compiles it into flat Rust/WASM rows without duplicating the model.
  • Apply gravity to every force-integrated mass body every tick; thrust-guided projectiles cancel it inside their bounded homing acceleration, while explicitly constant-speed-guided munitions preserve their complete velocity magnitude under a validated zero-thrust, zero-damping, zero-gravity kinematic policy. Never add a generic ignoresGravity flag.
  • Keep locomotion visuals entirely client-side: the sim publishes one chassis point, the rig places every wheel, cleat, foot, or fan in the world. Each rig clamps every part it owns to max(naturalY, terrainY + clearance) as a hard invariant — tunneling is never allowed, floating over dips is.
  • Derive per-part visual state from the interpolated root pose and interpolated velocities. Animation always plays off body motion; the rig never branches on whether a part is touching ground. Floor clamping and decorative spring controllers remain frontend-only and never alter the authoritative or interpolated root.
  • Keep the camera frontend and exhaustively enumerated: a gesture’s anchor point is the product of two orthogonal data axes — anchorPointCameraScreen (cursor / screen-center) and anchorPointCameraTerrain (plane-2d / terrain-3d) — while movement metric (bar-spring / anchor-distance-relative / absolute-world / absolute-world-momentum), focus height (focusHeightMode: constant-altitude canonical / terrain-follow BAR parity), BAR cardinal yaw locking, render transition (bar-spring-dampened / ema), and transition scope (all-movements / zoom-only) are separate config choices. All anchor behaviors and movement metrics must be reachable from config, never from a hardcoded branch in the picker. The canonical camera disables cardinal yaw locking, flies at constant altitude, applies pan/height-pan/rotation/follow immediately, and reserves its EMA for discrete zoom. Water is never an anchor surface and never a camera floor: anchoring over water reads the terrain bed, and the eye’s clearance floors on the bed alone so the camera may submerge. Relative zoom min-filters its anchor depth across the configured sample neighborhood and clamps one tick’s eye travel to zoom.travelClampFraction of controller distance. The canonical battle camera resolves collision lift at render time only — never committed into focus, distance, yaw, or pitch, so no gesture can be cancelled or outlived by terrain it brushed — keeps no fixed closest-orbit rail (constraints.zoomInLimit: none), and validates every committed pose — finite fields, padded map bounds, bed-to-rail altitude band, distance and pitch rails — at one constraint point.
  • Keep unit, building, turret, shot, and ray definitions atomic, swappable, and free of overlapping responsibility. A unit owns its locomotion inline; a building is the single immobile host family. Every unit and building mounts at least one turret. Make the turret a standardized, addressable mounted emitter with one authoritative effect family: attack, optional economy-overlay resourcePylon, or sensor. Construction, repair, and production belong to the host. Every turret blueprint directly owns one nested turretRange object containing lock-on range/volume/hysteresis and sensor matrices. A turret has no independent cost, mass, health, death explosion, construction phase, or detached life.
  • Keep visible volumetric hardware closed: hulls, engine housings, barrels, cones, and other solid unit/building parts include every end face needed from any camera angle and LOD. Open-ended geometry is reserved for explicitly hollow conduits, sleeves, beams, and overlays whose opening is part of their function; it is never an accidental missing cap.
  • Give every physical body the same base ledger before its kind-specific fields: a universal EntityId, a { metal, energy } cost, a mass, a health pool, and a { radius, force, damage } death explosion. These are a floor that unit, building, and shot bodies all meet. A turret is still an addressable entity for lock-on and provenance, but its resources and lifetime belong to the host. A unit’s locomotion is the same kind of intrinsic host behavior: part of the body, sharing the unit’s id, cost, and health.
  • Make every body death an explosion. When a unit, building, or shot’s health hits zero it detonates its death blast, applying outward force (heavier bodies resist more) and damage to everything in its radius, friend or foe. A shot’s detonation is the smallest case; a host death ends its mounted turrets as part of the same assembly, without separate turret health checks, detached turret pieces, or turret death explosions.
  • Name body geometry by physical role, not by ad-hoc size: every physical body carries three radii — radiusVisual (drawn size), radiusHitbox (the damage-receiving hurtbox), and radiusCollision (body-vs-body no-overlap contact) — with the same three names meaning the same things on units, buildings, and shots. A mounted turret may expose an addressable aim/selection volume for lock-on and line targeting, but that volume is a mount target on the host rather than an independent body. Keep the death explosion’s own radius separate from this trio, and keep the word “push” reserved for a future sustained push-field capability rather than this hard-contact radius.
  • Keep agency and command distinct: host bodies are agents with their own health and death, but the player commands only units and buildings. A unit moves itself; both host kinds control mounted turrets; a turret executes a typed effect while its host exists and its mount control mode is host, autonomous, or manual; a fired shot runs itself. Control runs down that chain, never past a host to puppet a part directly.
  • Do not let turrets live, die, detach, or build separately from their host. A turret has no independent cost, mass, health, or death explosion; killing the host kills the whole mounted assembly. A unit’s locomotion likewise has no health of its own — it is part of the body, so the only way to stop a unit moving is to kill it. Construction creates the host assembly as one product with its authored turret set, not body first and turrets later.
  • Make shots destructible bodies: every shot carries a tiny health pool and detonates the instant it reaches zero, running its normal explosion/splash/submunition path. Contact with the ground, another shot, or any solid body forces that health to zero on the spot. Emit every physical shot from its turret center in an inert state; it becomes contact-active only after its complete hitbox clears the host-centered ARM volume derived by enlarging the host's same-shape HIT volume at least 1.5 times while retaining the host collision margin. Once armed it collides with everything, including the host that fired it. Small-but-real shot health is what lets a point-defense turret shoot incoming munitions out of the air.
  • Give every addressable live instance — unit, building, mounted turret, travelling munition, and build site — a universal runtime EntityId plus the host ids it belongs to: top-level hosts point root_host_id at themselves, mounted turrets store parent_id, root_host_id, and mount index. A unit’s locomotion is not on that list — it is part of the unit body, not a separately addressable instance. Assign ids by addressability, not independent bodyhood: a mounted turret can be locked onto and can attribute emissions without carrying its own health; a ray sustained by a live turret attributes through its emitter instead of minting its own id; and a build site is the product carrying its final id from frame one rather than a shell that hands off later.
